# 写推特卡片 card.yml（一图速览）

推特卡片是在 X 上**引用（quote）一条源推文**时贴的一张图：刷推的人不点开报告，一眼看完“这是什么、为什么现在、我们查到了什么、所以呢”。卡片中间有一张 Excalidraw 手绘配图，先用图把最关键的发现讲出来，文字再补数字和结论。它是报告的第四种阅读深度（5 分钟 / 30 分钟 / 完整 / 推特卡片），比 5 分钟总览还要浅。

- 稿件：`$DIR/card.yml`（你写）；产物：`$DIR/card.png`、`$DIR/card.en.png`（`pnpm rh card <slug>` 生成，4:5、1200×1500）。
- 页面：报告的阅读路径里多出“推特卡片 / Tweet card”按钮，点开后有推文文案和“复制文案”“复制图片”（直接写进剪贴板，在 X 里 ⌘V 粘贴），以及“打开源推文”。
- 卡片会**公开出现在 X 上**。私有报告（尤其 `domain: work`）做卡片前先和用户确认哪些内容可以公开；卡片里不写私有站点地址。

## 立场：中立的研究者

卡片以**中立研究者**的身份发布，讲的是这个领域的事实，不是某家公司的立场或计划。

- **尽量不提 Mantle**（以及 `rh.config.json` 的 `cardAvoidTerms` 里的其他词）。报告是为 Mantle 写的也一样：把发现上升到领域层面（“EVM L2”“zk rollup”“用 SP1 的链”），而不是“Mantle 的 X”。`rh card` 与 `rh check` 发现这些词时会给警告。
- 只有发现本身就是关于某个项目、且换成泛称就不成立时，才点名；点名任何项目都只陈述可核对的事实（链上读数、官方文档），不评价、不站队。点名 Mantle 前先问用户。
- **不写给某家公司的建议**（“Mantle 应该…”“我们计划…”）。结论写成领域层面的判断或对所有同类项目都成立的动作（“L2 要自己…”）。
- 用词克制：不用“重磅”“颠覆”“必须立刻”这类营销或恐吓口吻；风险写清楚前提（“足够强的量子计算机**可**攻破…”，不是“量子已经攻破…”）。
- 改写后的泛化论断同样要有台账依据：报告台账里关于 Mantle 的 observed 行，不能直接当成“所有 L2”的证据；要找泛化的行（例如“L2 在 L1 上的验证器不会随 L1 升级自动 PQ 化”），找不到就不写。
- **泛化时保留台账的范围限定**：台账写“所调研项目”，卡片就不能写“没有项目”；证据只涉及 SP1 / RISC Zero，就不能写成“zkVM”；结论有前提（“继续在 L1 结算并切换新版 blob”）就写进 caption 或正文；只对部分架构成立的（如 zk rollup 才有 SNARK 验证器），在图上标成“示例”。未审计、PoC、草案阶段的数字要标出来。

## 版块与深度控制

| 版块 | 回答什么 | 上限（显示宽度） | 大约 |
|---|---|---|---|
| `title` | 主题 + 结论的钩子 | 56 | ≤ 28 个汉字 / 2 行 |
| `background` | 不懂这个领域的人必须先知道的**一件事**（是什么、为什么重要） | 104 | ≤ 52 个汉字 / 2 行 |
| `context` | 为什么是现在：源推文说了什么、最近发生了什么 | 104 | ≤ 52 个汉字 / 2 行 |
| `figure.caption` | 配图的一句话说明：图回答的问题，或读图的方法 | 44 | ≤ 22 个汉字 / 1 行 |
| `figure.excalidraw` | 配图：把最关键的一条发现画出来 | 2–8 个节点 | 见下文“配图” |
| `findings` | 我们的调研结论，**2–3 条，通常 2 条**（有配图，3 条只有每条都很短时才放得下） | 每条 76 | ≤ 38 个汉字 / 2 行 |
| `findings[].stat` | 可选：这条发现的关键数字 | 8，且一行放得下 | `6/14`、`~37×`、`$1.2B` |
| `takeaway` | 一句 so-what：读者 / 我们该怎么做 | 96 | ≤ 48 个汉字 / 2 行 |

显示宽度：汉字和全角标点算 2，英文字母、数字、半角标点算 1（卡片上一个汉字约等于两个字母宽），中英文共用一套上限。`rh check` 与 `rh card` 按 schema 检查上限；`rh card` 还在固定画布上排版，**超出画布就失败**。超出时删内容（先删一条发现，再把各段压到 1–2 行），不要想办法缩小字号。

深度的取舍：

- **背景只讲一件事。** 不是报告的“前置知识”面板缩写；挑读者不知道就看不懂发现的那一个概念。
- **现状对准源推文。** 卡片配的是那条推文：写它宣布了什么、和我们的调研有什么关系。一份报告只有一张卡片；换一条源推文引用时，按需改 `context` 和 `quote` 后重新 `rh card`。
- **发现 = 我们独有的东西。** 优先写报告里查到、源推文没说的：链上读数、对比、反直觉的事实、修正。不要复述源推文。
- **每条发现一个论断。** 一条只说一件事，能带一个数字就带（stat 是读者扫视时第一眼看到的）。
- **结论是动作或判断，**不是摘要的重复。
- **图和文字分工。** 图画结构或对比（谁在哪、哪边有问题），发现写图里放不下的数字和后果。图已经讲清楚的那条发现可以删掉，把位置留给别的发现。

## 配图（Excalidraw）

`figure.excalidraw` 与 explainer 里 ` ```excalidraw ` 代码块的 JSON 规格完全相同（完整语法：`node <am> help excalidraw`，写法见 am 文档 `references/diagrams.md` §4），在 YAML 里可以写成行内 `{ … }`。`rh card` 把它交给 answer-me-with-html 渲染并烘焙成手绘 SVG，放在卡片中间的浅色图区里。

- **图区约 508×140（卡片坐标）**，图按比例等比缩放。缩放后**图里任何一段文字小于 16px 就失败**（相当于手机信息流里约 9.6px，再小就要点开才能看）。实际上就是：**一行、2–3 个节点**，原图宽约 560 以内、高约 130 以内，节点 `fontSize` 20–22。不要画多行的图。
- **分组标题用 `texts`，不要用 `boxes` 的 `label`**：am 把 boxes 的标签固定为 14px，缩放后一定过小。写法见下面的示例（节点用 `x` / `y` 摆位，标题 `texts` 放在节点上方 36px 处）。
- **一张图只讲一件事**，2–8 个节点。常用三种：
  - **对比 / 分组**：两个节点并排，各带一个 `texts` 标题（如“随 L1 自动升级 / L2 要自己迁移”），只有问题那组用红色。
  - **流程**：一行 3–4 个节点，边上写动词（“签名”“确认”“升级”），出问题的那一步标红。
  - **前后对比**：同样的布局画两次，只改变化的那一处。
- 颜色含义和 am 一致：绿 = 结论 / 安全，红 = 问题 / 风险，蓝 = 被解释的对象，灰虚线 = 已知或外部，黄 = 假设。全图只强调一处。
- 节点里写名字和关键参数（`升级多签 ECDSA`、`SNARK 验证 BN254`），不写句子，最多 2 行（英文太长 am 会自动折成 3 行，要缩短）；节点标签和正文用同样的术语。
- `caption` 写图的适用范围或前提（“在 L1 结算并跟进新版 blob 的 L2”），或图回答的问题；不要重复图里的分组标题。
- am 的布局检查照常生效：“overlap”就调 col / row；“needs about N px”就加大 `grid.w` 或缩短边标签。错误会按语言标出（`zh：配图：…`）。
- 图里的每个事实同样要能在台账里找到。

## 推文文案（`tweet`）

每种语言写一段配图发的推文文案。它**不画进图片**，在报告页卡片模式里显示，有“复制文案”按钮；改文案不需要重新 `rh card`。

- **长度**：按 X 的计数（汉字、全角标点、箭头算 2，英文、数字、常用标点算 1，链接算 23），**80–280**。不超过 280，信息流里整条展示、不会折叠成“显示更多”。中文大约 100–130 个字，英文大约 220–280 个字符。
- **作用是帮读者读懂图**，不是把图上的字再抄一遍。三段，段间空一行：
  1. **钩子 + 分界**：一句话说清这件事的关键点（通常就是图要表达的那条线）。
  2. **读图**：告诉读者图左 / 图右 / 箭头分别是什么，以及图的适用前提（图上的 caption 往往只有一行，这里可以说完整）。
  3. **补一条图里放不下的**：一个限定、一个反直觉的事实，或解释图上某个前提（如 caption 里的“跟进新版 blob”是什么意思）。**不要重复卡片上已有的发现**。
- 和卡片同样的规则：中立研究者口吻、不提 `cardAvoidTerms` 里的词、只用台账里 observed / inferred 的论断、保留范围限定（“所调研项目”“未审计”）。
- 纯文本：不要用 `**`（X 不支持 Markdown）；不加 hashtag 和 emoji，除非用户要求；私有报告不放链接。
- 文案是引用源推文时发的：不用重复源推文说了什么，直接接上它的话题。

## 证据规则（与 explainer 相同）

- 卡片上每个论断都必须在 `research/ledger.md` 有对应行；只能用 observed / inferred 的论断。**不要把 speculative 写进卡片**（卡片上没有地方标注推测）。
- 数字要和台账、报告页一致（四舍五入方向也一致）。写 `~37×` 这类近似值时，台账里要有算法。
- 页脚自动写论断台账统计（导入报告没有台账时不写），不用手写。

## 格式

```yaml
# 推特卡片：pnpm rh card <slug> → card.png / card.en.png
quote: https://x.com/<handle>/status/<id>   # 可选：要引用的源推文，只在页面上显示为链接，不画进图
zh:
  title: 后量子迁移：L1 升级不等于 L2 全栈安全
  background: 足够强的量子计算机可攻破 EVM 签名、KZG 和椭圆曲线型 SNARK；哈希主要损失安全余量。
  context: Aztec 计划 2027 年选定方案、2030 年完成迁移；Ethereum 2029-12 的 PQ 目标只覆盖 L1 协议。
  figure:
    caption: 在 L1 结算并跟进新版 blob 的 L2   # 写清图的适用范围 / 前提
    excalidraw:
      defaults: { fontSize: 22 }
      nodes:
        - { id: l1, label: "共识签名 BLS\nblob 承诺 KZG", x: 0, y: 36, w: 250, h: 84, color: green }
        - { id: l2, label: "升级多签 ECDSA\nSNARK 验证 BN254", x: 300, y: 36, w: 250, h: 84, color: red }
      texts:   # 分组标题：用 texts 并写 fontSize（boxes 的 label 固定 14px，缩放后太小）
        - { x: 4, y: 0, text: "随 L1 协议迁移", fontSize: 22, color: green }
        - { x: 304, y: 0, text: "L2 自迁示例", fontSize: 22, color: red }
  findings:
    - stat: BN254
      text: SP1 / RISC Zero 的 STARK→BN254 外包装，最终链上验证不抗量子。
    - ML-DSA-44 签名 2,420 B，~37× ECDSA；未审计验签约 1.2M–8.1M gas。   # 不带 stat 时可直接写字符串
  takeaway: 所调研项目尚无全栈 PQ；L2 仍需制定自身迁移计划，不能只等 L1。
  tweet: |-   # 推文文案：多行用 |-，段间空一行；X 计数 80–280
    后量子迁移里有条容易被忽略的分界：Ethereum 2029-12 的 PQ 目标只覆盖 L1 协议。

    图左：在 L1 结算并跟进新版 blob 的 L2，可随 L1 获得；图右：L2 要自己迁，如升级多签、BN254 验证器。

    “跟进新版 blob”：EIP-4844 为 PQ 承诺预留接口；验证逻辑仍可能要改。
  # date: 2026-10-16   # 可选：卡片页脚的日期，默认用 meta 的 updated
en:
  title: "Post-quantum: L1 upgrades do not cover all of L2"   # 含冒号的值加引号
  ...
```

- 每段一行，不能换行；只支持 `**强调**`（画成高亮），其余 Markdown 原样显示。
- 双语报告要写 `zh` 和 `en` 两份。英文卡片和 `explainer.en.md` 一样交给 `sol` subagent 审（术语、论断定性、长度），达成一致后再渲染。英文不是逐字翻译：按英文读者的阅读习惯重写，同样受上限约束。

## 流程

1. 写 `card.yml`（新报告在把关 ③ 之前写好，和页面一起审；已发布的报告见 SKILL.md §9）。
2. `pnpm rh card <slug>`：失败就按提示删减后重试；排版失败时，被裁掉的预览在 `.rh/cards/<slug>/overflow-<lang>.png`。输出里的“剩余空白”是还能加的余量。
3. 用 Read 工具看 `card.png` / `card.en.png`：文字截断、数字放不下、高亮过多（每张图最多 2–3 处）、配图字太小或和文字重复、出现了 `cardAvoidTerms` 警告都要改。
4. `pnpm rh check <slug>`：`card.yml` 改过而 PNG 没重新渲染时会报错。
5. 和页面一起交给用户审阅（把关 ③）：两张 PNG、两段推文文案（`rh card` 的输出里有全文和 X 计数）；用户批准后 `pnpm rh publish <slug> --note "推特卡片"` 上线。
