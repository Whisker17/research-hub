EVM Execution Engines: revm, evm2, and Mantle's Execution-Layer Choice

evm2's real gain is in the interpreter hot path, and the only public head-to-head shows 1.10–1.19×. reth main has switched but not released. Mantle should first fix its revm stack (versions, differential tests, benchmarks), then evaluate evm2 in step with the OP upstream.

The short answer: evm2 does not define new EVM semantics. It is a reimplementation of revm. Its gain sits in the interpreter hot path, in three places (F1, F2):

  • a dispatch backend chosen at compile time;
  • compile-time instruction tables per type, spec and inspection mode;
  • pc, stack length and remaining gas kept in registers.

The only public head-to-head is a 10-block mainnet replay at 1.10–1.19×. The README's "up to 2x" has no public data (F3).

The ecosystem moved faster than the source material says. reth main replaced revm with evm2 on 2026-10-24, but no release includes it yet (F9). Base only builds evm2 in parallel and runs differential testing against revm (F11). RISE downstreamed revm into its own VM; it did not "downgrade revm" (F12).

For Mantle: do not migrate the consensus path now. Do three things first (F15–F18, actions): op-geth↔op-revm differential replay, a green CI on the revm fork, and a revm upgrade. Mantle is 5 majors behind.

I

Background

Running example: one ADD. It pops two words and pushes their sum, which takes a few machine instructions. The page uses it to show where the rest of the cost comes from, and what evm2 removes.

B-1

Interpreter dispatch

~4min
What it is

The interpreter reads an opcode, finds its handler function and calls it. How it finds and calls the handler is the dispatch method.

Why it matters here

ADD itself is cheap, but the dispatch cost repeats hundreds of millions of times. evm2's main gain is here.

Minimal example

revm: loop { op = code[pc]; table[op](&mut interp) }. TCO: each handler ends with a direct jump to the next handler, with no return to a loop.

Common misconception

Myth: 2× faster dispatch makes the node 2× faster. Fact: block replay also includes state reads, precompiles and keccak, which dilute the gain.

B-2

The revm framework

~4min
What it is

Evm holds a Context (Tx / Block / Cfg / Journal / DB), an instruction table, precompiles and an Inspector. Handler runs a transaction in four phases: validate → pre_execution → execution → post_execution.

Why it matters here

All L2 customization hooks into these extension points. The cost of moving to evm2 is mostly here, not in opcodes.

Minimal example

Context<BlockEnv, TxEnv, CfgEnv, DB, Journal<DB>, Chain>; state changes stay in the Journal until finalize().

Common misconception

Myth: revm relies on runtime checks. Fact: revm components are all generics, monomorphized at compile time.

B-4

JIT / AOT

~3min
What it is

Compile contract bytecode to machine code and run that. JIT compiles hot code at runtime; AOT compiles ahead and caches the result.

Why it matters here

gakonst's tweet says the new EVM has "JIT baked in". You need to know whether that means "available in the repo" or "on by default".

Common misconception

Myth: having a JIT makes execution faster by default. Fact: evm2-jit is off by default, and compiles a contract in the background only after 8 misses.

B-5

BAL (Block-Level Access List)

~2min
What it is

EIP-7928 makes a block carry the state that each transaction reads and writes. Validators use it to run transactions in parallel, then check the BAL.

Why it matters here

The GPT source treats BAL as an evm2 differentiator. revm v107 already has the same API.

Common misconception

Myth: a BAL comes with a parallel scheduler. Fact: evm2 and revm both give only read/write primitives; you write the scheduler.

How the hot path works: one ADD on each side

First the sketch, then the code. The top row is revm; the bottom row is evm2's TCO backend.

One step on revm main (Mantle's v107 has the same structure, but keeps gas and the function pointer in one struct [2]):

For each opcode revm reads the opcode, writes back pc, looks up two tables, charges gas, builds an InstructionContext and makes one indirect call. The handler gets &mut Interpreter, so the compiler cannot keep pc, stack length and gas in registers across that call (ledger H3, inferred).

evm2's TCO backend (nightly rustc): one function per opcode, monomorphized on const OP, ending in a tail jump.

The packed backend on stable rustc packs the pc pointer and the stack length into one usize, which handlers take and return by value.

build.rs picks the backend at compile time. It is not a runtime switch:

F1

evm2's real gain is in the interpreter hot path

confidence: high
Claim

Compared with revm, evm2 removes four costs: memory round trips for pc, stack length and gas; the runtime gas-table lookup; the spec branch inside gated opcodes; and, with TCO, the call/ret of the central loop.

Evidence

observed revm interpreter.rs:295-342@ee9ab3f; evm2 dispatch/tco.rs, table/packed.rs, dispatch/mod.rs:57-80@c8bb5a2 (ledger H2, H12–H17). inferred The list of savings comes from comparing the two structures (H20).

Implication

The gain depends on the workload. Compute-heavy contracts with many short opcodes gain most; blocks dominated by state reads and writes gain least.

F2

The backend is fixed at compile time: packed on stable 64-bit, TCO needs nightly

confidence: high
Claim

EVM2_DISPATCH_BACKEND is a build-time variable read by build.rs. Default rule: wasm → single_return, nightly rustc → tco, 64-bit → packed. The nightly cargo feature has nothing to do with TCO.

Evidence

observed evm2/crates/evm2/build.rs:21,41-72,88-97@c8bb5a2; the nightly feature in Cargo.toml (ledger H9–H11).

Implication

On a non-wasm 64-bit target, a stable build gets packed (1.10× in evm2#384). To use TCO, the nightly toolchain must be part of a reproducible build.

F3

"Up to 2x" has no public data; the only public comparison is 1.10–1.19×

confidence: high
Claim

evm2#136 added "up to 2x" to the README with no data. evm2#384 is the only head-to-head. Conditions: 10 mainnet blocks (2,279 transactions), Ryzen 9 7950X, against revm 42.0.1. Results: TCO 145.89 vs 173.32 ms (1.19×), packed 156.76 vs 171.81 ms (1.10×).

Evidence

observed alloy-rs/evm2#136 and #384 PR bodies (ledger H34, H35). observed #667 / #693 / #745 after #384 compare only against older evm2 (H36).

Implication

Quote "1.1–1.2× in replay", not "2×". Mantle must measure the current ratio against revm 43 in-house (see Reproduce).

F4

Single optimizations shrink in block replay and depend on code layout

confidence: medium
Claim

evm2#667 made snailtracer, burntpix and erc20_transfer 23–34% faster; the same change made mainnet replay only 4.8–6.2% faster. #745 reports that with target-cpu=native, editing an unrelated cold function moved snailtracer by 8.5%.

Evidence

observed alloy-rs/evm2#667 and #745 PR bodies, criterion medians on Zen 5 / Zen 4 (ledger H37, H38).

Implication

Fix the compiler flags and the machine for any evaluation, and replay Mantle's own blocks. Do not rely on single-contract benchmarks.

F5

evm2 is not "more compile-time" than revm: components are dyn, custom hosts are not supported yet

confidence: high
Claim

evm2 makes the type family (10 associated types on EvmTypesHost) and the instruction tables compile-time. DB, precompiles, Inspector and the JIT runner are Box<dyn>; transactions dispatch through HashMap<u8, Arc<dyn ErasedTxHandler>> keyed by type byte; evm2 can assert Send only at runtime. A source TODO says custom hosts are not well supported yet.

Evidence

observed evm2/src/evm/config.rs:20-57, evm/mod.rs:207-238,616-644, evm/registry.rs:350-352@c8bb5a2 (ledger X9–X13, X15). inferred The direction is the reverse of revm (X14).

Implication

The GPT source's "evm2 is more compile-time" is wrong. An L2 customizes evm2 with a type family, registered tx handlers and TxHandlerHooks; Base already uses these for deposits and the L1 fee (X16).

F6

BAL, async DB and the split Inspector path are not unique to evm2, so they are no reason to migrate

confidence: high
Claim

revm v107 already has the same BAL build and read API; revm main (v116, #3709) uses the same corosensei fibers for async DB; both engines split the tracing path from the plain path. evm2's parallel BAL example has no scheduler and no conflict detection; it only validates the BAL.

Evidence

observed revm crates/state/src/bal.rs, database/interface/src/async_db.rs@ee9ab3f; evm2 examples/bal_parallel.rs:64-101@c8bb5a2 (ledger X24–X26, X31–X33, X36). inferred X27, X34.

Implication

Mantle's v107 already has BAL and the split Inspector path. Only the fiber-based async DB needs an upgrade to revm main (v116); v107 has a blocking block_on wrapper (X32).

F7

The JIT is a port of revmc: off by default, BaseEvmTypes only

confidence: high
Claim

evm2#207 ported revmc into crates/jit (same main author, DaniPopes); the backend is LLVM 23. Default enabled: false. When enabled, a contract compiles in the background after 8 misses, with up to 4 workers and a 1 GiB resident cache. The JIT context accepts only BaseEvmTypes. Default single_error=true reports every failure as OutOfGas.

Evidence

observed evm2#207; crates/jit/runtime/src/runtime/config.rs:211,217,372,382, jit/context/src/lib.rs:45, runtime/src/evm2_evm.rs:29@c8bb5a2 (ledger H22–H27). inferred "JIT baked in" means in-repo plus a first-class hook, not on by default (H31).

Implication

An L2 with custom types, such as Mantle's op-revm semantics, cannot use the evm2 JIT today. Pilot JIT off the consensus path first.

revm's limits, split into "trade-off" and "fixable" (ledger X39, X43, H41–H43):

  • Design trade-offs: handlers take &mut Interpreter; the instruction table is a mutable Box; spec checks run inside handlers; all frames share one memory and the frame stack is non-recursive; generic parameters leak into the API; public traits expose interpreter internals (#3776 reports UB through the safe API).
  • Already fixed inside revm: async DB (v116), BAL (v107+), account-ext, SIMD jumpdest analysis (#3947, ported from evm2), split instruction and gas tables (#3561).
  • Possible but not merged: tail-call dispatch, tried three times (#2778, #3307, #3556). #3556 measured snailtracer 8.7% faster; CodSpeed reported a 3.76% overall regression.
  • Rejected by the maintainer: replacing SharedMemory with memory per frame (#3601). DaniPopes created the evm2 repo one week later (2026-04-30).
  • Pace: about 1.35 revm major versions per month; 12 of the 22 tags from v99 to v120 mark API-breaking changes.
F8

revm's hot-path limits come from API conventions, not from what is technically possible

confidence: medium
Claim

revm can implement TCO, register passing and compile-time opcode constants (#3556 had an implementation). The obstacle: these changes alter every handler signature and the customization model, so they break the API. The maintainer already rejected the memory change.

Evidence

observed bluealloy/revm#3556, #3601, crates/handler/src/instructions.rs:26-38,99@ee9ab3f (ledger H5, H41, H42). inferred H43.

Implication

"revm is bad" is not accurate. Accurate: revm puts a general extension model and compatibility first; the evm2 team chose a new repo to drop those constraints.

Common pattern: dispatch shape, stack reuse, jumpdest caching, parallel prewarm, plus old-vs-new interpreter diffs

confidence: high
Claim

geth #35638 keeps the old loop as a reference and runs diff and fuzz tests in every CI run. Besu #11524 diffs v1↔v2 per opcode and on random programs, and caught all 52 injected bugs. Besu v2 is 2.53× faster on arithmetic in JMH single-opcode micro-benchmarks.

Evidence

observed go-ethereum core/vm/interpreter.go:134-137@2006f08 and PR #35638; besu PR #11524 (ledger M31, M32, M35, M36). observed evmone, Nethermind and ethrex source (M33, M34, M37).

Implication

The recent geth and Besu rewrites both keep old and new paths side by side with continuous diffs. Whether Mantle upgrades revm or evaluates evm2, it needs this first.

The current EIP-7904 measured 6 full clients against a 100 Mgas/s target and decided not to change the gas table. reth is the worst client only on ECPAIRING_BASE, roughly tied with ethrex (ledger M39). The GPT source mixed this up with an older report on "7 standalone EVMs, revm 18" (M40).

P

Limits and open questions

Speculative, not used as conclusions on this page:

  • On Mantle mainnet, reth serves as RPC or verifier, not as sequencer (M17).
  • At 60M gas per 2-second block, peak demand is about 30 Mgas/s. That is below EIP-7904's 100 Mgas/s target, so the interpreter may not be the bottleneck today (M41).
  • The sequencer's block-building path may not benefit from the engine's parallel prewarm (M42).
  • "Up to 2x" may come from internal runs of compute-heavy benchmarks such as snailtracer (H39).
  • The JIT's single_error may change only trace / RPC error reasons, not state (H28).
  • MegaETH has an internal evm2 migration plan (A37); revm investment may decline (A41); revm's fiber async is a port from evm2 (X35); some Mantle core patches could become evm2 handlers (X41).

Threats to validity:

  • We ran no local benchmark: the evm2 bench build depends on mcl_rust, which needs cmake. All performance numbers come from project PRs, with conditions given in each finding.
  • GitHub code search covers only default branches, so we may undercount evm2's dependents.
  • We have no first-hand operations data on the mainnet sequencer or production flags.

Open questions:

  1. What is the current ratio of evm2 against revm 43, and against Mantle's revm 38, on Mantle blocks?
  2. Will the OP upstream (op-reth / op-revm) follow evm2, and when?
  3. When will evm2-jit support custom EvmTypes?
  4. Who ran the audit gakonst mentioned, what was its scope, and will the report be public?
  5. In Mantle block processing, what shares go to the EVM interpreter, state reads and the trie?

Glossary

dispatchinterpreter dispatch
How the interpreter finds and calls the handler for the current opcode.not transaction scheduling
TCOtail-call dispatch
Each handler ends with become, a direct jump to the next handler, with no return to a central loop; evm2 enables it only on nightly rustc.not JIT
packedpacked backend
evm2's default on stable 64-bit targets: the pc pointer shifted left by 11 bits plus the stack length in one usize, with remaining gas returned separately.not compressed bytecode
monomorphization
Rust generates one copy of the code per set of concrete type parameters, so calls skip the vtable.the opposite of dyn
dyntrait object, type erasure
A trait object called through a vtable at runtime.the opposite of monomorphization
Handlerrevm Handler
The revm trait that runs a transaction as validate → pre_execution → execution → post_execution.not an opcode handler
Journaljournaled state
The in-memory layer that records state changes and revert entries; revm reuses it across transactions, evm2 detaches it per transaction.not the database
op-revm
The OP Stack extension of revm: deposits, L1 fee, operator fee; in the optimism repo from v108.not op-geth
BALBlock-Level Access List, EIP-7928
A per-block list of state accesses that validators use to execute in parallel and then check.not the EIP-2930 transaction access list
JITjust-in-time compilation
Compiles hot contracts to machine code at runtime.not TCO
AOTahead-of-time compilation
Compiles contracts ahead and caches the result.
EESTEthereum Execution Spec Tests
The official Ethereum execution-layer test fixtures.
differential testingparity testing
Run two implementations on the same input and compare every output.not unit testing
prewarmingparallel prewarm
Runs transactions in parallel before the main loop to load state into caches.not parallel execution
EIP-7825transaction gas cap
The per-transaction gas cap added in Osaka.
revmc
Paradigm's EVM-to-LLVM JIT/AOT compiler; evm2-jit is a port of it.
