前置知识

运行示例：一条 ADD。它只做“弹出两个字、压入一个和”，本身只需几条机器指令。下文用它说明：其余开销来自哪里，evm2 省掉了哪些。

B-1

解释器分派（dispatch）

~4min
是什么

解释器读一个 opcode，找到对应的 handler 函数，再调用它。“怎么找、怎么调”就是分派方式。

为什么这里需要

ADD 本身很便宜，每条 opcode 的分派开销会被重复上亿次。evm2 的主要收益就在这里。

最小例子

revm：loop { op = code[pc]; table[op](&mut interp) }。TCO：每个 handler 末尾直接跳到下一个 handler，不回循环。

常见误解

误解：分派快 2 倍，节点就快 2 倍。事实：区块回放还包括状态读、预编译和 keccak，收益会被稀释。

B-2

revm 的框架结构

~4min
是什么

Evm 由 Context（Tx / Block / Cfg / Journal / DB）、指令表、预编译、Inspector 组成。Handler 按 validate → pre_execution → execution → post_execution 跑一笔交易。

为什么这里需要

L2 定制都挂在这些扩展点上。迁移到 evm2 的成本主要在这里，不在 opcode。

最小例子

Context<BlockEnv, TxEnv, CfgEnv, DB, Journal<DB>, Chain>；状态变更留在 Journal，finalize() 取出。

常见误解

误解：revm 靠运行时判断。事实：revm 的组件全是泛型，编译期单态化。

热路径怎么工作：一条 ADD 在两边的路径

先看示意图，再看代码。图上半部分是 revm，下半部分是 evm2 的 TCO 后端。

revm main 的单步（Mantle 用的 v107 结构相同，但 gas 和函数指针放在同一个结构里 [2]）：

每条 opcode 都要：读 opcode、写回 pc、查两张表、扣 gas、构造 InstructionContext、做一次间接调用。handler 拿到的是 &mut Interpreter，所以编译器无法把 pc、栈长度、gas 跨过这次调用留在寄存器里（台账 H3，推断）。

evm2 的 TCO 后端（nightly rustc）：每个 opcode 一个以 const OP 单态化的函数，末尾直接尾跳。

stable rustc 上的 packed 后端：把 pc 指针和栈长度压进一个 usize，handler 按值收发。

F1

evm2 的真实优势集中在解释器热路径

置信度: high
论断

相对 revm，evm2 省掉四类开销：pc、栈长度、gas 在内存里的往返；运行时查 gas 表；门控 opcode 里的 spec 分支；TCO 下中心循环的 call/ret。

证据

observed revm interpreter.rs:295-342@ee9ab3f；evm2 dispatch/tco.rs、table/packed.rs、dispatch/mod.rs:57-80@c8bb5a2（台账 H2、H12–H17）。inferred 节省项由两边结构对照推出（H20）。

影响

evm2 的收益和 workload 强相关：计算密集、短 opcode 多的合约受益大；状态读写密集的区块受益小。

F2

后端在编译期选定，stable 上是 packed，TCO 需要 nightly

置信度: high
论断

EVM2_DISPATCH_BACKEND 是 build.rs 读的构建期变量。默认规则：wasm→single_return，nightly rustc→tco，64 位→packed。nightly cargo feature 与 TCO 无关。

证据

observed evm2/crates/evm2/build.rs:21,41-72,88-97@c8bb5a2；Cargo.toml 的 nightly feature（台账 H9–H11）。

影响

在非 wasm 的 64 位目标上，stable 编译只拿到 packed（evm2#384 中 1.10×）。要用 TCO 就要把 nightly 工具链纳入可复现构建。

F3

“up to 2x”没有公开数据；唯一公开对比是 1.10–1.19×

置信度: high
论断

README 的“up to 2x”由 evm2#136 加入，PR 没有数据。evm2#384 是唯一正面对比。条件：10 个主网区块（2,279 笔交易），Ryzen 9 7950X，对比 revm 42.0.1。结果：TCO 145.89 vs 173.32 ms（1.19×），packed 156.76 vs 171.81 ms（1.10×）。

证据

observed alloy-rs/evm2#136、#384 正文（台账 H34、H35）。observed #384 之后的 #667 / #693 / #745 只和 evm2 旧版比（H36）。

影响

对外口径用“回放 1.1–1.2 倍”，不要用“2 倍”。当前对 revm 43 的比值需要自己跑（见复现）。

F4

单项优化在区块回放里被稀释，且对代码布局敏感

置信度: medium
论断

evm2#667 让 snailtracer、burntpix、erc20_transfer 快 23–34%，同一改动在主网回放里只快 4.8–6.2%。#745 报告：在 target-cpu=native 下改一个无关的冷函数，snailtracer 变化 8.5%。

证据

observed alloy-rs/evm2#667、#745 正文，Zen 5 / Zen 4 criterion 中位数（台账 H37、H38）。

影响

评估时要固定编译参数和机器，用 Mantle 自己的区块回放，不要只看单合约基准。

F5

evm2 并不比 revm“更编译期”：组件边界走 dyn，自定义 host 尚不支持

置信度: high
论断

evm2 把类型族（EvmTypesHost 的 10 个关联类型）和指令表编译期化；DB、预编译、Inspector、JIT runner 都是 Box<dyn>，交易按 type 字节查 HashMap<u8, Arc<dyn ErasedTxHandler>>，Send 只能运行时断言。源码 TODO 写着自定义 host 尚不支持。

证据

observed evm2/src/evm/config.rs:20-57、evm/mod.rs:207-238,616-644、evm/registry.rs:350-352@c8bb5a2（台账 X9–X13、X15）。inferred 方向与 revm 相反（X14）。

影响

GPT 资料“evm2 更强调编译期定制”的说法不准。L2 在 evm2 上的定制方式是：类型族 + 注册 tx handler + TxHandlerHooks，Base 已用这一套实现 deposit 和 L1 fee（X16）。

F6

BAL、异步 DB、Inspector 分离都不是 evm2 独有，不能作为迁移理由

置信度: high
论断

revm v107 已有同构的 BAL 构建与读取 API；revm main（v116，#3709）用同样的 corosensei fiber 做异步 DB；两边都把 trace 路径和普通路径分开。evm2 的 BAL 并行示例没有调度器和冲突检测，只验证 BAL。

证据

observed revm crates/state/src/bal.rs、database/interface/src/async_db.rs@ee9ab3f；evm2 examples/bal_parallel.rs:64-101@c8bb5a2（台账 X24–X26、X31–X33、X36）。inferred X27、X34。

影响

Mantle 的 v107 已有 BAL 和分离的 Inspector 路径。只有 fiber 异步 DB 要升级到 revm main（v116）才有；v107 只有阻塞的 block_on 包装（X32）。

F7

JIT 是 revmc 的移植：默认关闭，只支持 BaseEvmTypes

置信度: high
论断

crates/jit 由 evm2#207 从 revmc 移植（作者同为 DaniPopes），后端是 LLVM 23。默认 enabled: false；开启后同一段代码 miss 8 次才后台编译，最多 4 个 worker，常驻缓存 1 GiB。JIT 上下文写死为 BaseEvmTypes；默认 single_error=true，所有失败都报成 OutOfGas。

证据

observed evm2#207；crates/jit/runtime/src/runtime/config.rs:211,217,372,382、jit/context/src/lib.rs:45、runtime/src/evm2_evm.rs:29@c8bb5a2（台账 H22–H27）。inferred “JIT baked in”指同仓 + 一等钩子，不是默认启用（H31）。

影响

带自定义类型的 L2（例如 Mantle 的 op-revm 语义）目前用不上 evm2 JIT。JIT 只适合先在非共识场景试点。

revm 的限制，按“取舍”和“可修”分开（台账 X39、X43、H41–H43）：

  • 设计取舍：handler 签名是 &mut Interpreter；指令表是运行时可改的 Box；spec 在 handler 内运行时检查；共享 memory + 非递归 frame 栈；泛型参数在 API 中外溢；公共 trait 暴露解释器内部（#3776 报告了 safe API 触发的 UB）。
  • 已在 revm 内修掉：异步 DB（v116）、BAL（v107+）、account-ext、jumpdest SIMD（#3947，从 evm2 移植）、指令表与 gas 表分离（#3561）。
  • 技术上能做、但没合入：tail-call 分派试了三次（#2778、#3307、#3556）。#3556 自测 snailtracer 快 8.7%，CodSpeed 报告整体退化 3.76%。
  • 维护者拒绝：用每帧 memory 替换 SharedMemory（#3601）。evm2 仓库在一周后（2026-04-30）创建。
  • 节奏：revm crate 主版本约每月 1.35 次；v99–v120 的 22 个 tag 里 12 个标了 API breaking。
