DEVELOPER ONBOARDING · mantle-agentic-meme-launchpad

How an AI agent holds a limited key and launches and trades tokens on-chain for you

This page explains how two projects form one system: the 7702 SDK, which upgrades a wallet into a restricted smart account, and the meme launchpad built on top of it (contracts, CLI, autopilot, and an OpenClaw agent that runs in a container). It explains the principles first, then takes apart a real run step by step. After reading it you should be able to follow the code and tell which security boundary a change touches.

0The five-minute version#

What does this system do? Why is it safe to let an AI move money?

  • You talk to an OpenClaw agent in Telegram (in Chinese in this run). It checks balances, launches tokens, buys and sells, snipes new launches and claims fees for you on a meme launchpad on Mantle Sepolia. There is no frontend.
  • Your wallet is a normal EOA, upgraded in place to a Calibur smart account through EIP-7702: the address stays the same, and the root key stays in your own terminal.
  • The agent gets only a session key. The on-chain AgentPolicyHook allows only 5 functions, caps MockUSD spending in total and per day, and lets the agent sell only tokens it bought itself. The key expires after 24 hours, and you can revoke it at any time.
  • No transaction needs gas from you: the relayer of the sponsor service pays the MNT, so your account and the agent can both hold 0 MNT.
  • A deterministic autopilot daemon does the sniping. The LLM only writes the strategy, starts and stops it, and reports. A strategy starts only after you reply “yes”.
  • The only enforced boundary on trading rights is on-chain: the rules in the skill only bind a model that follows them. The container is a credential-isolation boundary: it keeps the root key and root home away from the agent, but it does not limit what the agent can do with the session key it already has. This is a POC: the contracts are not audited, and it runs on testnet only.

Principles

First the two projects one at a time, then together. Section 1 is the 7702 SDK: it gives the agent a restricted, revocable, gasless smart account. 17702 SDK: a restricted smart account for the agent#

How is the 7702 SDK designed? What happens on-chain and off-chain in one grant and one execution? How do we use it?

mantle-7702-sdk is a separate repository, published on npm as three packages: @0xwh1sker/mantle-aa-sdk, -cli and -sponsor. This project uses it only as a dependency (pinned to ~0.1.5) and never modifies, copies or forks its code. The problem it solves: how to let an untrusted AI agent use the money in an account, with a capped loss and the right to take it back at any time. Its answer has four capabilities:

  1. In-place upgradeA person’s normal wallet (EOA) becomes a Calibur smart account through EIP-7702. Address, balance and private key do not change.
  2. session keyThe person grants each agent its own key. It is not an admin key, it expires after 24 hours, and it can be revoked at any time.
  3. On-chain policyWhich functions this key can call and how much it can spend is checked at execution time by the on-chain AgentPolicyHook, not left to off-chain code.
  4. gaslessUpgrade, grant, execution, revoke: the sponsor pays gas for every step. The person and the agent can both hold zero MNT; the operator funds the relayer with MNT (step 0).

DESIGN

Three packages, three contracts#

The SDK has an off-chain half and an on-chain half. Each of the three off-chain packages has its own user: people use the CLI, programs (such as this project’s meme-sdk) use the TypeScript library, and the operator runs the sponsor. Of the three on-chain contracts, the account itself is Uniswap’s existing Calibur; the SDK wrote AgentPolicyHook itself and ported a VerifyingPaymaster for the 4337 path. The next two subsections explain why the packages are split this way and what each contract does.

The three packages are cut by “who uses it, where it runs, what it holds”. Dependencies go one way: cli → sponsor → sdk and cli → sdk. The sdk at the bottom depends on neither of the other two and carries nothing except viem.

What each of the three contracts does#

The split: Calibur decides “who can sign, and executes what they signed”; the hook decides “is this call allowed”; the paymaster decides “who pays gas”, and only on the 4337 path. All three are deployed on Mantle Sepolia and shared by every account; they are not deployed per account.

Trust model#

The four parties are trusted very differently, and every design choice in the SDK follows from this table:

WhoTrusted?Design that follows
root key (person)Fully trustedRoot is the account itself (keyHash = 0), admin, not bound by the hook. Only it can upgrade, grant, revoke and transfer.
session key (agent)Not trustedEvery limit must hold on-chain at execution time. The SDK’s local checks only fail early and save gas; they do not count.
sponsorTrusted for its money and uptimeIt is not a security boundary: the agent can bypass it, pay its own gas and call the account directly, and the on-chain rules still apply.
Launchpad (trusted spender)Checked by a person, then written into the policyThe hook cannot verify the launchpad’s behavior, so the launchpad must meet an interface contract: no owner, pulls money only from the caller, a sell pays in full or reverts.

This gives the SDK’s core promise: a compromised session key can cause a net outflow of quote assets no larger than its allowance, measured at purchase cost; it can sell only the amount it bought itself; it cannot change the policy, and it does not come back after revocation. The market value of its holdings is not guaranteed; see section 5. (AA-DESIGN §4.0)

HOW IT WORKS

In the SDK, an account’s life has only three kinds of operation. The next four subsections follow this order:

  1. Upgrade + first grantroot signs · one type-4 transactionUNDELEGATED → DELEGATED → INITIALIZED, registering the first session key and writing its policy at the same time
  2. Agent executionsession key signs · one per calllocal simulation → sign batch → sponsor pays → Calibur verifies → hook checks each call
  3. Revoke / panicroot signs · one transactionCalibur deletes the key, the hook writes a tombstone, approvals go to zero. The tombstone is permanent: the same key never comes back

EIP-7702: upgrade in place, same address#

EIP-7702 lets an EOA “delegate” its code to a contract implementation. After delegation, contract code runs at this address, but the address, balance and private key are the same as before. The implementation here is Uniswap’s Calibur v1.1.0 (deployed as CaliburEntry).

The upgrade takes one type-4 transaction, with gas paid by the sponsor. The transaction carries two things: the 7702 authorization signed by the root key, and an initialization batch. The batch also registers the first session key and writes its policy on AgentPolicyHook.

After the upgrade, Calibur holds two kinds of key. The root key (keyHash = 0) is admin and not bound by the hook; a session key is not admin, has an expiry, and is bound to AgentPolicyHook. For every call in a session-key batch, Calibur calls the hook once before and once after.

TRAP

The 7702 authorization takes effect before execution. If the initialization batch fails, the delegation is not undone and the account stays in DELEGATED. The SDK’s state machine is UNDELEGATED → DELEGATED → INITIALIZED and rereads the chain state before a retry, so just run account init again.

Read it item by item and you know where the agent’s limits are:

  • The allowlist has only 5 (contract, function) pairs. On MockUSD only approve is allowed, so there is no transfer and money cannot be moved out.
  • Limits count the net decrease of the MockUSD balance: 100 in total, 50 per 86400 seconds. Money that comes in does not give back used allowance. The MNT allowance is 0.
  • approve can only name the launchpad as spender, for no more than the remaining allowance.
  • Buys and sells must pay the account itself, and deadline must fall in [now, now + 600 s].
  • Sells cannot exceed this key’s inventory. Inventory is the hook’s own bookkeeping: the key can sell at most what it bought through LAUNCHPAD_BUY.
  • createToken and claimCreatorFees are NONE: only the allowlist is checked, not the arguments. Launching a token costs nothing and gives the caller no tokens, and claiming fees moves money into the account, so neither can hurt the account.

TRAP

Inventory is tracked per key, not per account. Tokens you transferred into the account yourself, or tokens another session bought, cannot be sold by this key (exit 12). In the portfolio, balance and inventory are two numbers; check the second before you sell.

gasless: the relayer pays#

What the session key signs is not a normal transaction but a Calibur SignedBatchedCall: a list of calls, a 2-minute deadline, and an executor set to the sponsor’s relayer address. The AA SDK sends it, with a request signature, to the sponsor’s sponsor_relay. The sponsor verifies the request, checks the allowlist and budget, simulates again on its own, and then the relayer sends a normal transaction that calls the account’s execute(batch, signature). The relayer pays the gas.

WHY

The sponsor is not a security boundary. It refuses accounts that are not on its allowlist and caps daily gas and per-call fees, but that only protects the sponsor’s own money. The agent can bypass the sponsor, pay its own gas and call the account directly, and the on-chain rules still apply. So when you work out how much money the agent can move, you can assume the sponsor does not exist. (AA-DESIGN §4.0)

The AA SDK has one more path: ERC-4337 EntryPoint v0.8, with a bundler and VerifyingPaymaster paying. The SDK implements it, but this demo does not use it, and acceptance covers only the relayer path.

session export, 24-hour expiry, revocation#

By default, session grant writes the session key into the root home, next to the root key and under the same password. Handing that directory to the agent would hand over the root key. So AA SDK 0.1.5 added a command that runs only off-chain:

Root terminal (root home environment)

MANTLE_AA_EXPORT_PASSWORD=<agent password> \
  mantle-aa session export --agent trader --out ~/.mantle-meme-agent

It decrypts the session key with the root home’s password, encrypts it again with a new password, and writes an agent home with only this one agent profile, without the root key or root profile. In that directory agent simulate|exec works as usual, and every account or session management command fails with a usage error, “missing root profile”.

  • 24-hour expiry. Keys granted by the mantle-aa 0.1.5 CLI always expire after 24 hours, with no option to change it, so policy init --expiry only accepts 24h. The expiry is stored in Calibur’s key settings, and that is its only source.
  • Revocation. A person runs mantle-aa session revoke --agent trader in the root terminal. One management batch does three things: Calibur deletes the key, the hook marks it with a tombstone, and the MockUSD approval to the launchpad goes to zero. The tombstone cannot be cleared; the same key can never be granted again.

Calibur nonce lanes and the hook address

The relayer path uses Calibur’s getSeq(key) as the nonce: a 192-bit key plus a 64-bit sequence. The SDK and the sponsor agree that each session key uses its own lane: lane = uint192(uint256(keyHash) >> 64), root uses lane 0, and the sponsor refuses session requests on the root lane. This is a convention, not on-chain isolation: a malicious session key that bypasses the sponsor can consume sequence numbers on other lanes, and the only effect is denial of service.

Calibur uses the low 5 bits of the hook address to decide which callbacks to call (after signature check, after UserOp validation, after ERC-1271, before execution, after execution). So AgentPolicyHook is deployed with a mined CREATE2 salt so that the low 5 bits are 0x1f, and the SDK checks this before granting a key.

Programs: the TypeScript library#

Programs use the library, not the CLI. Every agent transaction in this project goes through the same code: find the only agent profile in the agent home, decrypt the session key, build an AgentSession, and call session.exec under the send lock. Inside, exec is the first four gates of Figure 5; the fifth is on-chain.

packages/sdk/src/executor.ts and packages/cli/src/cli.ts (excerpt; optional arguments and error diagnostics removed)

import { AgentSession, loadProfileSigner, RelayerExecutor } from "@0xwh1sker/mantle-aa-sdk";

// cli.ts: the sponsor URL comes from MANTLE_AA_SPONSOR_URL, the password from MANTLE_AA_KEYSTORE_PASSWORD
const executor = new RelayerExecutor({ client, url, addresses });

// executor.ts: session key in the agent home → AgentSession
export function openAgentSession(o) {
  const { name, profile } = agentProfile(o.home, o.agent);
  const signer = loadProfileSigner(name, { home: o.home, password: o.password });
  return new AgentSession({ client: o.client, account: profile.account,
                            keyHash: profile.keyHash, signer, executor: o.executor });
}

// executor.ts: send = lock → simulate, sign, hand to sponsor → wait for receipt → write journal
export async function execute(o) {
  return withSendLock(o.home, async () => {
    const { hash } = await retrySponsorBusy(() => o.session.exec(o.calls));
    const receipt = await receiptOf(o.client, hash, 60_000);
    if (receipt.status !== "success") throw new ExecutionRevertedError(…); // trust the receipt, not the sponsor
    appendJournal(o.home, tradesOf(receipt, o.launchpad, o.session.account, o.session.keyHash));
    return { hash, receipt };
  });
}

Every refusal is a typed error: PolicyViolationError, LimitExceededError (with remaining), InventoryExceededError (with held), SponsorRejectedError, SponsorBusyError, ExecutionRevertedError. ON-CHAIN AND LIBRARY

Contracts: bonding curve and truncation#

MemeLaunchpad is both the token factory and the market maker for every token. It has no owner, is not upgradeable, fixes every parameter in its constructor, and calls only MockUSD and the tokens it deployed itself. Prices come from a bonding curve: constant product on virtual reserves, the same idea as pump.fun.

ParameterValueMeaning
TOTAL_SUPPLY1,000,000,000 tokensAll minted to the launchpad at creation
CURVE_SUPPLY800,000,000 tokensThe part the curve can sell; the other 200 million are kept for a future “graduation”, and no code in this version can touch them
VIRTUAL_TOKEN_01,066,666,667 tokensStarting virtual token reserve vT
VIRTUAL_QUOTE_0200 mUSDStarting virtual quote reserve vQ
FEE_BPS100 (1%)Charged on buys and sells, rounded up; the creator gets half (rounded down), the protocol the rest

On a buy, the net amount after fees goes into vQ, and you get vT − ⌈k / (vQ + net)⌉ tokens. Every division rounds up so rounding always favors the curve, so vQ · vT ≥ k in every state. The starting price is about 1.875 × 10⁻⁷ mUSD per token; when all 800 million are sold, the price is 16 times the start and vQ is exactly 800 mUSD. Buying the whole curve costs about 606 mUSD (fees included).

The last buy is truncated. If you pay enough to buy all the tokens left on the curve, the contract takes only the amountInUsed it needs, gives you all the remaining tokens, and the state becomes Completed. Measured on a fork: buying the last 2,015,113.1 tokens took exactly 6.060607 mUSD (0.060607 of it fees).

WHY

The SDK does not rely on on-chain truncation. When the quote returns completes = true, it first clamps both the approve and the buy’s amountIn to amountInUsed. There are two reasons: the hook rejects an approve above the remaining allowance, and the AA SDK’s simulation charges the allowance by the buy’s amountIn. On-chain truncation only covers “someone got in between the quote and the chain”; then the unused approval stays with the launchpad (a trusted spender), the next approve overwrites it, and revocation sets it to zero. (DESIGN D29, §4.3.3)

The lifecycle is only None → Trading → Completed. Graduated holds a place in the enum but can never be reached. After Completed, buys and sells both revert (CurveAlreadyCompleted, CLI exit code 40), and positions cannot be sold. The CLI and the skill say the same thing: “Curve completed; trading is disabled. This v1 launchpad has no migration path, so the position is stranded.” It is “stranded”, not “graduated”.

CREATE2: launch and first buy in one batch#

createToken deploys the token with CREATE2, with salt keccak256(abi.encode(caller, salt)). Because the address can be computed offline, the CLI can put “launch + approve + buy” into one batch before the token exists.

The key point is that Calibur calls the hook separately for each call in the batch. The buy’s beforeExecute reads balanceOf(predicted address), and by then the first call has already deployed the token, so the read works. This was verified in the 0.1.0 fork tests along the full sponsor path, and the two-transaction fallback was not needed.

Fees: 1% of every trade is split inside the contract; creatorFees[token] records the creator’s half. Only the creator can call claimCreatorFees(token), and the money goes to the caller; here the creator is the account, so when the agent claims fees, money flows into the account. Anyone can call claimProtocolFees(), but the money goes only to the treasury fixed at construction.

WHY

Cost can only come from the local journal. On-chain Trade events record only the account and cannot tell two sessions of the same account apart. So “one active session per account at a time” is the supported scope; if the journal is lost, that token’s cost is null (unknown) and the autopilot leaves it alone. (DESIGN D33, R-8)

TRAP

When a session call fails, the deployed Calibur throws only a bare CallFailed(), and the launchpad’s revert reason is lost. diagnoseFailure in executor.ts first looks for explicit revert data; only if there is none does it reread chain state in the contract’s check order to infer the reason (unknown token / curve completed → balance → slippage). This is a heuristic: if it cannot infer a reason, it returns the AA error unchanged (exit 30).

What one journal line looks like, and what happens after a crash halfway through a write

For each confirmed transaction, every Trade log in the receipt that belongs to this launchpad and has this account as trader becomes one line of JSON:

One line of <agentHome>/meme/journal.jsonl (fields from packages/sdk/src/journal.ts, values are placeholders)

{"keyHash":"0x…","txHash":"0x…","token":"0x…","side":"buy",
 "quotePulled":"3000000","tokens":"15608217968123367985416564","fee":"30000",
 "blockNumber":"…","correlationId":"…"}

For a buy, quotePulled includes the fee; for a sell, it is the amount received after the fee. If the process crashes halfway through an append, the last line may have no newline. On read, an incomplete last line is skipped and that token’s cost becomes null; the next append (under the send lock) first cuts it off, or, if it is in fact a complete record missing only the newline, adds the newline and keeps it. A bad line anywhere else is a loud error and is never skipped quietly.

autopilot: a deterministic program for sniping#

“Sniping” means buying a new token with a fixed amount right after it launches and selling once it hits a target. This is the job of a separate daemon, not the LLM: it follows the strategy file mechanically. The LLM only turns your words into a strategy, reads it back to you, starts and stops it, and explains afterwards what it did.

strategy.json (“3U per new token, sell half at +50%, hold at most 30 minutes”)

{
  "entry": { "amountPerToken": "3", "maxAgeSeconds": 60, "keywords": [], "excludeOwn": true,
             "maxOpenPositions": 10, "maxEntryPriceMultiple": 2 },
  "exit":  { "takeProfitPercent": 50, "takeProfitSellPercent": 50,
             "maxHoldMinutes": 30, "stopLossPercent": null },
  "slippagePercent": 3
}

The daemon’s loop is simple. When the watcher sees TokenCreated, it filters on “age when found, keywords, not launched by us, price no more than 2× the launch price, number of positions”; then checks that both remaining allowance and balance are enough; then quotes again and buys. After that, on every Trade of a held token (and on a tick every 10 seconds), it uses the local curve model to compute “how much would selling 50% net” and compares that with the journal cost of that part: at +50% it rechecks with quoteSell and sells, taking profit only once per position; at the maximum holding time it sells all that is left.

  • Chain time. Every time uses the latest block’s timestamp: the age when found, the buy time (that block’s time), the maximum hold. On an anvil fork, evm_increaseTime + evm_mine tests the maximum hold without really waiting 30 minutes.
  • pid lock. autopilot start first refuses if a daemon is already running (exit 44), then starts a detached child process. The daemon creates the pid file exclusively under the send lock, so of two daemons started at the same time only one wins.
  • Recovery. Before each autopilot transaction is sent, {token, reason, unique id} is written to state.json as pending; execute writes that id into the journal as correlationId. If the daemon dies “on-chain but not yet saved”, on restart it accepts only the journal record with the same id. Manual trades carry no id, so they are never mistaken for it.
  • Noticing revocation. An idle daemon sends no transactions, so it never hits exit 13. So every tick reads the chain directly: is the key still registered, has it expired, is it revoked on the hook? If any is wrong, it records session_ended and exits.
  • Telegram notifications. When a bot token and chat id are set, the daemon pushes template messages in order through the Bot API’s sendMessage, without the LLM. Each has a 10-second timeout; a failure records an error event (with the token scrubbed) and never affects trading.

The files it writes are all in <agentHome>/meme/autopilot/: pid, strategy.json, state.json, events.jsonl, daemon.log.

OpenClaw runs in a long-lived container. The image is OpenClaw 2026.10.6 pinned by digest, with this repo’s mantle-meme installed at build time. Why a launcher is needed#

On Linux, OpenClaw 2026.10.6 puts every command started by the exec tool under a child subreaper, with no switch to turn it off: when the command returns, every process it left behind is killed, and when a conversation turn ends, anything still running is stopped too. The daemon started by autopilot start is exactly such a leftover process; started directly from the agent, it is gone within milliseconds.

The fix does not change mantle-meme itself. It adds two small files to the image:

  • launcher.mjs is the container’s main process. It runs under the image’s own tini, outside OpenClaw’s process tree. It listens on /tmp/mantle-meme-launcher.sock inside the container (not on a mounted volume), accepts only autopilot start --strategy <file> [--agent <name>] [--json], runs the real CLI with an argument array (no shell), and passes stdout, stderr and the exit code back unchanged.
  • mantle-meme.mjs is the mantle-meme on the agent’s PATH. Every command except autopilot start runs the real CLI directly in the same process; autopilot start is sent to the launcher together with the current directory.

So the daemon is a descendant of the launcher and outlives the conversation turn; output and exit codes are the same as a direct call (a second start still returns 44).

TRAP

The daemon inherits the container’s environment, not the environment of the docker exec that triggered it. To set variables such as MANTLE_MEME_AUTOPILOT_TICK_MS, set them when the container starts.

Gateway, model, RPC relay, proxy#

  • Gateway. demo-up.sh sets MANTLE_MEME_GATEWAY=1 on the container, so the launcher starts openclaw gateway --bind loopback as a child process, and the container lives as long as the gateway. The Telegram channel is written by config set: dmPolicy: "allowlist", allowFrom with only your chat id, groupPolicy: "disabled"; the bot token is read from the environment variable TELEGRAM_BOT_TOKEN and never written to a file. DMs from any other id are dropped silently.
  • One bot, two uses. The gateway receives messages by long polling, and the autopilot pushes through the same bot’s sendMessage. So only one process at a time may poll this bot; otherwise you see 409 Conflict.
  • Model. OpenClaw manages the model login itself and stores it in the OpenClaw state directory. There are two ways: providers with an OpenClaw plugin use models auth login --provider …; a custom OpenAI Responses-compatible endpoint is first configured with config set models.providers.…, then the key is entered at the prompt with models auth paste-api-key (not on the command line). After start, demo-up.sh runs models status --check and stops if it fails; but this check sends no request, so a wrong key or URL can still pass. Only a real conversation turn proves the provider accepts the key.
  • RPC relay. The public Mantle Sepolia RPC rejects bursts (rate limit), and portfolio sends many reads in parallel. scripts/rpc-relay.mjs forwards on 127.0.0.1:8547, at most 4 at a time, and retries rate-limited requests; it logs neither URLs nor request bodies.
  • Proxy. On networks that reach Telegram only through a proxy, demo-up.sh rewrites the current shell’s https_proxy to host.docker.internal, passes it to the container, and sets NODE_USE_ENV_PROXY=1; both OpenClaw and the autopilot notifications go through it. DEMO_PROXY= turns it off.
TRAP

After the container restarts, OpenClaw resumes the interrupted conversation turn (the bot says “continuing your interrupted request”). So run demo-down.sh only when the bot is idle.

KEY FLOWS

Command buy#

You say “buy 2U of DOGE9”. Following the skill’s rules, the agent runs quote and then buy, without asking you to confirm (requests within the policy run directly). The real work happens in the CLI and the AA SDK:

  1. The CLI resolves the symbol (scanning the latest 1000 tokens, exact, case-insensitive) and confirms the curve is still trading; otherwise it exits 40 / 42 right away.
  2. It calls the on-chain quoteBuy. If the buy would empty the curve, it clamps to amountInUsed. minOut is the quote minus 5%; deadline is the latest block time plus 300 seconds (the hook allows at most 600).
  3. It builds the batch [approve(MockUSD → launchpad, amount), buy(token, amount, minOut, deadline, account)] and takes the send lock.
  4. The AA SDK prechecks each call locally against the hook’s rules and runs an eth_call; if they pass, it signs with the session key and sends the batch to the sponsor.
  5. The sponsor authenticates, simulates again and reserves the fee; the relayer sends the transaction. On-chain, Calibur verifies the signature, the hook checks every call, and the launchpad fills the trade.
  6. The CLI waits for the receipt: status must be success; it does not take the sponsor’s word for it. Then it writes this transaction’s own Trade logs to the journal, releases the lock and returns JSON.
WHY

The sponsor accepts only one in-flight request per account at a time and answers a second one with SPONSOR_BUSY. The autopilot and your manual commands share one account, and the send lock makes them queue instead of colliding at the sponsor. Acceptance tests this case: an autopilot buy and a manual buy started at the same time both succeed, and the user never sees SPONSOR_BUSY. (DESIGN D20, §9.1 item 8)

5Security model and trust boundaries#

If the agent is hit by prompt injection, what is the worst that can happen?

The conclusion first: analyze the agent as already compromised. Every decision of the agent comes from the model, and the model reads token names that anyone can write on-chain, command output, and your messages. Only the on-chain contracts can limit how a compromised agent moves money; the container does something else: it keeps the root key out of the agent’s reach from the start.

Enforced on-chain#

  • Calibur + AgentPolicyHook: allowlist, limits, inventory, recipient, deadline window, expiry, revocation tombstone (each check in Figure 4). A non-admin key cannot call the account itself, and the hook refuses calls that target the hook, so a session key cannot change the policy; the hook refuses every ERC-1271 signature from a session key.
  • The launchpad: no owner, no upgrade, no admin withdrawal path; pulls money only from msg.sender; trades only tokens it registered; a sell pays in full or reverts. These are the AA SDK’s interface requirements for a “trusted launchpad” (AA-DESIGN §4.4). The hook cannot verify them itself; they are a statement of trust the person makes when writing the launchpad into the policy.

The AA SDK’s promise: a compromised session key can cause a net outflow of quote assets no larger than its allowance, measured at purchase cost; it can sell only the amount it bought itself; it cannot change the policy, cannot sign ERC-1271, and does not come back after revocation. It does not guarantee the market value of holdings: a compromised key can sell all its holdings with a tiny minOut, and the loss at market value can far exceed the allowance.

Only skill rules#

“Quote first”, “get your yes before starting the autopilot” and “do not print environment variables” rely only on the model behaving. A model that reads a malicious token name may break any of them. For example, it may start the autopilot without waiting for your confirmation, or buy a token someone else pumped at a high price; the latter is a legal trade within the allowance, and the chain will not stop it.

SECURITY

Anyone can launch a token on a public testnet. A token’s name, symbol and description are untrusted input, and they appear in list, info, autopilot notifications and the agent’s context. The autopilot itself is a deterministic program, and names only affect its keyword filter; but the LLM reads them.

Credentials in the container#

The container is a credential-isolation boundary: the root home is never mounted, so the agent cannot reach the root key. It does not limit what the agent can do with the session key it holds; that is the chain’s job. Also, the agent’s exec tool is not sandboxed inside the container, so it can read anything in there: the agent’s password (which amounts to the session key itself), the bot token, OpenClaw’s model login. The container has internet access, so a compromised agent can send them out. The consequences, in order: the session key is abused within the allowance (revoking stops it), the bot is impersonated (rotate the token), the model quota is stolen.

SECURITY

This is a POC: the contracts are not audited (0.1.0 had a contract review checkpoint with a PASS verdict; the final independent security review is in 0.1.4), and it runs only on Mantle Sepolia with test tokens. The relayer and market-sim wallets hold only testnet amounts. Do not move any configuration here to mainnet.

7Known limits#

What can it not do yet? What will surprise you?

  • No stop-loss. stopLossPercent in the strategy is a reserved field; anything other than null is a usage error. If the price keeps falling, the autopilot sells only when the maximum hold runs out.
  • No sandwich protection. Slippage limits only the output of one trade; maxEntryPriceMultiple only skips new tokens that were clearly pumped already, which is not sandwich protection. The contract does not protect the fill price either.
  • A sold-out curve is stranded. After Completed, buys and sells stop; this version has no path to migrate to an AMM.
  • The maximum hold sells this session’s entire inventory of that token, including the part you bought by hand. The autopilot manages only the positions it opened, but it sells by inventory.
  • Public RPC limits. The public Mantle Sepolia RPC rejects bursts (rate limit exceeded), so in the demo every request goes through the local relay; it is also load-balanced and sometimes one block behind (requested block is above the latest consensus block), and then the autopilot may record a new token as skipped too_old.
  • Only one active session per account is supported (cost, portfolio and autopilot all assume this). On-chain inventory is still tracked per key.
  • After 24 hours you must grant and export again, and export to an empty agent home.
  • CR-02: a huge buy budget (≳1e73 base units) overflows before truncation and reverts safely. The contract is deployed and cannot change; the SDK’s clamp keeps normal amounts away from it; deferred to the next launchpad version.

Glossary#

EOA
Externally owned account: a normal address controlled by one private key, with no code of its own.
EIP-7702
A transaction type (type-4) that lets an EOA delegate its code to a contract implementation. Address and private key stay the same.
Calibur / CaliburEntry
Uniswap’s 7702 account implementation (v1.1.0). Supports several keys, each bound to a hook and an expiry.
root key
The EOA’s own private key: the account’s admin, not bound by the hook. Only in the person’s root terminal.
session key
A non-admin key that root grants to the agent; every call passes AgentPolicyHook; expires after 24 hours.
AgentPolicyHook
The AA SDK’s on-chain policy contract. Singleton, not upgradeable; stores policy, spent allowance, inventory and state per (keyHash, account).
policy / ruleKind
A session key’s rights: allowlist, limits, trusted spenders, deadline window. ruleKind decides what is checked in a call’s arguments: ERC20_APPROVE, LAUNCHPAD_BUY, LAUNCHPAD_SELL, NONE.
quote asset
An ERC20 with an allowance in the policy; here only MockUSD (mUSD, 6 decimals, a test token anyone can mint).
inventory
The hook’s record of “how much of a token this key got by buying”, which is also the most it can sell.
tombstone
The revoked = true mark on the hook; it cannot be cleared, and the same key can never be granted again.
SignedBatchedCall
A list of calls signed by the session key, with a deadline and a named executor (the relayer).
sponsor / relayer
mantle-aa sponsor serve: the sponsoring service that authenticates, simulates and keeps the books; the relayer is the hot wallet it uses to send transactions and pay gas.
bundler / paymaster
The ERC-4337 path: a bundler packs UserOps for EntryPoint v0.8, and VerifyingPaymaster pays. The SDK supports it; this demo does not use it.
root home / agent home
The key directory MANTLE_AA_HOME points to. The root home holds the root key; the agent home is written by session export and holds only one session key.
bonding curve
A market-making method where the price depends on the amount sold. Here: constant product on virtual reserves.
amountInUsed
The quote amount actually taken by a buy. Smaller than the amountIn you gave when the buy is truncated.
Completed / stranded
The state after the curve sells out. Buys and sells stop; positions cannot be sold.
CREATE2 / salt
A contract deployment with a predictable address. The launchpad hashes the caller with the salt, so nobody else can take your address first.
send lock
<agentHome>/meme/send.lock: lets only one process at a time send for this account.
journal
<agentHome>/meme/journal.jsonl: the fill records of every confirmed transaction of this session; the only source of cost.
correlationId
A transaction id the autopilot creates before sending and writes into the journal, used to reconcile after a crash.
autopilot daemon
The background process that snipes and takes profit from a strategy file, with no LLM.
chain time
The latest block’s timestamp. The autopilot uses it for every time decision.
launcher
The container’s main process; it starts the autopilot for the agent so the daemon is not in OpenClaw’s process tree.
child subreaper
A Linux process attribute: orphaned processes are reaped by it. OpenClaw’s exec tool uses it to clean up processes a command leaves behind.
gateway / skill
OpenClaw’s resident service (connects channels such as Telegram); a skill is a SKILL.md directory that teaches the model to use a tool.
market-sim
A market simulator with no LLM: a few EOAs that pay their own gas launch, buy, sell and pump.
