结论先行：Aggregator Hook 没有把 Curve、Fluid、V3 分叉的资产搬进 Uniswap。每类外部来源由一个适配器 hook 包装。hook 在 beforeSwap 里去原协议成交，再返回一个 delta，让 v4 自己的曲线空转（F1、F2）。所以“v4 池”只是一个可报价、可组合、可统一结算的身份。

先看懂“虚拟池”，再谈叙事
  • 机制：hook 在 beforeSwap 里替 v4 成交，specified = −amountSpecified 让核心曲线空转；unlock 的 delta 归零检查兜底。

I

前置知识

B-0

PoolManager 单例与 PoolKey

~4min
是什么

v4 只有一个 PoolManager 合约，所有池子都是它里面的一条状态记录。池子由 PoolKey 确定：两个币、fee、tickSpacing、hook 地址。

为什么这里需要

建一个“池”只是在 PoolManager 里登记一个 PoolKey，不需要部署池合约，也不需要放入储备。Aggregator Hook 正是利用这一点，给外部池登记一个身份。

常见误解

误解：有 PoolId 就有储备。事实：Aggregator Hook 的虚拟池在 PoolManager 里没有储备，也不允许加流动性。

[23] 报告 uniswap-v4-hooks 的“v4 机制”一节

B-1

unlock 与 delta 结清（flash accounting）

~5min
是什么

调用者先 unlock，在回调里做 swap、take（取币）、settle（付币）。每个地址在每个币种上的应收应付叫 delta。回调结束时，只要还有一个 delta 不为 0，整笔交易回滚 [2]。

为什么这里需要

这让 hook 可以在一笔交易里先从 PoolManager 取币、拿去外部协议成交、再把输出记回来。只要最后账平，PoolManager 不关心币是从哪里来的。

最小例子

take(token0, 外部池, X) → 记 −X；settle(Y token1) → 记 +Y

常见误解

误解：take 是借款，要付利息。事实：它只是同一笔交易内的记账，结束前必须结清。

~3min
是什么

hook 地址的低 14 位决定 PoolManager 调用哪些回调。部署时要用 CREATE2 换 salt，挖出低位正好匹配的地址。

为什么这里需要

Aggregator Hook 只开 4 个权限，低位固定是 0x2888。这也是在链上识别它们的一个线索。

B-3

return delta（beforeSwapReturnDelta）

~5min
是什么

有 beforeSwapReturnDelta 权限的 hook，可以在 beforeSwap 返回一个 BeforeSwapDelta。它的 specified 一侧会加到核心的 swap 量上；hook 自己承担这份 delta。

为什么这里需要

返回 specified = −amountSpecified，核心 swap 量变成 0，v4 曲线不成交 [2]。hook 再用 unspecified 一侧告诉 PoolManager 应该给 swapper 多少。

最小例子

卖 X 个 token0：amountSpecified = −X，hook 返回 +X → amountToSwap = 0

常见误解

误解：hook 只能在 swap 前后“看一眼”。事实：有这个权限的 hook 能完全替代核心定价。

[2] v4-core Hooks.sol L248–282、Pool.sol L320

v3 回调付款（swap callback）

~3min
是什么

虚拟池怎么成立

虚拟池的本质，是把四样东西拆开放（Fig 2）：

层 放在哪里
身份（PoolKey / PoolId） PoolManager
结算（delta、take、settle） PoolManager
储备、定价、LP 费 外部协议
两边的翻译 Aggregator Hook

BaseAggregatorHook 只开 4 个权限 [1]：

  • beforeInitialize：建池时把 PoolKey 映射到外部池，并做校验。
  • beforeAddLiquidity：直接 revert LiquidityNotAllowed()，这个池不接受 LP。
  • beforeSwap + beforeSwapReturnDelta：替 v4 成交并改写记账。

核心逻辑在 _innerBeforeSwap。注意第 162 行的注释 // cancel core：

F1

“v4 池”只是路由与结算身份，储备一直在外部协议

置信度: high
论断

Aggregator Hook 的池在 PoolManager 里没有储备，不接受 LP，也不用 v4 曲线定价。它只提供一个 PoolKey，让路由器能报价、组合多跳，并在 PoolManager 里统一结算。

证据

observed 只开 4 个权限，加流动性直接 revert [1]。observed pseudoTotalValueLocked 读的是外部池里的代币数量 [1]。observed 核心 swap 量被抵消为 0 时，Pool.swap 直接返回零 delta [2]。inferred 储备、定价、场所费都留在原协议。

影响

统计 TVL、做价格预言机或索引成交时，要把虚拟池和原生 v4 池分开；它的 PoolId 不代表任何 v4 储备。

F2

能“借用”外部流动性，靠的是 return delta 加上 unlock 的归零检查

置信度: high
论断

hook 在外部成交后，返回 specified = −amountSpecified 抵消核心计算，unspecified 一侧写外部输出。PoolManager 不关心输出来自哪里，只要求 unlock 结束时每个 delta 归零。外部池只成交一部分时，hook 留下未结 delta，整笔交易回滚。

证据

observed amountToSwap += hookDeltaSpecified [2]；hookDelta 记给 hook，swapper 的 delta = 核心 delta − hookDelta [2]。observed unlock 发现非零 delta 计数就回滚 [2]。inferred 按 K 面板的记账表，hook 两种币的 delta 都归零；少成交一部分时 token0 留下正 delta。

影响

写自己的 aggregator hook 时，安全边界在“返回的 delta 是否等于真实收付”。PoolManager 只保证账平，不保证价格对。

记账推演（exact-in，卖出 X 个 token0，V3 适配器，f 为协议费）：

步骤 hook token0 hook token1 swapper
回调 take(token0, V3 池, X) −X
V3 把 Y 打进 PoolManager，settle() +Y
协议费 take(token1, TokenJar, f) −f
返回 delta，核心空转；afterSwap 记账 +X −(Y−f) −X / +(Y−f)
合计 0 0 路由器付 X、取 Y−f

适配器把外部协议的“收款方式”翻译成 take / settle，差异集中在资金路径和支持的 swap 类型

置信度: high
论断

V3、Pancake、Slipstream 共用一份实现：PancakeSwap V3 适配器全文只有 17 行。Curve 每个池一个 hook，同一 hook 地址让路由器识别“碰的是同一个 Curve 池”。Curve 和 Fluid 不设单跳滑点限制，注释说由路由器检查。UniswapX 适配器方向相反：hook 当 filler，v4 swapper 是订单的对手方。

F5

它不是另一个 1inch：寻路仍在链下，变的是外部来源的身份和结算位置

置信度: high
论断

传统聚合器把 DEX 适配器放在自家执行合约和路由栈里，不对外提供统一的 v4 PoolKey 接口。Aggregator Hooks 把适配器做成 v4 池，任何会调 v4 的路由器都能报价和执行；多跳可以把原生 v4 池和外部来源放进同一次 unlock。

证据

observed 官方称 hook 包装外部来源，“so that any router sees it as a Uniswap pool”，整条路径单笔结算，“nothing new to approve” [6]。observed 0x 执行入口是 Settler，授权给 AllowanceHolder 或 Permit2 [18]；1inch Classic 链下寻路、经自家 Router 执行 [19]；CoW 用批量拍卖 [20]。observed Guidestar 走同一套 Universal Router 与 Permit2 [9]。observed 上线前已有 0x AllowanceHolder 发起的交易触及这些 hook（112 笔）[4]。

影响

1inch、0x、Aggregator Hooks、UniswapX 更可能分层共存：前两者管“去哪里找价”，hook 管“怎么在 v4 里结算一跳”，UniswapX 管“谁来承担报价风险”。

F6

协议费是 Uniswap 的价值捕获，也是这条路径相对直连的成本

置信度: high
论断

协议费 = 虚拟池 slot0 的 protocolFee × 25，从 unspecified 一侧送进 TokenJar：exact-in 从输出里扣，exact-out 加在输入上。链上实际设置是：Ethereum 多数虚拟池 10bp，部分稳定币对 3bp；Base 3bp 或 1bp；LitePSM 不收。所以同一个 Curve 池，经 hook 走比 1inch 直连多付这笔费。

证据

observed ProtocolFees(25) 与 _applyWithProtocolFee [1]。observed 提案原文：乘 25 突破 PoolManager 10bp 硬上限，最高 250bp；默认 10bp，稳定币对 3bp，Base 3bp / 1bp [10]。observed 链上最新 protocolFee 多为 40 pips（×25 = 10bp）或 12 pips（3bp），LitePSM 池没有设置记录 [4]。observed aggregator hook 自报 1<<11，LitePSM 自报 1<<12，UniswapX 为 0 [1][3]。inferred 对已有自家适配器、价格敏感的第三方聚合器，直连通常更便宜。

影响

这条路径的主要用户，是本来就走 Uniswap 前端和 API 的订单流。它把这些订单流在外部成交的部分，变成了协议收入。

F7

部署是无许可的，能不能被路由才是真正的闸门

置信度: medium
论断

Curve 适配器工厂的 createPool 没有访问控制，任何人都能部署 hook 并建池。但 Uniswap 路由对一部分 hook 自动收录，另一部分要人工 allowlist；审核只看路由兼容性，不是安全审计。0x 称 6 条链 84,163 个 hook 里 54.2% 恶意，Uniswap 方面否认这影响其路由。

证据

observed createPool 无修饰符 [1]。observed 官方文档：部分 hook 要审核并加入 allowlist [14]；审核表单写明 “not a security audit or an endorsement” [15]。observed 0x 数据截至 2026-09-11，是 0x 自己的分类 [16]。observed 双方争论见二手报道 [17]。

影响

评估一个 hook 生态，看 allowlist 和执行质量数据，而不是看部署了多少个 hook。

F8

这些 hook 早就在跑，量几乎都是稳定币 PSM 兑换，协议费收入还很小

置信度: high
论断

链上最早的 HookSwap 在 2026-04-19，比公告早约半年。最近 16 天 Ethereum 约 2.5 亿美元成交里，99.6% 来自 LitePSM 系列 hook（USDC/USDS、DAI/USDC）。LitePSM 不收协议费，所以全历史实收协议费只有约 2,500 美元。

证据

observed 首笔 HookSwap：Ethereum 2026-04-19、Base 2026-05-01 [4]。observed 按 hook 汇总，LitePSM 系列约 2.484 亿美元 [4]。observed ProtocolFeesCollected 合计约 2,500 美元，上线后 1.5 天约 433 美元 [4]。observed 版本字符串确认这些合约是 LitePSMAggregator 等官方适配器 [5]。inferred 成交额和协议费收入严重不成比例。

影响

现在用成交额衡量这项功能会高估它的商业价值。要看两件事：非 PSM 来源（Curve、Fluid、V3 分叉、Slipstream）的成交量，协议费收入走势。

F9

公告主要是公开和扩面，头 1.5 天的增量在 Base 和 Robinhood

置信度: medium
论断

Ethereum 每日交易数在公告前后都约 320 笔；Base 从约 110 笔升到约 900 笔，Robinhood 从约 7 笔升到约 130 笔。约七成 hook swap 发生在直接调用 Uniswap Universal Router 的交易里。

证据

observed Dune 上线前后对比 [4]；Universal Router 地址来自官方部署页 [8]。inferred Uniswap 路由早已在用这些 hook，公告带来的是新链、新来源与关注度。数据只有 1.5 天，只能算早期读数。

影响

跟踪接受度，至少要看 30 天：非 Uniswap 路由器的占比、非 PSM 来源的量、协议费收入。

外部协议（Curve、Fluid、PancakeSwap、Aerodrome、Sky）都没有公开表态；本文也没有找到“吸血鬼攻击”批评的一手来源 [6]。

走向：对 Uniswap 和 hooks 叙事的判断

本面板全部是推测

每条判断都写明了它成立的前提。前提变化时，结论也会变。

判断（speculative） 成立的前提 反面信号
短期接受度来自 Uniswap 自家前端与 API；第三方聚合器不会大规模改走 hook 路径 协议费保持 1–10bp；第三方已有直连适配器 第三方路由器的占比持续上升
外部协议短期中立：保留场所费，多拿成交 储备与场所费留在原协议（F1） 外部协议限制回调调用者，或在自家前端优先
Uniswap 的竞争点从“池子深”转向“订单流”：协议费是对自有订单流使用外部流动性收的费 流量主要来自 Uniswap 路由器（F9） 协议费收入主要来自第三方路由
hooks 下一阶段的关键是 allowlist / 注册表与风险标注，不是 hook 数量 恶意 hook 争议持续（F7） Uniswap 公布执行质量数据，并默认开启单跳检查
更多“包装型 hook”会出现：PSM、RWA 申赎、wrap / unwrap LitePSM 这类固定费率、无 AMM 价格冲击的兑换已占主导（F8） 非 PSM 来源的量长期很小

围绕 hooks 的叙事里，“Uniswap 变成流动性结算层”这一点有代码支撑：任何来源只要能被翻译成 take / settle，就能成为 v4 池（F2）。但它能不能成为行业标准，取决于路由端的治理，而不是 hook 本身。

虚拟池virtual pool
只有 PoolKey 身份、没有 v4 储备的池；成交由 hook 去外部协议完成。不是原生 v4 池
PoolManagerv4 单例合约
保存所有 v4 池状态的唯一合约，也负责 delta 记账。
PoolKey池子身份
两个币、fee、tickSpacing、hook 地址；哈希后得到 PoolId。PoolId 不代表有储备
unlock解锁会话
调用 PoolManager 的入口；回调结束时所有 delta 必须归零。
delta欠账
某个地址在某个币种上对 PoolManager 的应收应付。不是余额
take取币
让 PoolManager 把币转给指定地址，并给调用者记负 delta。
settle付币确认
sync 之后把币转进 PoolManager，再按到账量记正 delta。
return delta返回欠账
hook 在回调里返回的 delta，用来改写记账。

allowlist路由白名单
