Uniswap Aggregator Hooks: Wrapping External Liquidity as v4 Pools

The hook trades on the external venue inside beforeSwap, then returns a delta that cancels v4's own curve. v4 supplies only the pool identity and unified settlement; reserves and pricing stay in the source protocol.

Bottom line: Aggregator Hooks do not move Curve, Fluid or V3-fork assets into Uniswap. An adapter hook wraps each kind of external source. In beforeSwap, the hook trades on the external venue, then returns a delta that makes v4's own curve do nothing (F1, F2). The "v4 pool" is therefore only an identity that routers can quote, compose and settle in one place.

Compared with 1inch-style aggregators, the venue adapter moves from a private contract into a public v4 pool interface (F5). The cost is a 1–10 bp protocol fee on top of the venue fee (F6). Onchain, these hooks have run since 2026-04. In the last 16 days, 99.6% of Ethereum volume was LitePSM stablecoin conversion, and lifetime protocol fees total about $2,500 (F8).

Context

Problem: On 2026-10-22 Uniswap announced "Uniswap v4 is now an aggregator". It said 7 external sources cover more than 90% of DEX activity on the three chains [6]. Readers want to know three things. How can v4 "borrow" another protocol's liquidity as a v4 pool? How does this differ from 1inch or 0x? Does it matter?

Why now:

  • The UNIfication proposal of 2025-11 lists this feature: "turning Uniswap v4 into an onchain aggregator that collects fees on external liquidity" [3][12].
  • The v4 protocol fee proposal of 2026-07 gives aggregator hooks their own fee, with a cap of 250 bp [10].
  • Debate about hooks is growing; in 2026-09, 0x publicly questioned hook safety [16].

Scope:

  • How Aggregator Hooks work in code, plus the v4 background they need
  • Comparison with aggregators and intent systems
  • Trade-offs, adoption, and where hooks are heading

Non-goals: investment advice and token price views; a full security audit of the adapters; Uniswap governance details (only where the protocol fee matters).

I

Background

B-0

PoolManager singleton and PoolKey

~4min
What it is

v4 has one PoolManager contract, and every pool is one state record inside it. A PoolKey identifies a pool: two currencies, fee, tickSpacing and the hook address.

Why it matters here

Creating a "pool" only registers a PoolKey in PoolManager. It deploys no pool contract and needs no reserves. Aggregator Hooks use this to register an identity for an external pool.

Common misconception

Myth: a PoolId means reserves exist. Fact: an Aggregator Hook's virtual pool has no reserves in PoolManager and refuses liquidity.

Go deeper

[23] the "v4 mechanics" panel of the uniswap-v4-hooks report

B-1

unlock and delta settlement (flash accounting)

~5min
What it is

The caller calls unlock and, inside the callback, swaps, calls take (pull tokens) and settle (pay tokens). Each address's balance owed or due per currency is a delta. If any delta is non-zero when the callback ends, the whole transaction reverts [2].

Why it matters here

This lets a hook pull tokens from PoolManager, trade them on an external venue, and book the output back, all in one transaction. If the books balance, PoolManager does not care where the tokens came from.

Minimal example

take(token0, external pool, X) → books −X; settle(Y token1) → books +Y

Common misconception

Myth: take is a loan with interest. Fact: it is bookkeeping inside one transaction and must clear before the transaction ends.

Go deeper

[2] v4-core PoolManager.sol L104–114, L279–302

B-2

Hook permission bits

~3min
What it is

The lowest 14 bits of a hook address decide which callbacks PoolManager calls. Deployers mine a CREATE2 salt until the low bits match.

Why it matters here

Aggregator Hooks enable only 4 permissions, so their low bits are always 0x2888. This is one way to spot them onchain.

Go deeper

[2] v4-core Hooks.sol L29–47

B-3

Return delta (beforeSwapReturnDelta)

~5min
What it is

A hook with the beforeSwapReturnDelta permission can return a BeforeSwapDelta from beforeSwap. PoolManager adds its specified side to the core swap amount, and the hook owns that delta.

Why it matters here

Returning specified = −amountSpecified brings the core swap amount to 0, so the v4 curve does not trade [2]. The unspecified side then tells PoolManager what the swapper gets.

Minimal example

sell X token0: amountSpecified = −X, hook returns +X → amountToSwap = 0

Common misconception

Myth: a hook can only "look" before and after a swap. Fact: with this permission, a hook can fully replace core pricing.

Go deeper

[2] v4-core Hooks.sol L248–282, Pool.sol L320

B-4

v3 swap callback

~3min
What it is

A v3 pool first sends the output token to the recipient. Then it calls the caller's uniswapV3SwapCallback, which must pay the input token. Finally the pool checks its balance.

Why it matters here

The V3, PancakeSwap V3 and Slipstream adapters use this callback to take the input from PoolManager straight to the external pool.

Go deeper

How the virtual pool works

A virtual pool splits four things across places (Fig 2):

Layer Where it lives
Identity (PoolKey / PoolId) PoolManager
Settlement (deltas, take, settle) PoolManager
Reserves, pricing, LP fees External venue
Translation between the two Aggregator Hook

BaseAggregatorHook enables only 4 permissions [1]:

  • beforeInitialize: maps the PoolKey to an external pool at creation and validates it.
  • beforeAddLiquidity: reverts with LiquidityNotAllowed(); the pool takes no LPs.
  • beforeSwap + beforeSwapReturnDelta: trade for v4 and rewrite the books.

F1

The "v4 pool" is only a routing and settlement identity; reserves stay in the external venue

confidence: high
Claim

An Aggregator Hook pool has no reserves in PoolManager, takes no LPs and does not price with the v4 curve. It only provides a PoolKey, so routers can quote it, compose multi-hop routes and settle in PoolManager.

Evidence

observed Only 4 permissions; adding liquidity reverts [1]. observed pseudoTotalValueLocked reads token amounts held by the external pool [1]. observed When the hook cancels the core swap amount to 0, Pool.swap returns a zero delta [2]. inferred Reserves, pricing and venue fees stay in the source protocol.

Implication

For TVL, price oracles or trade indexing, separate virtual pools from native v4 pools; their PoolId stands for no v4 reserves.

F2

v4 "borrows" external liquidity through a return delta plus the zero-delta check at unlock

confidence: high
Claim

After the external trade, the hook returns specified = −amountSpecified to cancel the core computation, and puts the external output on the unspecified side. PoolManager does not care where the output came from; it only requires every delta to be zero when unlock ends. If the external pool fills only part of the order, the hook keeps an open delta and the whole transaction reverts.

Evidence

observed amountToSwap += hookDeltaSpecified [2]; PoolManager books the hook delta to the hook, and the swapper's delta = core delta − hook delta [2]. observed unlock reverts on a non-zero delta count [2]. inferred Per the ledger table below, both of the hook's deltas net to zero; a partial fill leaves a positive token0 delta.

Implication

When you write your own aggregator hook, the safety boundary is whether the returned delta equals what the hook paid and received. PoolManager guarantees balanced books, not a correct price.

F4

Adapters translate each venue's payment model into take / settle; they differ in token paths and swap types

confidence: high
Claim

V3, PancakeSwap V3 and Slipstream share one implementation: the PancakeSwap V3 adapter is only 17 lines long. Curve uses one hook per pool, so a shared hook address tells routers they touch the same Curve pool. Curve and Fluid set no per-hop slippage limit; comments say the router checks it. The UniswapX adapter runs the other way: the hook is the filler, and the v4 swapper is the order's counterparty.

Evidence

observed PancakeSwap / Slipstream inherit V3 and change only the callback name or the pool lookup [1]. observed Curve calls exchange(..., 0); Fluid sets amountLimit to 0 or the maximum [1]. observed README: the v4 swapper provides the counter-side of the UniswapX order [1]. observed Deployed hook version strings include SushiswapV3Aggregator and SushiswapV2Aggregator [5]. inferred Adding a V3 fork mostly means a new factory and callback name.

Implication

To review a new adapter, ask three questions. Where is the input paid from? Where does the output land? Is there a per-hop minimum output? User protection sits in the router's final minOut.

F5

Not another 1inch: route search stays offchain; what changes is the venue's identity and where it settles

confidence: high
Claim

Classic aggregators keep DEX adapters inside their own executor and routing stack; they expose no shared v4 PoolKey interface. Aggregator Hooks make the adapter a v4 pool that any v4-aware router can quote and execute. A multi-hop route can put native v4 pools and external venues in one unlock.

Evidence

observed Each hook wraps a source "so that any router sees it as a Uniswap pool", with "nothing new to approve" [6]. observed 0x executes through Settler [18], 1inch Classic through its Router [19], and CoW through batch auctions [20]. observed Guidestar uses the same Universal Router and Permit2 [9]. observed Before launch, 112 transactions from 0x's AllowanceHolder already touched these hooks [4].

Implication

1inch, 0x, Aggregator Hooks and UniswapX will more likely coexist in layers. The first two decide where to find price; the hook settles one hop inside v4; UniswapX decides who carries the quote risk.

F6

The protocol fee is Uniswap's value capture and the cost of this path versus a direct call

confidence: high
Claim

Protocol fee = the virtual pool's slot0 protocolFee × 25, sent from the unspecified side to TokenJar. Exact-in takes it from the output; exact-out adds it to the input. Onchain, most Ethereum virtual pools pay 10 bp (some stable pairs 3 bp), Base pays 3 bp or 1 bp, and LitePSM pays nothing; so a Curve pool costs this fee more through the hook than through 1inch.

Evidence

observed ProtocolFees(25) and _applyWithProtocolFee [1]. observed The proposal's 25× multiplier lifts the 10 bp cap to 250 bp, with rates of 10 bp, 3 bp for stable pairs, and 3 / 1 bp on Base [10]. observed The latest onchain protocolFee is mostly 40 pips (×25 = 10 bp) or 12 pips (3 bp); LitePSM pools have no fee record [4]. observed Flags: aggregator hooks 1<<11, LitePSM 1<<12, UniswapX 0 [1][3]. inferred For price-sensitive third-party aggregators with their own adapters, a direct call is usually cheaper.

Implication

The main users of this path are orders that already come through Uniswap's frontend and API. It turns the part of that flow filled on external venues into protocol income.

F7

Deployment is permissionless; the real gate is whether a hook gets routed

confidence: medium
Claim

The Curve adapter factory's createPool has no access control, so anyone can deploy a hook and create pools. But Uniswap's router picks up some hooks automatically and allowlists others by hand; the review covers routing compatibility only, not security. 0x says 54.2% of 84,163 hooks on 6 chains are malicious; Uniswap disputes that this affects its routing.

Evidence

observed createPool has no modifier [1]. observed Official docs: some hooks need review and an allowlist entry [14]; the review form says "not a security audit or an endorsement" [15]. observed 0x's data is as of 2026-09-11 and uses 0x's own classification [16]. observed Second-hand reports cover the dispute [17].

Implication

To judge a hook ecosystem, look at the allowlist and execution-quality data, not the number of deployed hooks.

F8

These hooks have run for months, almost all volume is stablecoin PSM conversion, and protocol fees are still small

confidence: high
Claim

The first onchain HookSwap was on 2026-04-19, about six months before the announcement. Of about $250M Ethereum volume in the last 16 days, 99.6% came from LitePSM hooks (USDC/USDS, DAI/USDC). LitePSM pays no protocol fee, so lifetime protocol fees are only about $2,500.

Evidence

Implication

Volume overstates the commercial value of this feature today. Watch two things: volume from non-PSM sources (Curve, Fluid, V3 forks, Slipstream) and the protocol fee trend.

The announcement mainly made the feature public and wider; the first 1.5 days added flow on Base and Robinhood

confidence: medium
Claim

Ethereum stayed at about 320 transactions a day before and after the announcement. Base rose from about 110 to about 900 a day, and Robinhood from about 7 to about 130. About 70% of hook swaps sit in transactions sent straight to Uniswap's Universal Router.

No external protocol (Curve, Fluid, PancakeSwap, Aerodrome, Sky) has made a public statement. We also found no primary source for a "vampire attack" critique [6].

Outlook: Uniswap and the hooks narrative

Everything in this panel is speculative

Each judgment states the condition it depends on. If the condition changes, so does the conclusion.

Judgment (speculative) Holds if Counter-signal
Near-term adoption comes from Uniswap's own frontend and API; third-party aggregators will not move to the hook path at scale The protocol fee stays at 1–10 bp; third parties already have direct adapters The third-party router share keeps rising

The code supports one part of the narrative: "Uniswap becomes a liquidity settlement layer". Any source that a hook can translate into take / settle can become a v4 pool (F2). Whether it becomes an industry standard depends on routing governance, not on the hooks themselves.

  • External reactions: we found no formal statement from external protocols or third-party aggregators.
  • The 0x dispute: the malicious-hook share is 0x's own classification, and 0x is a competitor [16].
