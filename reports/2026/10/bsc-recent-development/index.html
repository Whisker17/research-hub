结论

执行回归上游，差异化放在协议层的金融基础设施
  • CAS20 是协议原生代币：状态仍在链上，计费不打折，省的是字节码解释。它直接沿用 Base B20 的设计，代码独立用 Go 实现（F1、F2）。
  • Payment Lane 是一道配额，不是独立通道：普通交易用不到保底的 5%，支付按目标地址认定，名单初始为空（F5、F6）。它和 Tempo 形状相同，倾向相反，没有移植证据（F9）。
  • 已经影响主网的只有 BEP-675 BidBlock 和 70M gas limit；Jenner 的功能还要等 release、硬分叉和治理开关（F8、F11、F4）。
  • 这些部件之间没有自动连接：CAS20 代币不会自动进入支付名单，经 Router 发起的支付不进 lane（F6）。

B-0

BSC 出块：Parlia 验证者与 builder

~5min
是什么

BSC 用 Parlia 共识：一组验证者轮流出块，每人连续出若干块，出块间隔 0.45 秒。验证者可以接收 builder 的报价，从中选出收益最高的一份出块 [3][6]。

为什么这里需要

Payment Lane 的检查点和 BEP-675 的风险，都取决于“验证者封块前有没有执行交易”。

最小例子

旧路径 SendBid：builder 发交易列表，验证者重新执行一遍再封块。新路径 SendBidBlock：builder 发已执行好的整块，验证者不执行就签名。

常见误解

误解：BidBlock 让验证者“不验证”。事实：验证者广播之后，仍会在本地完整导入这个块，失败就撤销 builder [3]。

深入

[3] BEP-675 §4

硬分叉与治理开关

~3min
是什么

硬分叉让所有节点在约定时间启用新规则，例如 Jenner。治理开关是链上合约里的参数，由 BSC 治理通过 GovHub（0x…1007）修改，不需要升级节点 [1][2]。

为什么这里需要

CAS20 和 Payment Lane 都要过两层：Jenner 激活后代码才生效；治理改参数后，功能才真正可用。

最小例子

Jenner 之后，CAS20 的创建开关仍然全部关闭。Payment Lane 的支付名单仍然为空。

常见误解

误解：代码合并就等于上线。事实：截至 2026-10-09，这些代码还不在任何 release 里，主网也没有排 Jenner 时间 [20]。

深入

[16] Jenner 公告

B-2

预编译与 stateful precompile

~4min
是什么

预编译（precompile）是固定地址上的原生代码，例如 ecrecover，输入进、输出出，不碰状态。stateful precompile 能读写 StateDB、知道调用者、能发事件，失败时随调用帧一起回滚 [5]。

为什么这里需要

CAS20 代币就是 stateful precompile。它用 Go 代码完成 ERC-20 合约的全部工作，所以必须自己补上 EVM 原本自动提供的约束。

最小例子

STATICCALL 里不能写状态；DELEGATECALL 进来时 storage 归谁？原生代码必须逐项处理这些情况。

常见误解

误解：原生代码的状态存在节点私有数据库里。事实：CAS20 的状态写在代币账户自己的 storage 里，进入 state root [1]。

深入

[5] bsc core/vm/contracts_stateful.go

B-3

原生代码怎么计费

~3min
是什么

EVM 按 opcode 收费，状态访问分冷 / 热（EIP-2929），写 storage 有 net metering 和退款（EIP-2200 / 3529）。原生代码不执行 opcode，所以要手动在每次读写时扣同样的费用 [5]。

为什么这里需要

这决定 CAS20 比字节码代币便宜在哪里：省掉解释开销，状态访问照常收费。

深入

[1] BEP-702 §3.14

B-4

父状态与实时状态

~3min
是什么

父状态是上一个区块执行完后的状态，本块所有交易看到的都一样。实时状态是本块里“这笔交易执行之前”的状态，会随前面的交易变化 [2]。

为什么这里需要

Payment Lane 两种都用：名单和比例读父状态，“收款方有没有代码”读实时状态。

最小例子

同一块里，交易 1 给地址 X 部署代码，交易 2 给 X 转 BNB。按父状态 X 没有代码；按实时状态 X 已经有代码。

常见误解

误解：EIP-7702 账户还是 EOA，所以没有代码。事实：委托标记 0xef0100‖addr 也算代码 [2]。

深入

[2] BEP-703 §3.2

CAS20：协议原生的合规代币

CAS20（Compliant Asset Standard）是 BEP-702 定义的代币标准。目标是稳定币和代币化 RWA。BEP 给出的动机是：BEP-20 只是 ABI 约定，不保证行为；隐藏的 mint 路径、审计后的 proxy 升级都可以藏在正常接口后面 [1]。CAS20 让链来保证代币行为。

代币分两个变体 [1][5]：

  • Asset：decimals 在 6–18 之间，创建后不变；带 multiplier、公告、批量 mint、扩展元数据。
  • Stablecoin：decimals 固定为 6；多一个不可变的 currency()，只能是 A–Z。它只是发行方的自我声明，不证明储备。

每个入口先检查调用形式：DELEGATECALL / CALLCODE 报 DelegateCallNotAllowed；带 value 报 NonPayable；STATICCALL 里写状态报 StaticCallNotAllowed。三者都是带具名错误的 revert，不会耗尽 gas [1][5]。

置信度: high
论断

代币状态写在代币账户自己的 storage 里（ERC-7201 命名空间），进入 state root。RequiredGas 恒为 0，全部费用在执行中按实际读写扣除，逐条复刻 EIP-2929 / 2200 / 3529。唯一的性能数据是 reth-bsc 的本地微基准：单线程 transfer 约 1.3 µs。

影响

0xEF 哨兵有三个作用 [1]：

  • 防止 EIP-161 把“没有 nonce、没有余额、没有代码”的代币账户连同 storage 一起删掉。
  • 它是 EIP-3541 保留的前缀，CREATE / CREATE2 部署不出来，所以无法伪造。
  • EXTCODESIZE 返回 1，“有代码就是合约”的判断仍然成立。

initCalls 让 Acme 在同一笔交易里配置角色和策略。它们运行在特权窗口里：跳过角色检查和转账侧策略，但不跳过 MINT_RECEIVER 策略、暂停、供应上限 [1][5]。

L

Payment Lane：给支付保底的配额

BEP-703 的动机：BSC 的 base fee 固定为 0，打包顺序完全靠小费竞价。某类流量暴涨时（例如发币），支付交易最先被挤出去 [2]。Payment Lane 的做法是：每个区块给“支付类交易”保底一部分 gas。BEP 原文是 “A quota, not a region”：它是配额，不是区块里的一段位置 [2]。

什么交易算 payment

Fig 5 是分类规则。每笔交易在执行前分类一次 [2][6]。

规则里有几处容易误解的地方 [2]：

  • 按地址，不按函数：调用名单上代币的任何函数（包括 approve）都算 payment。
  • 只看顶层 to：经 Router、多签、AA 钱包发起的支付不算 payment，即使内部转了 USDT。
  • 名单初始为空：Jenner 不预装任何地址。USDT、USDC 只是预期的首批条目，要等治理提案。
  • code 读实时状态：防止“同块先部署代码或 7702 授权，再转 BNB”把任意执行塞进 lane。

回到例子：Alice 直接调用 xUSD 的 transfer，只有 xUSD 地址被治理加进名单，它才是 payment。Alice 用智能钱包付款时，顶层 to 是钱包合约，这笔交易是 general。

F6

支付按顶层 to 地址认定，名单初始为空；CAS20 代币不会自动进入 lane

置信度: high
论断

分类只读交易的顶层 to，不解析 selector，不跟踪内部调用。名单只能由治理经 GovHub 调用 0x…2007 的 updateParam 增删，从下一个区块起生效。CAS20 的激活开关与 Payment Lane 名单是两套独立的参数。

证据

observed classify.go:34-58 [6]；BEP-703 §3.2、§3.6 [2]；PaymentLane.sol:91-116 [15]（P5、P6、P10、P12）。inferred 与 CAS20 没有自动连接（S3）。

影响

钱包和支付网关想让交易进入 lane，必须让用户直接调用名单上的合约。可升级合约被列入名单后，要持续监控它的实现。

配额怎么算

下表是一个假设的 100M gas limit 区块（不是主网参数），ratio 取默认 500，所以 Q = 5M [2]：

情形 P 支付 N 普通 + 系统 结果
支付不足 2M 92.5M ✓有效：3M 保底空着
没有支付，普通塞满 0 95.5M ✗无效：普通用了保底
支付超额 8M 92M ✓有效：多出的 3M 与普通共享
总量超限 8M 93M ✗无效

BEP 自带的例子用 55M gas limit：Q = 2.75M，约容纳 130 笔 BNB 转账，或 45–78 笔稳定币转账 [2]。

F5

Payment Lane 是给支付的保底配额，不是独立通道

置信度: high
论断

默认 5%、上限 10% 的 gas 只能给支付用，即使空着也不还给普通交易；支付可以超出这个额度。BEP 不改交易格式、区块头、费用规则和排序，也不承诺任何单笔支付被打包。

证据

observed BEP-703 §1、§3.3、§4、§5 [2]；paymentlane.go:60-81 [6]（P1、P2、P3、P13、P14、P16、P19）。inferred 不提供 FIFO、抗审查、抗 MEV 保证（P4）。

影响

它保证的是“拥堵时支付这一类交易总有空间可抢”。单笔支付仍要付有竞争力的小费。

置信度: high
论断

两者都在共识层给一类交易加 gas 上限。区别有三点：Tempo 不读状态，参数是区块头字段，并且给非支付封顶约 6%；BSC 读两种状态，不改区块头，并且给支付保底 5%。BEP-703 全部 41 个修订和三个实现 PR 的评论里，“Tempo”都是 0 次出现。

其他开发方向

BEP-706：毫秒时间戳预编译

BSC 区块头里本来就有毫秒信息，但 block.timestamp 返回秒。0.45 秒出块时，相邻两三个块的秒数可能相同。BEP-706 在 0x70 加了一个预编译：固定 20 gas，返回 Time × 1000 + 毫秒余数 [3]。block.timestamp 的语义不变。用途是 RFQ 报价截止、拍卖截止这类需要亚秒精度的合约逻辑。

BEP-714：备用验证者等 1 秒

轮到的验证者掉线时，备用验证者要等一段时间才能出块。Lorentz 把这个初始等待从 1 秒提到 2 秒，BEP-714 把它改回 1 秒 [3]：

一个验证者掉线，影响 8 个块BEP-714 §4.1
旧：(0.45正常出块间隔 + 2备用初始等待) × 8 = 19.6 秒
新：(0.45 + 1改回 Lorentz 之前的默认值) × 8 = 11.6 秒
正常出块间隔不变。9-11 的首版还改 turnLength 和惩罚阈值，9-15 缩减为只改等待时间。

0x68 双签证据按字节计价

Jenner 还把 0x68 双签证据预编译的价格改成 10000 + 16 × 输入字节数，防止超大 header 用固定价格换取无上限的哈希计算 [5]。这项改动绑定 Jenner，但 BEP-718 和官方公告都没有列出。

v1.8.0-alpha（2026-08-13，预览版，不用于生产）合并了 geth v1.17.3，同时删掉了三项 BSC 自研功能 [20]：

  • opcode 级优化（superinstruction）

reth-bsc：双客户端

reth-bsc 的流程是 Go 先实现，Rust 移植 [8]。CAS20 的 Rust 版回放 Go 录下的 145 次调用，逐步比对返回值、gas、退款、事件和最终 state root。最新 release 是 v0.1.2（2026-08-20），Jenner 相关代码都还没有发布。v0.1.2 修了一个状态根错误：它曾在内部测试网 QANet 的 Pasteur 切换点导致集群分裂。仓库 README 仍写“作为验证者运行：尚未支持”，没有证据表明主网验证者在运行 reth-bsc。

BAP-710：PropAMM Relayer（应用层提案）

BAP-710 于 2026-10-08 合并进 BEPs 仓库，类型是 Application，不改共识 [4]。PropAMM 是做市商自己定价的池子：价格来自链下高频报价，不来自链上曲线。

它要解决的问题。BAP §3.1 的说法是：做市商要把报价带上链，需要解决三件事 [4]：

  1. 低成本地发布报价；
  2. 保证 taker 按模拟时看到的报价成交；
  3. 有可靠的上链路径。

今天在 BSC 上，每个做市商要为每个 builder 各做一遍。每个 taker 还要逐个对接每个做市商的合约和报价格式。BAP 把现有做法按“复杂度压在谁身上”做了对比 [4]：

现有做法 复杂度在谁身上
Solana PropAMM 做市商：自建上链管道，每家重复
Base PropAMM 做市商付 gas：每次更新都上链；模拟与成交之间状态会变
Titan taker：订阅单一 builder 的 state override 流，自己组 bundle
BAP-710 共享的 relayer 承担组包、分发、builder 适配

两组多对多，由两个部件分别消除 [4]：

多对多 谁来消除
做市商 × builder relayer：做市商只推一条 pamm_sendQuoteUpdateV1 流
taker × 做市商的格式 链上标准：统一的 registry + IPropAMM 池子接口

各角色要做什么 [4]：

角色 集成工作
做市商 推一条报价流；池子实现 IPropAMM，从 registry 读报价
钱包 只换 RPC 地址，交易模型不变
聚合器 / solver 现有适配器加 IPropAMM，eth_call 发给 relayer
builder 不改代码，只执行原子 bundle

聚合器有一条硬约束：只能把 PropAMM 路由返回给“交易会发到 relayer”的钱包。交易只发到公开 RPC，会因缺少报价更新而 revert；后果是失败，不丢资金 [4]。

Fig 8 是一笔成交的流程。

链上的报价 registry 不检查过期：relayer 和 builder 按截止时间丢弃过期报价。需要链上保护的池子，要在 quote / swap 里自己检查新鲜度 [4]。registry 里的 “lane” 指一份报价状态，与 Payment Lane 无关。

relayer 是许可制的运营方：做市商和 taker 在它的控制台申请角色，管理员批准后发 API key；做市商可以只让指定 taker 看到报价 [4]。BAP 自己把“多 relayer 互通”列为应对单一运营方的长期办法。截至 2026-10-09，本文没有查到正在运营的 relayer。

F13

relayer 的核心是即时上链，不只是把集成工作集中起来

置信度: high
论断

报价平时不上链。某笔 taker 交易读到某个报价时，relayer 才把两者打成原子 bundle 发给所有 builder。这样，无人使用的报价不花 gas，模拟与成交之间也没有状态差。做市商 × builder 的重复由 relayer 消除；聚合器 × 做市商的格式差异由 IPropAMM 接口消除。

证据

observed BAP-710 §3.1、§3.2、§4.5.4、§5.2 [4]（J43–J48）。inferred “核心是即时上链”由以上推出（J50）。

影响

聚合器接 PropAMM 的成本接近接一个 PancakeSwap 池子，但必须判断用户钱包是否走 relayer。

与 Flashbots PUR（ERC-8324）的关系

PUR（Priority Update Registry）是 Flashbots 在以太坊上做的共享合约，参考实现在 flashbots/priority-update-registry [24]。它已提交为 ERC-8324 草案（ethereum/ERCs PR #1852，2026-07-03 创建，未合并），并部署在以太坊主网 [25]。

PUR 的思路有三点 [24]：

  • 做市商的“优先更新”交易只能写 PUR 自身的 storage。因此 builder 不用模拟，也能知道它改了什么。
  • builder 把更新插在读取它的用户交易之前。
  • 没被读到的更新不上链。

BAP-710 的链上 registry 和 PUR 同名同构，见下表 [4][24]：

  • 接口都叫 IPrioUpdateRegistry，方法名相同：updateState / getState / addUpdater / isUpdater。
  • 存储布局相同：每个 lane 最多 255 个 word，基址公式也相同。
  • BAP 的命名空间串是 PrioUpdateRegistryV2.lane.v1。
  • BAP §5.2 写道：“早期 registry 草案自己验证签名（batchUpdateStateWithSignature）”。这个函数名正是 PUR 的接口。

BAP-710 正文没有提到 Flashbots 或 ERC-8324。

维度 Flashbots PUR BAP-710
存储 lane ≤ 255 word，base = keccak(ns, target, lane) + i 相同（命名空间 V2）
新鲜度 uint32 时间戳；registry 检查读写时间窗 48 位递增 seq；registry 不查过期
签名 内置；时间窗内可重放 移到 decoder lane；seq 防重放
谁插入更新 每个 builder 维护更新池，插在读取交易前 relayer 匹配读写集、组 bundle；builder 不改
标准化 ERC-8324 草案，主网已部署 BAP Draft，未见部署
F14

和 PUR 作用相同的是 BAP-710 的链上 registry，不是 relayer

置信度: high
论断

BAP-710 的 registry 是 PUR 的改版：接口和存储布局同名同构，新鲜度从时间戳改成递增 seq，签名移到 decoder。relayer 是 BSC 在 PUR 之外加的一层：PUR 要求每个 builder 自己插入更新，BAP-710 把这件事集中到一个对所有 builder 中立的 relayer。

证据

observed PUR README 与合约 [24]；ERC-8324 PR [25]；BAP-710 §4.2、§5.2 [4]（J51–J56）。inferred “registry 是 PUR 改版，relayer 是新加的一层”（J57）。

影响

熟悉 PUR 的做市商，迁移到 BSC 时池子读报价的方式基本不变。要改的是新鲜度检查（时间戳改 seq）和提交路径（发给 relayer，不发给 builder）。

T

术语表

ParliaBSC 共识
BSC 的 PoSA 共识：一组验证者轮流出块，连续出若干块后换人。不是以太坊的 Gasper
builder组块者
把交易组成块或 bid 交给验证者的一方，赚取 MEV 收益。不是验证者
JennerJenner 硬分叉
BSC 下一次硬分叉，包含 BEP-702、703、706、714，由 BEP-718 汇总。不是 Pasteur（已上线）
GovHub治理中枢
BSC 系统合约 0x…1007。治理提案只能以它为目标，由它转发参数修改。
stateful precompile有状态预编译
能读写状态、知道调用者、能发事件的原生代码合约。普通预编译不碰状态
RWA现实世界资产
代币化的证券、基金份额等链下资产。
B20Base 原生代币
Base 在 Beryl 升级上线的原生代币标准，Rust precompile 实现。不是 BEP-20
CAS20合规资产标准
BEP-702 定义的 BSC 原生代币标准，地址前缀 0xCA52。不是新的 ERC 编号
ActivationRegistry激活注册表
0x7020…01，保存 CAS20 的 admin 和三个 feature 开关。
PolicyRegistry策略注册表
0x7020…02，保存共享的黑白名单和组合策略。
Payment Lane支付保底
BEP-703：每块给支付交易保底一定比例的 gas。不是独立的执行通道
quota保底配额
Payment Lane 的 Q = ratio × G / 10000，ratio 读父区块状态。
BidBlock整块 bid
BEP-675：builder 提交已执行的整块，验证者封块前不重放。SendBid 只提交交易列表
QANet内部测试网
BNB Chain 的内部 QA 网络，不是公开测试网 Chapel。
PropAMM专有 AMM
做市商自己定价的池子，价格来自链下高频报价，不来自链上曲线。不是普通 AMM
PUR优先更新注册表
Flashbots 的 Priority Update Registry（ERC-8324 草案）：只能写自身 storage 的共享合约，用来承载 builder 优先插入的报价更新。不是 Payment Lane
