The conclusion first, in five points:

  1. BNB is not abandoning BSC. The official wording is that New L1 "complements BSC rather than replacing it". It uses BNB for gas and issues no new token. Today it runs only as an internal devnet. The roadmap plans testnet for late 2026 and mainnet for early 2027 (F1).
  2. The main change is the timing structure, not multithreading. Validators vote only on the transaction order. Execution runs in the background, and its result lands D blocks later (F2). The docs give the "parallel EVM" one sentence and mark it "Detailed design is in progress" (F3). The cost: users pay for the declared gas_limit, with no refund (F4).
  3. The 20 ms sub-block is a revocable promise signed by the block producer. It is not a consensus object. Consensus is still BSC's Parlia PoSA, with at most 64 validators (F5, F7). Order-execution separation and application-specific sequencing are two different things (F9).
  4. The 0x76 native AA transaction matches Tempo's almost item by item: type byte, field names, precompile name, gas constants (F10). The shielded pool can call public contracts with pooled funds, so it is more than payments. But the call itself is public, and the pool takes only BNB (F12).
  5. "Lattice" appears only in the state commitment (LtHash). It is not Falcon, and no part of the stack uses PQ signatures. In 2026-09 researchers published a collision attack of about 2^81 queries on the same LtHash parameters. The New L1 docs still say "~128-bit" (F14, F15).

Context

The problem. BSC executes first and votes second: the producer executes every transaction before it proposes, and validators re-execute before they vote [5]. At 450 ms, execution gets only part of the block time; BNB Chain wants high-frequency trading, real-time payments and agent trading. Its targets are 100K+ TPS, sub-50ms preconfirmation and sub-second finality [14] (C7). The official view: BSC can't retrofit these changes, so it needs a new chain [15] (C1).

Why now.

  • 2026-07-08: the H2 2026 technical roadmap announced the new L1, with testnet planned for late 2026 and mainnet for early 2027 [14] (C6).
  • 2026-07-14: the BNB Chain forum opened a NewL1 category; the pinned post says it complements BSC [15] (C1).
  • 2026-10-22: the official docs site published the full New L1 design docs, at devnet stage [1] (C4).

I

Background

B-0

Parlia PoSA and BLS fast finality

~4min
What it is

Parlia is BSC's consensus. A stake-elected set of validators takes turns producing blocks, 16 blocks each. Fast finality is a voting layer on top. Validators sign the block header with BLS; once 2/3 have signed, the next producer aggregates the votes into its header.

Why it matters here

New L1 keeps this consensus and changes three things: the block interval, the validator cap, and what a vote signs [2] (C30, C33).

Minimal example

Votes for block N land in N+1 → N becomes justified; votes for N+1 land in N+2 → N becomes finalized. At 200 ms blocks that is about 0.5 s [2] (C34, C35).

Common misconception

Myth: PoSA is PoA. Fact: stake elects the validators every day, and the chain can slash them. But the set has a cap, so it is not permissionless PoS (C45).

[18] BEP-126 §4.1

B-1

Async execution (decoupling execution from consensus)

~4min
What it is

A conventional chain executes every transaction before it proposes a block, and the header carries the post-execution state_root. Async execution splits the two steps. Consensus only fixes the order. Execution runs in the background, and its result goes into a later block. Once consensus fixes the order, the order alone determines the result; execution only computes it.

Why it matters here

Execution, network-wide re-execution and voting do not fit in 200 ms. The whole New L1 design rests on this split [5] (X4, X6).

Minimal example

Monad writes block N's result into N+3; EIP-7886 into N+1; New L1 into N+D, where D follows load [5][31][32] (X20).

Common misconception

Myth: async execution is parallel execution. Fact: the first changes when execution happens; the second changes how one block executes.

B-2

Native AA transaction

~3min
What it is

A new transaction type (an EIP-2718 envelope) puts batched calls, sponsored gas, passkey signatures and limited session keys into the protocol. Nodes check them directly, with no bundler, EntryPoint or smart-contract wallet.

Why it matters here

New L1's 0x76 is this kind of transaction, and it closely matches Tempo's [7][33] (A1, A34).

Minimal example

One 0x76 transaction carries 1–64 calls under one outer signature, one nonce and one receipt [7] (A5).

Common misconception

Myth: native AA is EIP-7702. Fact: 7702 attaches contract code to an EOA; New L1 rejects 7702 transactions [8] (A30).

B-3

The note model of a shielded pool

~4min
What it is

Funds deposited in the pool become notes (similar to UTXOs). A note's hash (its commitment) goes into an append-only Merkle tree. To spend a note, you publish a nullifier to block double spends. A ZK proof shows that you own some note in the tree and that inputs equal outputs, without saying which note.

Why it matters here

New L1's ShieldedPool uses this model, plus a flow that calls public contracts from the pool [9] (P3, P9).

Minimal example

Zcash Orchard is payments only; Railgun can unshield → call a contract → reshield [43][44] (P25, P26).

Common misconception

Myth: a shielded pool hides everything. Fact: deposits, withdrawals and contract calls reveal amounts and targets [9] (P20).

[9] Shielded Pool

B-4

Homomorphic hashing with LtHash

~l2
What it is

A hash turns each state entry (an account or a storage slot) into a long vector; the chain adds all vectors element by element. The sum is the digest of the whole state. To change one entry, subtract its old vector and add its new one. Security rests on the SIS lattice problem: it is hard to find small coefficients that make a sum of vectors equal zero.

Why it matters here

New L1 uses it instead of an MPT; the word "lattice" comes from here [10] (P29, P31).

Minimal example

To update one state entry, subtract its old vector and add its new one [10] (P30).

Common misconception

Myth: using a lattice means post-quantum signatures. Fact: LtHash is a state commitment, not a signature (P37).

Go deeper

[40] SIMD-0215

B-5

Application-specific sequencing (ASS)

~l2
What it is

An app sets (or limits) the order of its own transactions and who gets the MEV. It does not leave this to the producer's tip ordering.

Why it matters here

It is the yardstick for asking whether New L1's order-execution separation is ASS (panel N).

Minimal example

Multi-Lane reserves capacity for an app's address but does not let the app set its transaction order (X50).

Common misconception

Myth: reserved capacity gives an app ordering rights. Fact: capacity isolation and application-specific sequencing are different mechanisms (X42, X50).

F5

The ~20 ms sub-block is a revocable promise signed by the producer, not a consensus object

confidence: high
Claim

During its turn, the current producer keeps packing ready transactions into signed slices (SubBlocks) and broadcasts them. A slice promises only inclusion and position, not voting, fork choice or finality. If the producer withdraws its stream, the status becomes aborted; if another producer takes the height, superseded. The stream is append-only, so a later higher-fee transaction cannot jump ahead. The forum proposal author calls it "not implemented at the protocol level … a reputational commitment".

Evidence

observed Pre-confirmation page, Guarantees and Limitations [3]; Transaction Lifecycle [4]; forum author reply [16] (C15, C20, C21, C23, C11). inferred 20 ms and 0.5 s are design targets, not measurements on a public network (C13).

Implication

The 20 ms itself is a target: the docs say ~20 ms, the roadmap sub-50ms, the forum 20–50 ms. Apps can use it for UI updates or payment receipts, but must handle revocation. Never release funds on it.

F6

No global mempool: a Gateway hands the transaction to the producer in one hop; "front-running protection" is just no broadcast

confidence: medium
Claim

A Gateway is an ordinary full node. It keeps custody of the transaction and sends replicas straight to the next producers on the validator schedule, which do not forward again. There is no txpool_*, and the current client has no auction or ordering API. The roadmap says TxStream is "blocking front-running by design", but the docs show only "no broadcast to a public mempool"; the producer still sees the transaction first. The TEE Gateway (encrypted intake and ordering inside a TEE) is only a forum proposal from 2026-10-10.

Evidence

observed Transaction Lifecycle [4], API list [13], roadmap [14], forum [16] (C24, C25, C8, C26). inferred No protocol mechanism backs the front-running claim (X43).

Implication

Front-running risk moves from searchers in a public mempool to the producer itself. Whether the TEE Gateway ships decides this.

F7

Consensus is still Parlia PoSA + BLS finality: not PoA, and not permissionless PoS

confidence: high
Claim

BNB stake elects up to 64 validators once a day, and the producer rotates every 16 blocks. A missed slot goes to others after a seeded random backoff. Once ⌈2N/3⌉ BLS votes arrive, the next producer aggregates them into its header. Casper-FFG rules then give justified and finalized heights, usually final after +2 blocks (about 0.5 s). The real change: a vote signs only the order. If a validator's local execution disagrees with an ExecutionCommitment, it abstains, so a wrong result cannot reach 2/3.

Evidence

observed Consensus page [2]; BEP-126 [18] (C30–C34, C36–C39). inferred A capped, stake-elected, slashable PoSA set (C45); 2.25× faster blocks (C42).

Implication

"PoA" is not accurate, and neither is "PoS". Decentralization is on BSC's scale: at most 64 validators. The docs also call Parlia the "current default" and are evaluating Minimmit as Consensus 2.0.

Inconsistencies inside the docs. How many blocks does order finality take? The consensus page says "+2 blocks", the API page "roughly one block interval", the status table "1–few" [2][3][13]. The migration guide says block-count constants are "off by ~3.75×" versus BSC; that uses BSC's old 750 ms. At today's 450 ms it is about 2.25× [11] (C43).

F2

The real novelty is the timing structure: headers carry no execution result, and the result lands D blocks later

confidence: high
Claim

A header carries only the fields known at proposal time, including the transaction list, and omits state_root, receipts_root, logs_bloom, gas_used and others. The background executor runs block N and writes the result as an ExecutionCommitment into the header of block N+D. D follows load: it moves toward 1 at low load and grows at high load, by at most ±1 per block. Governance sets its cap D_MAX, with no value in the docs and "up to 8 blocks" on the forum (preliminary). While catching up, one block can carry several commitments.

Evidence

observed Async Execution page [5]; forum author reply [16] (X4–X8, C29). inferred The docs describe adaptive D as a mechanism but do not say it runs on devnet (X11).

Implication

RPC meaning changes with it. latest is the executed block, D blocks behind the newest block on a subscription. A query for an ordered but unexecuted block returns a retryable -38004 [5] (X17). The executor also creates system transactions (rewards, slashing, validator updates).

F3

The "parallel EVM" is one sentence: access-list based, detailed design in progress

confidence: high
Claim

The docs give one sentence. It says: "The current design centers on an access-list-based parallel EVM … Detailed design is in progress." The scheduler, the handling of missed dependencies, and whether it reuses the EIP-7928 format are all absent. Yet the Overview architecture table lists "Parallel EVM" as part of the execution layer, with no maturity note. The roadmap also lists "parallel execution" as one route to 100K+ TPS.

Evidence

observed Async Execution, What's Next [5]; Overview architecture table [1]; roadmap [14] (X2, X3, C7).

Implication

Today you can assess only async execution. The 100K+ TPS target depends on a component whose detailed design is still in progress.

F4

Charging the declared gas_limit with no refund is the price of async execution

confidence: high
Claim

Consensus admits transactions against state that is D blocks old. So some admitted transactions will fail at execution: an empty balance, a drain earlier in the block, a nonce clash, a changed approval. To make them still pay for block space, New L1 charges gas_bid × gas_limit, refunds no unused gas, and voids EIP-3529 refunds. It derives an effectiveBalance from in-flight spend and admits a transaction only if that covers the cost. Each account also has hard caps on in-flight gas and calldata within the D window.

Evidence

observed Async Execution, "Paying for Block Space" [5]; migration guide [11]; AA page [7]; the docs contrast this with Monad's reserve balance (X12–X16, A24). inferred Every chain that moves execution off the consensus path must address admission against lagged state (M4).

Implication

A receipt's gasUsed usually equals the declared limit. Wallets and SDKs must change their defaults: margins such as estimate × 1.5 become pure spend. The protocol pins the base fee to 0, so the tip is the price [11].

F8

BSC's parallel EVM never reached an official release; New L1 changes a different layer: the timing structure

confidence: high
Claim

None of the 132 releases in the bsc repo enables Parallel EVM 1.0–3.0 or TxDAG. The only "parallel execution" is a 2025-12 BAL feature build. BSC removed BEP-592 in 2026-05, and its execution layer now follows upstream geth and EIP-7928. BSC's own BEP-684 only lets votes skip execution; the header still commits to state_root. New L1 goes further: the execution result leaves the header entirely, lands D blocks later, and D adapts.

Evidence

observed bsc release search, PR #3690, v1.8.0-alpha, PEVM 2.0 blog, 2023 roadmap, BEP-396, op-geth releases, BEP-684 [21]–[29] (X22, X23, X26, X28, X29, X32, X33, X35). inferred The 2023 roadmap's "deployed … to the BSC mainnet" means a fork running on full nodes, not the validator path (X24); New L1 goes further than BEP-684 (X36, X37). speculative No evidence shows whether New L1's access list reuses BAL / EIP-7928 (X38).

Implication

To judge New L1's execution, look at async execution. Treat the parallel EVM as not yet delivered.

N

Order-execution separation ≠ application-specific sequencing; Multi-Lane only reserves capacity

The architecture diagram says "Order-Execution separation"; the text means "votes sign the order, not the execution result" [1][2] (X39). It does not change who decides the order.

Dimension New L1 order-execution separation Application-specific sequencing (ASS)
Solves execution cannot block consensus at 200 ms the order of an app's own transactions, who gets the MEV
Who orders the current producer, by tip the app, an app sequencer, or contract rules
Granularity the whole chain one app or one trading pair
Ordering rights for apps ✗none ✓the core feature
Fair ordering / MEV rules ✗none in the protocol ✓usually a design goal

What Multi-Lane is. Governance registers a bps quota for some contract addresses in LaneRegistry; 1,500 bps means 15% of block gas [6] (X44, X45):

  • A transaction enters a lane deterministically by its to address; unregistered addresses and contract creations go to the default lane.
  • No calldata or selector routing: any transaction sent to a registered address uses that lane's quota.
  • It reserves capacity, not inclusion; inside a lane, ordering is by tip, with no FIFO.
  • Unused quota flows back to the default lane; occupancy counts the declared gas limit.
F9

Order-execution separation is only a timing split, orthogonal to ASS; Multi-Lane is capacity isolation

confidence: high
Claim

Ordering power stays with the current producer: the Gateway has no ordering API, lanes order by tip, and the preconfirmation window is append-only. So order-execution separation gives apps no ordering rights and does not change who gets the MEV. Multi-Lane reserves gas for registered contract addresses but gives no ordering rules, like the payment lanes on Tempo and BSC. Compared with BSC Payment Lane (BEP-703: one payment class, unused quota stays idle), Multi-Lane has several lanes, and unused quota flows back.

Evidence

observed Multi-Lane page [6]; Transaction Lifecycle [4]; Pre-confirmation [3]; BEP-703 [30] (X40, X41, X44–X47). inferred Orthogonal to ASS, so at most a base for ASS (X42, X50); the differences from Payment Lane (X48).

Implication

App-level ordering on New L1 needs a separate sequencer or contract rules built on top.

O

Native AA: 0x76 is a BNB variant of Tempo's design

The bot's transaction is a 0x76: 1–64 calls that succeed or fail together, with one signature, one nonce and one receipt [7] (A5). An account has three key levels, all managed by the AccountKeychain precompile (0x…4000) [7] (A11–A13):

Level Can do Limits
root its address is the account; deploys contracts, manages keys nobody can revoke it, so root cannot rotate within the same address
admin authorizes and revokes other keys cannot deploy; must have no scope, limit or expiry
access an ordinary session key bound by scope (target + selector), a native spend limit, an expiry

Alice's bot key is an access key, scoped to swap on the DEX router. The spend limit counts only native outflow, so it caps BNB but not BEP-20 tokens (A16, A33). The key also cannot use token_fee: that feature is only for root-signed, sponsored transactions [7] (A22).

F10

0x76 and the Tempo Transaction share type byte, fields, precompile, digest and gas constants

confidence: high
Claim

Both chains call their native AA transaction 0x76, with 12 identical field names. Both key precompiles have the name AccountKeychain and three levels, with the same admin limits. The delegated signing digest, the WebAuthn rules, the P256 and delegated-key surcharges, and "a revoked key can never be re-authorized" are all the same. New L1 drops Tempo's fee_token (paying gas in TIP-20) and the 7702-style delegation, and adds token_fee (the account repays the sponsor in a token). 2D nonces have a field but stay disabled. Tempo mainnet went live on 2026-03-18, seven months before the New L1 docs.

Evidence

observed New L1 AA page [7], transaction types [8]; Tempo transaction spec [33], AccountKeychain [34], mainnet blog [35] (A34–A36, A39–A43). inferred Many independent details match word for word and number for number, so it is a BNB variant of Tempo's design (A37). speculative Nobody can check whether the client ports Tempo's reth code (A38).

Implication

The same type byte with different fields means two schemas behind one 0x76; existing Tempo tools must not assume compatibility.

F11

The protocol fixes the signature schemes: adding PQ signatures needs a protocol upgrade; 7702 transactions are rejected

confidence: high
Claim

New L1 supports only secp256k1, P256 and WebAuthn signatures, and key management is a precompile built into the EVM. On 2026-10-08, EIP-8130 narrowed to "Keystore Accounts", and its transaction type moved to EIP-8430 (0x79, PR not merged). 8130 validates with pluggable authenticator contracts and expects PQ algorithms to arrive as new authenticators. 7702 attaches delegated code to an EOA; 4337 uses the off-protocol UserOp system. New L1 rejects 7702 and 4844 transactions and needs no 4337 infrastructure.

Evidence

observed AA page signature table [7]; System Contracts [12]; EIP-8130 @1a1f470 [36]; PR #12385 [37]; EIP-7702 [38], ERC-4337 [39] (A8, A13, A30, A44–A46, A48). inferred A new signature algorithm needs a protocol upgrade (A47).

Implication

The earlier Native AA report puts 0x79 under 8130; that is now out of date.

P

Shielded pool: one step beyond payments, far from private DeFi

ShieldedPool is a system contract predeployed at genesis (0x…5000) [9] (P1). It has four flows [9] (P9):

  • Shield: an EOA calls privDeposit; the address, amount and asset are public.
  • Shielded transfer: spends 1–2 notes inside the pool and always publishes 2 nullifiers (padding with a fake one), producing up to 3 notes.
  • Unshield: withdraws to a normal address; the amount, asset and destination are public.
  • Atomic call: takes funds out of the pool, calls one public contract, and puts the return value back into the pool.

Every spend carries two PLONK proofs (BN254, 864 bytes each). The pool proof shows value conservation and note ownership; the auth proof shows that the EOA recorded in the note signed an EIP-712 message [9][8] (P5, P6). There are two submission paths. A 0x77 transaction has no sender, nonce or outer signature, because the proofs are the authorization. Or a relayer calls transact [9] (P11, P12).

Flow Public Hidden
Shield depositor, amount, asset who holds it later
Shielded transfer the fee on the direct path sender, recipient, amount, asset
Unshield amount, asset, destination the note history
Atomic call unshield amount, call target, calldata, reshield amount who made the call
F12

Pooled funds can call public contracts, so it is more than payments; but it is not private DeFi

confidence: high
Claim

An atomic call lets pooled funds trigger one public EVM call; the result returns to the pool as an open note (owner hidden, amount and asset public). The DEX contract, call target, calldata and amounts are public, and only the link between Alice and this call is hidden. If the call reverts, the spend stands and you can retry the escrowed funds. Railgun's similar flow reverts as a whole. The only supported asset is native BNB.

Evidence

observed Privacy page, Flows, Current Status, Security Assumptions [9]; transaction types [8]; Railgun docs [43] (P8, P18, P19, P25). inferred The composability is "pooled funds trigger one public call", not private execution (P24). speculative The docs do not say whether an atomic call can target any contract (P27).

Implication

Is it only private payment? No, it can reach DeFi. But the DeFi itself is fully public, so it is "using public DeFi anonymously".

F13

Do not put real funds in the shielded pool yet: unaudited, someone else's SRS, BNB only

confidence: high
Claim

The docs' warning reads: "Do not treat it as safe for real value". The PLONK SRS is an imported public one; New L1's own ceremony and a third-party circuit audit remain outstanding pre-mainnet tasks. Not implemented: ERC-20 / BEP-20 shielding, the reserved PQ authorization, paymaster / 4337 submission, compliance hooks (an interface seam only), and recursive proof aggregation. The contract is immutable, and governance can only pause deposits.

Evidence

observed Privacy page [9]; FAQ [13] (P7, P17, P21–P23). inferred The roadmap's "selective disclosure for compliance" has not landed in the docs (P46).

Implication

Privacy today is "a design plus a devnet demo", not a usable product. Two more metadata leaks: registering a privacy address publicly links it to your EOA, and a relayer sees your IP and timing.

Q

PQ: "lattice" appears only in the state commitment

New L1 has no MPT. Each piece of state (an account or a non-zero storage slot) is one KV entry. Fig 5 shows how entries become the state_root [10] (P28, P29).

Where does PQ come in? In one place only. The docs base the accumulator's security on the SIS lattice problem. They say 1024 × u16 "targets ~128-bit security" and cite Bellare–Micciancio 1997 and Solana SIMD-0215 [10] (P31). The table lists the cryptography of every component [2][7][9][10][45] (P40–P43):

Component Uses PQ?
Consensus votes BLS aggregate signatures ✗
Account signatures secp256k1, P256, WebAuthn ✗
Sub-block signature 65-byte recoverable signature ✗
Privacy proofs PLONK on BN254 ✗
Privacy authorization EOA signs EIP-712 (PQ scheme reserved, not built) ✗
State commitment BLAKE3 + LtHash (lattice problem, not a signature) !partly
F14

LtHash is a state commitment, not Falcon; no part of New L1 uses PQ signatures

confidence: high
Claim

Falcon (FN-DSA) is a lattice signature: a private key signs, a public key verifies. LtHash is a homomorphic set hash: it compresses the whole state into a digest you can update incrementally. Both relate to lattices, but they do different jobs, and the New L1 docs never mention Falcon. BLS, secp256k1 / P256 / WebAuthn and BN254 PLONK are all elliptic-curve cryptography, which NIST says Shor's algorithm breaks. The roadmap's "Post-Quantum Readiness" is a research plan for all of BNB Chain (hybrid schemes, AA-based upgrades without new addresses). Its New L1 section treats LtHash only as a speed measure.

Evidence

observed State DB [10]; roadmap [14]; NIST IR 8547 [45] (P29, P31, P44, P45, P42). inferred LtHash is not a signature (P37); no component is PQ (P43).

Implication

Do not call New L1 a "post-quantum L1". "Lattice-based state commitment" is the accurate term.

F15

A ~2^81-query collision attack on the same LtHash parameters appeared in 2026-09; the docs still say ~128-bit

confidence: medium
Claim

ePrint 2026/2083 (2026-09-18) attacks LtHash16 (N = 1024, d = 16), which Facebook and Solana use. A collision needs about 2^81 hash queries and at most 2^101 operations. On 2026-09-25, SIMD-0215 rewrote its security section and accepted the attack. Its argument: the collision set has about 2^72.83 items, but fewer than 2^65 accounts hold lamports, so it cannot form a valid state. New L1 uses the same parameters with a different entry encoding (storage slots included). Its 2026-10-22 docs still say only "~128-bit".

Evidence

observed ePrint 2026/2083 abstract [41]; SIMD-0215 @f1afd94 security section [40]; State DB [10] (P32–P34). inferred The docs do not reflect this update (P35); Solana's rebuttal holds only for Solana's encoding, so New L1 needs its own argument (M7). speculative Solana's argument does not carry over to New L1 as is (P36).

Implication

This is not a directly exploitable bug. But New L1 must argue collision safety again for its own state encoding.

F16

The cost of dropping the MPT: no eth_getProof, no snap sync, and bridges need another design

confidence: medium
Claim

The accumulator is a sum, not a tree, so there is no inclusion path. eth_getProof always returns -32004, snap sync does not exist, and whole-state debug reads are not supported. Until an "accumulator-native" inclusion proof ships (the docs say planned), bridges and light clients must rely on BLS finality votes and full-node answers. The native BSC↔New L1 bridge is still in development, and the CrossChain address is a placeholder. The accumulator archive adds 2 KB per block, about 0.9 GB per day.

Evidence

observed State DB [10]; migration guide [11]; network info [13] (P38, P39, C2, M2).

Implication

Cross-chain designs, light clients and indexers that rely on MPT proofs cannot plug in directly.

R

What it means for us

These are factual premises plus inferences, not advice to BNB Chain.

  1. ASS design: New L1 covers only half. Multi-Lane sits at the same layer as the earlier report's "outer layer: allocate capacity by class". New L1 has no "inner layer: pick an ordering rule per class" (M5). So New L1 is not a reference implementation for ASS. Only its capacity setup (LaneRegistry + governance + unused quota flowing back) is a reference.
  2. Preconfirmation: the same strength, a one-sided promise by the producer. New L1's SubBlock, like the Mantle FIFO preconf lane in the earlier report, is not guaranteed by consensus (M6, F5). What is worth borrowing is the interface: signed slices, revocation states (aborted / superseded), and client-side self-verification steps [3].
  3. Async execution: the cost is already written down. When assessing "move execution off the critical path", design the admission rules at the same time (M4, F4). Options: fee on declared gas plus in-flight spend caps, or a Monad-style reserve balance. RPC meaning (latest = executed) must change too.
  4. Native AA: two chains now use the fixed Tempo-style design. The earlier report suggested an 8130 PoC first; the "protocol-fixed + 0x76 schema" route now has a second adopter (M3, F10). Unlike New L1's fixed signature schemes, EIP-8130's pluggable authenticators give a PQ upgrade path without a protocol upgrade (F11).
  5. PQ: do not treat LtHash as a PQ scheme. If you consider LtHash for state commitment, argue collision safety again for your own entry encoding (M7, F15).
CAUTION

Point 2 relies on the earlier report's description of Mantle's preconf lane. This report did not re-check Mantle's code.

S

Limits and open questions

  • No source code, no measurements. The New L1 client has no public repo. Every mechanism here comes from the 2026-10-22 docs snapshot (C50). 20 ms, 0.5 s and 100K+ TPS are targets (C13).
  • The docs are moving. The devnet is "highly unstable". The docs already contradict themselves: how many blocks order finality takes, which tip newHeads follows, and 64 validators versus the API range [2, 21] (C4, C44).
  • The roadmap and the docs differ. The roadmap's GasToken survives only as token_fee; "scheduled execution" maps only to validity windows; "selective disclosure" is only an interface seam (M8, M9, P46).
  • Speculative items (5). Whether the access list reuses EIP-7928 (X38); whether the AA ports Tempo's code (A38); whether atomic calls restrict targets (P27); whether Solana's LtHash argument carries over (P36); whether the scheme field of privDeposit holds a PQ slot (P48).
  • Open questions.
    1. The design of the access-list parallel EVM; the value of D_MAX; any accountability beyond abstaining when an execution commitment is wrong.
    2. Whether the TEE Gateway ships; the Minimmit timeline.
    3. Which SRS the deployment imports; when the audit and ceremony happen.
    4. Whether New L1 responds to ePrint 2026/2083; accumulator-native proofs and how the bridge verifies.
    5. Whether 0x76 is byte-compatible with Tempo.
