Starknet's Account Model, Post-Quantum Migration, and STRK20 / Shadow Accounts

Starknet's PQ confidence rests on two structural choices — a hash-based STARK proving layer and native accounts whose signature scheme the protocol does not fix. But as of 2026-10-14, mainnet has moved only the proving layer and two hashes off elliptic curves, and "a fully quantum-resistant L1 by 2027" is an option under consideration with no defined scope. The confidentiality of STRK20 and Shadow Accounts rests on Stark-curve ECDH and does not inherit the proving layer's PQ property.

Bottom line: the Starknet protocol does not fix a signature scheme. Each account contract decides which signatures it accepts, so a move to PQ signatures needs no hard fork (F1). The proving layer uses hash-based STARKs and does not depend on elliptic curves either. These two facts are the real basis for "faster than Ethereum". But on mainnet v0.14.4, the state tries, contract addresses, default account signatures, consensus and DA are not yet PQ (F4).

The confidentiality of STRK20 and Shadow Accounts uses Stark-curve ECDH, and the viewing public key is stored on-chain in plaintext. Once quantum attacks are practical, a user's private history and Shadow links can be rebuilt after the fact (F11, F14).

Background

B-0

Starknet native accounts

~4min
What it is

Starknet has no EOAs; every account is a contract. The protocol calls the account's __validate__, requires the return value 'VALID', then calls __execute__ with the call list [1][2].

Why it matters here

The signature scheme lives in the account contract, not in the protocol. This is why a move to PQ signatures needs no hard fork.

Minimal example
INVOKE v3 → account.__validate__(calls)   // check signature, return 'VALID'
          → account.__execute__(calls)    // call each target contract
Common misconception

Myth: Starknet accounts are quantum-resistant by default. Fact: OZ default accounts and Braavos use Stark-curve ECDSA by default; the five signer types in Argent (Ready) contracts include no PQ type [4][5].

B-1

What quantum computers break: Shor and Grover

~4min
What it is

Shor's algorithm solves elliptic-curve discrete logs in polynomial time. It breaks ECDSA, ECDH and the curve-based Pedersen hash. Grover's algorithm gives only a square-root speed-up on hash search, and larger parameters offset it [8].

Why it matters here

To decide whether a component is PQ, ask whether it depends on discrete logs or only on hashes.

Minimal example

Public key x(k·G) is on-chain → a quantum attacker solves for k → forges signatures, or decrypts data encrypted to k.

Common misconception

Myth: no quantum computer exists today, so data posted today is safe. Fact: ciphertexts and public keys stay on-chain forever, so they can be harvested now and decrypted later (HNDL).

Go deeper

[8] Quantum Hub "Learn"

B-2

A proof of correct execution ≠ a PQ signature

~3min
What it is

A STARK proves that a program ran by its rules. If that program checks an ECDSA signature, a signature forged with Shor is also accepted "correctly" [8].

Why it matters here

Starknet's proving layer is PQ, but that does not make accounts, addresses or privacy encryption PQ.

Minimal example

Quantum Hub: "A post-quantum proving layer does not migrate account signatures by implication."

Common misconception

Myth: STARKs make the whole chain quantum-resistant. Fact: the official answer to "Is Starknet quantum-resistant?" is "No. Not as a single system-wide claim."[8]

B-3

Pedersen, Poseidon, BLAKE2s

~4min
What it is

Starknet uses three hashes. Pedersen is a linear combination of Stark-curve points, so its security rests on discrete logs. Poseidon is an algebraic hash (Hades permutation). BLAKE2s is a conventional bitwise hash [2].

Why it matters here

Roadmap Phase 1 replaces Pedersen with BLAKE2. Where Pedersen is still used shows how much migration work remains.

Minimal example

Contract address = Pedersen("STARKNET_CONTRACT_ADDRESS", deployer, salt, class_hash, Pedersen(calldata)), still true on 2026-10-13 [1].

Common misconception

Myth: Pedersen is a hash, so it is as safe as BLAKE2. Fact: StarkWare says it "inherits elliptic-curve assumptions"[9].

B-4

Notes and nullifiers: how a privacy pool stops double spends

~5min
What it is

In a privacy pool, a balance is not balances[user] but a set of notes. Spending a note writes its nullifier on-chain, and each nullifier can be written only once [16].

Why it matters here

STRK20 is this kind of pool. The nullifier comes from a private key, so observers cannot match it to the spent note.

Minimal example
note_id   = Poseidon(NOTE_ID_TAG, channel_key, token, index, 0)
nullifier = Poseidon(NULLIFIER_TAG, channel_key, token, index, 0, k)
Common misconception

Myth: STRK20 turns Starknet into a UTXO chain. Fact: notes live only in one contract's storage; the chain keeps its account model [16].

B-5

ECDH and the viewing key

~4min
What it is

ECDH lets two parties derive the same shared secret on an elliptic curve. STRK20 uses it to encrypt channel data to the recipient, and the user's viewing key to the auditor [16].

Why it matters here

All STRK20 confidentiality rests on ECDH, so its PQ status differs from the proving layer.

Minimal example

R = r·G, shared = x(r·K) = x(k·R), ciphertext = Poseidon(tag, shared) + plaintext [16].

Common misconception

Myth: a viewing key can only "view". Fact: the STRK20 viewing private key also derives nullifiers and Shadow identities, so a leak exposes the whole private history [16].

Accounts: the protocol calls entry points, the contract picks the scheme

Fig 2 shows the call order between the protocol and the account when Alice sends a plain transfer. The protocol does three things [1]. It picks the entry point by transaction type. It calls with caller = 0. It checks that the return value is 'VALID'. Which signature scheme to use, and how to check it, is up to Alice's account contract.

Validation limits. On mainnet v0.14.4, __validate__ may use at most 1,000,000 Cairo steps and 100M L2 gas [1]. It cannot call other contracts or deploy. It reads the block number rounded down to a multiple of 100, and the timestamp rounded down to the hour [1]. The official reason is to stop free DoS (heavy validation that then fails) and mempool pollution [2].

L

Falcon-512 accounts: they run, but are costly and unaudited

The algorithm. Falcon-512 is a lattice-based signature. Verification works in the ring ℤ12289[x]/(x512+1) [10]:

c=HashToPoint(m, salt),s0=c−s1h(modq),‖s0‖2+‖s1‖2≤34,034,726

h is the public key and s1 is the signature. A Falcon-512 public key is 897 bytes and a signature is 666 bytes [10]. In Cairo, the public key packs into 29 felts and a direct signature into 31 felts [10].

Variants. OZ cairo-pq-verifiers implements five variants: hint mode with a BLAKE2s, Poseidon or SHAKE-256 hash-to-point, and direct mode with BLAKE2s or SHAKE-256 [10]. Only SHAKE-256 interoperates with standard signers. In hint mode the signer supplies s1h and the chain only checks it; in direct mode the chain computes it. Both modes have the same security [10].

STRK20: a contract-level privacy pool

STRK20 is one privacy-pool contract on Starknet (0x0403…812a). It was deployed with v0.14.2 on 2026-04-20, and launched officially on 2026-06-09 [16][23]. The unusual part is steps 3–6 of Fig 4. Private logic runs in a virtual OS and produces a proof. The sequencer gateway verifies the proof; the on-chain contract checks only the proof facts [16][1].

What runs on-chain. apply_actions runs validate_proof → collect_fee (2.5 STRK) → _apply_actions [16]. Nullifier WriteOnce stops double spends: before a write, the contract asserts the slot is empty [16]. Per-token running balances enforce conservation; each must be zero at the end of the transaction [16].

F9

STRK20 is a contract-level privacy pool; the sequencer gateway verifies its proofs, which are not settled on Ethereum yet

confidence: high
Claim

The pool contract's own __execute__, run in the virtual OS, compiles private actions into public ones. The sequencer gateway verifies the Stwo proof; the contract checks only the message hash in the proof facts and 450-block freshness. SNIP-36 states that in Phase 1, Starknet consensus alone verifies the proofs.

Evidence

observed privacy.cairo, actions.cairo [16] (S1–S7); gateway.rs, account_transaction.rs [1] (S8–S10); SNIP-36 [19] (S11); proof_fact_fold.rs still uses test constants [1] (S12); pool deployment and parameters [11] (S52, S55).

Implication

STRK20 state correctness depends today on Starknet consensus (3 sequencers), not on proof verification on Ethereum.

Authorization and compliance. A spend needs Alice's account signature, and the pool accepts any one of three paths: custom validation, is_valid_signature(tx_hash), or is_valid_signature(SNIP-12 CallSet hash) [16]. On first use, Alice registers a viewing key. The public key x(k·G) goes on-chain in plaintext, and the private key k is ECDH-encrypted to the single auditor public key; both are write-once [16]. A deposit needs an attestation signed by a screener, valid for 300 seconds [16].

Who sees what. By observer [18][16]:

Observer Can see Cannot see
On-chain observer Depositor, withdrawal recipient, amounts; recipient address of a new channel; timing Amount, token and parties of a plain transfer
Relayer / paymaster User IP, the submitted payload Private actions in plaintext
Proving service Viewing key and all private actions (full witness) —
Discovery service Viewing key, channel and note counts, sync times IP, when an OHTTP relay is used
Auditor Full history after decrypting the viewing key Cannot sign spends
Bob (recipient) The sender and all amounts on that channel Alice's other channels
F10

STRK20 hides data only from on-chain observers; the proving and discovery services get the viewing key

confidence: high
Claim

The virtual-transaction calldata that the SDK sends to the proving service contains the viewing key and all private actions. OHTTP hides only the IP and blocks the TLS terminator; it does not hide data from the service operator. Deposit and withdrawal amounts and new-channel recipients are public. The sender is hidden from outsiders only when a paymaster submits.

Evidence

observed SDK proof-invocation-factory.ts [16] (S5); discovery security spec [16] (S31); official security page [18] (S27–S29); SNIP-36 "privacy is de facto" [19] (S33). inferred The proving service gets the full witness (S30).

Implication

When you assess STRK20 privacy, count the proving-service and discovery-service operators as trusted parties.

F11

STRK20's encryption layer is Stark-curve ECDH and does not inherit the proving layer's PQ property

confidence: high
Claim

Channel distribution and auditor escrow use Stark-curve ECDH plus Poseidon masking, with no PQ key encapsulation. The viewing public key x(k·G) is stored on-chain in plaintext and cannot be replaced. The official "Post-quantum" wording refers only to the proof system.

Evidence

observed _compute_shared_x and encrypt_private_key in utils.cairo [16] (S23, S34, S35); interactive page "No trusted setup. Post-quantum." (S40); a search-index snippet of starknetprivacy.com showed "quantum-resistant by design", which the page source no longer contains on 2026-10-14 (X4). inferred A quantum attacker can recover k from the on-chain public key (S36); the auditor public key is a single global point of failure (S38).

Implication

Do not describe STRK20 confidentiality with "Starknet's proving layer is quantum-resistant".

Audit and formal verification. OpenZeppelin audited commit c5e2fb5 (2026-03-18 to 03-31, report 2026-05-29) and found 0 Critical / High issues [17]. The scope is only the 9 files in packages/privacy/src, without the anonymizer or the SDK [17]. The Lean development has 236 theorems and no sorry. It models the hash as injective and encryption as an abstract invertible function, so it proves neither confidentiality nor quantum resistance [16][20].

StarkWare's words: "We formally verified the protocol. The Cairo contract that implements it is covered separately by the OpenZeppelin audit."[20]

O

Shadow Account: a keyless proxy contract

What it is. The official docs: "A shadow account is a persistent, pseudonymous identity for one user and one dapp … A shadow account is not a wallet account: it has no keys and cannot sign."[21] Fig 5 is the authorization chain from Alice's signature to the Vesu contract.

The Shadow Account contract is small. Its storage holds only owner (the anonymizer) and an upgrade component. Its single business entry point, execute, checks only that the caller is the owner [22]. It has no __validate__, __execute__ or is_valid_signature [22][11].

Address derivation. Three Poseidon steps give the salt. The address then follows the Pedersen contract-address formula, with the fixed Primer class [16][22]:

identity_key=Poseidon(𝙸𝙳𝙴𝙽𝚃𝙸𝚃𝚈_𝙺𝙴𝚈_𝚃𝙰𝙶, 𝑢𝑠𝑒𝑟, k, 𝑎𝑛𝑜𝑛𝑦𝑚𝑖𝑧𝑒𝑟)𝑝𝑎𝑟𝑡𝑖𝑎𝑙=Poseidon(identity_key, dapp_name)𝑐𝑜𝑚𝑚𝑖𝑡𝑚𝑒𝑛𝑡=Poseidon(𝑝𝑎𝑟𝑡𝑖𝑎𝑙, 𝑛𝑜𝑛𝑐𝑒)𝑎𝑑𝑑𝑟𝑒𝑠𝑠=Pedersen_addr(𝑠𝑎𝑙𝑡=𝑐𝑜𝑚𝑚𝑖𝑡𝑚𝑒𝑛𝑡, 𝙿𝚁𝙸𝙼𝙴𝚁_𝙲𝙻𝙰𝚂𝚂_𝙷𝙰𝚂𝙷, 𝑑𝑒𝑝𝑙𝑜𝑦𝑒𝑟=𝑎𝑛𝑜𝑛𝑦𝑚𝑖𝑧𝑒𝑟)

Here k is Alice's STRK20 viewing private key [16]. We recomputed the addresses from mainnet events: 172 of 173 Shadow Accounts match. The first one (2026-09-07) was deployed before the Primer method existed, with the runtime class [11].

One Vesu deposit. Fig 6 shows Alice moving private USDC into Vesu. On-chain, this is one transaction: a relayer calls pool.apply_actions [11][16].

F12

A Shadow Account is a keyless proxy authorized by privacy proofs and driven only by the anonymizer

confidence: high
Claim

A Shadow Account stores its owner (the anonymizer) and an upgrade component. Its business entry point execute accepts only the owner. The anonymizer accepts calls only from the privacy pool and puts no limit on call targets or selectors. The pool calls the anonymizer only when a proof is valid. On mainnet, governance can upgrade the anonymizer with zero delay.

Evidence

observed shadow_account.cairo [22] (W12–W15); shadow_account_anonymizer.cairo [16] (W17, W18, W22); mainnet ABI and owner queries [11] (W11, W14, W15); authorization chain (W32–W35). inferred dapp_name is an identity namespace, not a call permission (W19); governance has potential control over all Shadow assets (W49).

Implication

"Derived for one dapp" does not mean "can only call that dapp". Permission limits must come from the wallet, or from extra contract logic.

Is it a private sub-account? The instinct is right. StarkWare's 2026-07-15 blog still called it "private sub-accounts … Not live yet", and the SDK renamed it to Shadow Account only in RC.5 on 2026-08-12 [23][16]. But the key differences are:

Dimension Intuitive private sub-account Actual Shadow Account
Key Its own child key ✗No key, cannot sign
Who sends txs The sub-account itself A relayer calls the pool, which drives it
Contents Balances and actions private ✗Balances, calls, positions all public
What is hidden Everything ✓Only the link to the main wallet
Granularity Any One per (user, anonymizer, dapp_name, nonce)
Protocol account Yes ✗Cannot send txs or is_valid_signature
F13

"Like a private sub-account" holds, but it hides the link, not the contents

confidence: high
Claim

A Shadow Account's balances, calls and positions are all public. Anyone can list every Shadow address from ShadowAccountDeployed events. A dapp that holds a partial commitment can list all nonces of that user under its dapp_name. Mainnet deployments started on 2026-09-07, with 173 by 2026-10-14. We found no official launch post dated 2026-10-13.

Evidence

observed official docs "What is private" [21] (W2, W42); events and get_shadow_accounts [16][11] (W43, W44); rename record [23][16] (W4–W6); mainnet event count [11] (W7, W8). inferred Matches the official former name (W47); cannot join protocols that need an account signature (W48). speculative The "10-13 launch" has no primary source (W9).

Implication

Shadow Accounts suit "public position, separate identity" cases such as lending and staking. They are not confidential execution.

The public OZ audit (2026-05-29) never mentions shadow accounts or the anonymizer [17]; no public audit covers the Shadow contracts yet. The official Vesu vault demo lives under the personal account starkience and calls itself "educational, not audited"[21].

PQ × privacy: one key ties together the whole history

Fig 7 shows which derivations use Alice's viewing private key k. The left side is public on-chain data; the right side is what k can rebuild.

F14

Recovering one viewing key rebuilds a user's private transfer history and all Shadow links after the fact

confidence: high
Claim

Nullifiers, channel keys and the Shadow identity_key all derive from the same k. The public key of k is on-chain in plaintext, written once and never replaceable. dapp_name is a short, guessable string, nonces are usually small, and every commitment is on-chain for comparison. The auditor public key is a single global point of failure: breaking it yields every registered user's k.

Evidence

observed hashes.cairo, privacy.cairo, utils.cairo [16] (S13–S16, S23, W24, W30); event listing (W43). inferred Recovery paths follow from the derivations (S36–S38, W46, X1).

Implication

A PQ migration of STRK20 cannot just rotate to new keys. On-chain public keys and ciphertexts cannot be withdrawn, so pre-migration history stays exposed.

F15

Switching only __validate__ to a PQ signature does not make every authorization path quantum-resistant

confidence: medium
Claim

STRK20 spend authorization calls the account's is_valid_signature or custom validation, not __validate__. Accounts also have separate signature paths: guardians, session keys, SNIP-9 outside execution.

Evidence

observed the three paths in assert_valid_signature [16] (S21); SNIP-6, SNIP-9 [3] (A27, A29); Argent guardians and Braavos's demoted Stark signer [5] (A42, A44). inferred If any path keeps ECDSA, the account still carries quantum risk (A51, S22, X2).

Implication

A PQ account review must cover the whole authorization graph: transaction entry, is_valid_signature, recovery, sessions and upgrades.

Q

Acceptance checks: how to tell if "a PQ L1 by 2027" is delivered

These are checks we suggest for tracking Starknet's next announcements. They are recommendations, not an official standard; each maps to a gap above.

  1. Scope: does Starknet publish the list of components that "fully quantum-resistant" covers (F6)?
  2. Phase 1: which release ships the BLAKE2 move for tries and addresses, and on which date (F4, F7)?
  3. Legacy state: does the legacy storage migration toolkit have a spec and code (F7)?
  4. Consensus: which vote signature scheme, is it PQ from day one, and how does the validator set decentralize (F7)?
  5. The L1 itself: specs for DA, settlement and finality; a plan for existing StarkGate assets (F7, F8)?
  6. Accounts: do major wallets ship a PQ signer and a migration flow that also removes old signature paths (F3, F15)?
  7. Falcon: is there an audit, and which variant follows the final FIPS 206 (F5)?
  8. Privacy: does STRK20 adopt PQ key encapsulation, and what happens to historical ciphertexts (F11, F14)?
CAUTION

When you quote Starknet's PQ progress, state the status per component, with version and date. Neither "Starknet is quantum-resistant" nor "Starknet will be a PQ L1 in 2027" has primary-source support today.

R

Limits and open questions

  • No reruns: scarb / snforge are not installed. Falcon costs come from the repository baseline, not from a local rerun.
  • Falcon cost gap: the mainnet receipt (63.9M L2 gas) is about half the devnet figure for the same variant (about 139.9M). The cause is unknown. The demo account's class was also not compared with a build (v0.14.4 removed the feeder get_class_hash_at).
  • Mainnet vs. source: for the pool and anonymizer, we checked only the version string '2.1' and the ABI, with no build comparison. The live sequencer configuration may also differ from the main branch (for example, consensus signing).
  • Audit coverage: code added after audit commit c5e2fb5 (the snip12 legacy signature path, ComputeAndInvoke, the anonymizer) has no public audit.
  • Proof parameters: we found no primary evidence for the S-two hash or security bits of mainnet block proofs, or for when private-transaction proofs settle on L1.
  • Unverified: the primary source of "S2morrow in production on mainnet on 2026-04-01" (C62); the Ready app's default signer (A45); the curve of the consensus authentication key (R35); whether wallets bind dapp_name to the site origin (W51); the conditions for "under ten cents" with a 2.5 STRK pool fee (S57).
  • Conflicts in official material: who generates proofs (the interactive page, the architecture page and starkzap differ); the screening provider (Elliptic or FPI); docs Version Notes stop at v0.14.1.
