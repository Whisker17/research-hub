Starknet 账户模型、后量子迁移与 STRK20 / Shadow Account

Starknet 的 PQ 底气来自两项结构设计：基于 hash 的 STARK 证明层，和协议不规定签名算法的原生账户。但截至 2026-10-14，主网只有证明层和两个 hash 迁出了椭圆曲线；“2027 年成为完全抗量子的 L1”还只是一个没有范围定义的考虑方向。STRK20 与 Shadow Account 的保密性建立在 Stark 曲线 ECDH 上，不继承证明层的 PQ 属性。

背景动机

问题：2026-10-08，@Starknet 发推：“We are actively considering becoming an L1. This would enable Starknet to become the first fully quantum-resistant network, with 2027 as our target.”[13] Ethereum Foundation（EF）Protocol 的目标是 2029 年 12 月 [15]。同一时期，StarkWare 在推广 STRK20 的 Shadow Account。我们想知道两件事：Starknet 凭什么觉得 2027 年就能成为 PQ L1；它的隐私协议和 Shadow Account 怎么工作。

为什么现在：Mantle 的研究要求所有输出都经过确定性验证。Starknet 的账户与 PQ 叙事近期被频繁引用，需要逐组件核对：哪些已上主网，哪些只在路线图上。

范围：

  • Starknet 原生账户与 EVM 账户模型（EOA、ERC-4337、EIP-7702、Native AA 提案）的区别
  • 组件级的密码学清单、PQ 状态和 Falcon-512 账户
  • “2027 PQ L1”：官方表述、三阶段路线图进度、转 L1 缺口、与 Ethereum 2029 对照
  • STRK20 隐私协议与 Shadow Account 的原理和隐私边界

非目标：投资建议与 STRK 价格；完整安全审计；Cairo / Lean 测试的本地复跑（本机没有 scarb / snforge）；密码学方案本身的安全性证明。

已有资料的不足：外部调研（ChatGPT Deep Research）的框架正确 [26]。但它有几处要修正：Falcon 成本表漏了一行，口径是资源量不是收费；把两个同名 s2morrow 仓库混为一谈；note / nullifier / identity 公式漏了 domain tag；没确认证明服务能拿到 viewing key。本文用源码、主网 RPC 和官方文档逐条核对（见 面板 S）。

前置知识

B-0

Starknet 原生账户（native account）

~4min
是什么

Starknet 没有 EOA，每个账户都是合约。协议按交易类型调用账户的 __validate__，要求它返回 'VALID'，再调用 __execute__ 执行调用列表 [1][2]。

为什么这里需要

签名算法写在账户合约里，不写在协议里。这就是“换 PQ 签名不需要硬分叉”的来源。

最小例子
INVOKE v3 → account.__validate__(calls)   // 验签，返回 'VALID'
          → account.__execute__(calls)    // 逐个调用目标合约
常见误解

误解：Starknet 账户默认就抗量子。事实：OZ 默认账户和 Braavos 默认用 Stark 曲线 ECDSA；Argent（Ready）合约的五类 signer 里没有 PQ 类型 [4][5]。

B-1

量子计算破坏什么：Shor 与 Grover

~4min
是什么

Shor 算法能在多项式时间内解椭圆曲线离散对数，所以 ECDSA、ECDH 和基于椭圆曲线的 Pedersen 都会失效。Grover 算法只给哈希搜索带来平方级加速，可以靠加大参数应对 [8]。

为什么这里需要

判断一个组件是不是 PQ，就看它依赖离散对数还是只依赖哈希。

最小例子

公钥 x(k·G) 已经上链 → 有量子计算机的攻击者解出 k → 伪造签名，或解密用 k 加密的数据。

常见误解

误解：现在没有量子计算机，所以今天上链的数据安全。事实：密文和公钥会永久留在链上，可以“先收集、后解密”（HNDL）。

B-2

证明正确执行 ≠ 签名抗量子

~3min
是什么

STARK 证明“这段程序按规则执行了”。如果程序里验的是 ECDSA 签名，攻击者用 Shor 伪造的签名同样会被“正确地”接受 [8]。

为什么这里需要

Starknet 的证明层抗量子，但这不能推出账户、地址或隐私加密抗量子。

最小例子

Quantum Hub 原文：“A post-quantum proving layer does not migrate account signatures by implication.”

常见误解

误解：用了 STARK，整条链就抗量子。事实：官方对“Is Starknet quantum-resistant?”的回答是“No. Not as a single system-wide claim.”[8]

B-3

Pedersen、Poseidon、BLAKE2s

~4min
是什么

Starknet 用三种 hash。Pedersen 是 Stark 曲线点的线性组合，安全性依赖离散对数。Poseidon 是代数 hash（Hades 置换）。BLAKE2s 是传统位运算 hash [2]。

为什么这里需要

路线图的 Phase 1 就是把 Pedersen 换成 BLAKE2。哪些位置还在用 Pedersen，决定了还剩多少迁移工作。

最小例子

合约地址 = Pedersen("STARKNET_CONTRACT_ADDRESS", deployer, salt, class_hash, Pedersen(calldata))，到 2026-10-13 仍是这样 [1]。

常见误解

误解：Pedersen 叫 hash，所以和 BLAKE2 一样安全。事实：StarkWare 自己说它“inherits elliptic-curve assumptions”[9]。

B-4

note 与 nullifier：隐私池怎么防双花

~5min
是什么

隐私池里的余额不是 balances[user]，而是一组 note。花掉一个 note 时，链上写入它的 nullifier；同一个 nullifier 只能写一次 [16]。

为什么这里需要

STRK20 就是这种隐私池。nullifier 由私钥派生，旁观者无法把它和被花的 note 对上。

最小例子
note_id   = Poseidon(NOTE_ID_TAG, channel_key, token, index, 0)
nullifier = Poseidon(NULLIFIER_TAG, channel_key, token, index, 0, k)
常见误解

误解：STRK20 把 Starknet 变成了 UTXO 链。事实：note 只存在于一个合约的存储里，链本身仍是账户模型 [16]。

B-5

ECDH 与 viewing key

~4min
是什么

ECDH 让双方用椭圆曲线算出同一个共享密钥。STRK20 用它把通道信息加密给收款方，把用户的 viewing key 加密给 auditor [16]。

为什么这里需要

STRK20 的保密性全部建立在 ECDH 上，所以它的 PQ 状态和证明层不同。

最小例子

R = r·G，共享 = x(r·K) = x(k·R)，密文 = Poseidon(tag, 共享) + 明文 [16]。

常见误解

误解：viewing key 只能“看”。事实：STRK20 的 viewing 私钥还参与 nullifier 和 Shadow 身份派生，泄露它会暴露整段私有历史 [16]。

账户模型：协议只调入口，签名由合约定

Fig 2 是 Alice 发一笔普通转账时，协议和账户之间的调用顺序。协议做三件事：按交易类型选入口，以 caller = 0 调用，检查返回值是否为 'VALID' [1]。签名用什么算法、怎么验，全由 Alice 的账户合约决定。

验证阶段的限制。 在主网 v0.14.4 上，__validate__ 最多用 1,000,000 Cairo steps 和 1 亿 L2 gas [1]。它不能调用其他合约，不能 deploy，读到的区块号向下取整到 100 的倍数，时间戳向下取整到整点 [1]。官方给出的理由是防止“验证很重、最后失败”的免费 DoS 和 mempool 污染 [2]。

Starknet 协议不规定签名算法：账户合约决定接受什么签名

置信度: high
论断

协议按交易类型以 caller = 0 调用 __validate__ / __validate_declare__ / __validate_deploy__，返回值必须是 'VALID'；验证阶段上限为 1,000,000 steps / 1 亿 L2 gas，并禁止外部调用。账户还能用 replace_class_syscall 原地换 class，地址和存储不变。

证据

observed blockifier account_transaction.rs、versioned constants、syscall 限制 [1]（A1–A13）；OZ / Argent / Braavos 升级实现 [4][5]（A30–A33）。

影响

换成 PQ 签名不需要硬分叉，只需要新账户 class，或已有账户升级 class。

F2

与 EVM 的真正差别是“没有协议根密钥”，不是“能不能写 PQ 验证”

置信度: high
论断

EOA 和 7702 账户的根密钥由协议固定为 secp256k1；7702 委托后，原私钥仍能直接发交易、重新委托。4337 也能写 PQ 验证，而且它的 nonce（192 位 key）比 Starknet 更灵活。Starknet 的原生 paymaster 字段目前被 gateway 拒收。

证据

observed EIP-7702 第 3、5、8 步与“Transaction origination”[6]（A53–A55）；ERC-4337 getNonce(address, uint192 key)[6]（A57）；gateway validate_empty_paymaster_data[1]（A20）。inferred 7702 委托 PQ 代码不能消除原私钥的量子风险（A56）。

影响

评估 PQ 迁移时，要问“协议是否强制保留一把 ECDSA 根密钥”，而不只问“合约能不能验 PQ 签名”。

F3

已有账户不会自动变成 PQ；升级授权本身仍依赖旧 ECDSA

置信度: high
论断

OZ、Argent、Braavos 账户都能自调用 replace_class 换成 PQ class，但这次升级必须先通过旧 ECDSA 的 __validate__。三家都没有公开迁移流程。主网 Falcon 演示账户是新部署账户（nonce = 1），不是升级而来。

证据

observed Quantum Hub “Existing accounts do not change automatically”[7]（A49）；升级守卫 [4][5]（A30–A33）；RPC 读到演示交易 nonce = 0x1 [11]（A46）。inferred 升级依赖旧签名（A50）；演示账户为新部署（A48）。

影响

已有账户必须在量子威胁到来之前完成升级；guardian、session、is_valid_signature 这些旧签名路径也要一起移除（见 F15）。

Falcon-512 账户：能跑，但贵且未审计

算法。 Falcon-512 是基于格的签名。验证在环 ℤ12289[x]/(x512+1) 上进行 [10]：

c=HashToPoint(m, salt),s0=c−s1h(modq),‖s0‖2+‖s1‖2≤34,034,726

h 是公钥，s1 是签名。Falcon-512 公钥 897 字节、签名 666 字节 [10]。在 Cairo 里，公钥打包成 29 个 felt，direct 签名 31 个 felt [10]。

变体。 OZ cairo-pq-verifiers 实现了 5 个变体：hint 模式配 BLAKE2s、Poseidon 或 SHAKE-256 三种 hash-to-point，direct 模式配 BLAKE2s 或 SHAKE-256 [10]。只有 SHAKE-256 与标准签名器互通。hint 由签名者附带 s1h，链上只检查；direct 由链上自己算。两者安全性相同 [10]。

STRK20：合约级隐私池

STRK20 是部署在 Starknet 上的一个隐私池合约（0x0403…812a），2026-04-20 随 v0.14.2 部署，2026-06-09 官方宣布上线 [16][23]。特别之处在 Fig 4 第 3–6 步。私有逻辑在 虚拟 OS 里执行并生成证明；证明由 sequencer 网关验证，链上合约只核对 proof facts [16][1]。

链上做什么。 apply_actions 依次执行：validate_proof → collect_fee（2.5 STRK）→ _apply_actions [16]。双花靠 nullifier 的 WriteOnce：写入前断言槽位为空 [16]。守恒靠逐 token 的临时余额，交易结束时必须归零 [16]。

论断

私有动作在虚拟 OS 里由池合约自己的 __execute__ 编译成公开动作；Stwo 证明由 sequencer 网关验证，合约只核对 proof facts 中的消息哈希和 450 块新鲜度。SNIP-36 写明 Phase 1 的证明只由 Starknet 共识验证。

授权与合规。 支出要 Alice 的账户签名，池合约接受三条路径中的任一条：custom 校验、is_valid_signature(tx_hash)、is_valid_signature(SNIP-12 CallSet hash) [16]。Alice 第一次使用时注册 viewing key：公钥 x(k·G) 明文写到链上，私钥 k 用 ECDH 加密给唯一的 auditor 公钥；两者都只能写一次 [16]。存款需要筛查方签名的 attestation，有效期 300 秒 [16]。

O

Shadow Account：无密钥代理合约

是什么。 官方文档原文：“A shadow account is a persistent, pseudonymous identity for one user and one dapp … A shadow account is not a wallet account: it has no keys and cannot sign.”[21] Fig 5 是从 Alice 签名到 Vesu 合约的授权链。

Shadow Account 合约很小：存储只有 owner（就是 anonymizer）和升级组件；唯一的业务入口 execute 只检查 caller 是否为 owner [22]。它没有 __validate__、__execute__ 和 is_valid_signature [22][11]。

地址派生。 salt 由三层 Poseidon 得到，地址再按 Pedersen 合约地址公式、用固定的 Primer class 计算 [16][22]：

identity_key=Poseidon(𝙸𝙳𝙴𝙽𝚃𝙸𝚃𝚈_𝙺𝙴𝚈_𝚃𝙰𝙶, 𝑢𝑠𝑒𝑟, k, 𝑎𝑛𝑜𝑛𝑦𝑚𝑖𝑧𝑒𝑟)𝑝𝑎𝑟𝑡𝑖𝑎𝑙=Poseidon(identity_key, dapp_name)𝑐𝑜𝑚𝑚𝑖𝑡𝑚𝑒𝑛𝑡=Poseidon(𝑝𝑎𝑟𝑡𝑖𝑎𝑙, 𝑛𝑜𝑛𝑐𝑒)𝑎𝑑𝑑𝑟𝑒𝑠𝑠=Pedersen_addr(𝑠𝑎𝑙𝑡=𝑐𝑜𝑚𝑚𝑖𝑡𝑚𝑒𝑛𝑡, 𝙿𝚁𝙸𝙼𝙴𝚁_𝙲𝙻𝙰𝚂𝚂_𝙷𝙰𝚂𝙷, 𝑑𝑒𝑝𝑙𝑜𝑦𝑒𝑟=𝑎𝑛𝑜𝑛𝑦𝑚𝑖𝑧𝑒𝑟)

这里的 k 就是 Alice 的 STRK20 viewing 私钥 [16]。我们用主网事件复算：173 个 Shadow Account 中 172 个地址吻合；第一个（2026-09-07）在 Primer 方式引入之前部署，按运行时 class 计算 [11]。

STRK20 的支出授权调用账户的 is_valid_signature 或 custom 校验，不调用 __validate__。账户还有 guardian、session key、SNIP-9 outside execution 等独立的签名路径。

证据

observed assert_valid_signature 三条路径 [16]（S21）；SNIP-6、SNIP-9 [3]（A27、A29）；Argent guardian、Braavos 降级后的 Stark signer [5]（A42、A44）。inferred 任一路径保留 ECDSA，账户就仍有量子风险（A51、S22、X2）。

影响

PQ 账户的检查范围是整张授权图：交易入口、is_valid_signature、恢复、会话、升级。

Q

验收清单：怎样判断“2027 PQ L1”是否兑现

下面是我们建议的检查项，用来跟踪 Starknet 后续的公告。它们是建议，不是官方标准；每一项都对应前面的一个缺口。

  1. 范围定义：官方是否给出“fully quantum-resistant”覆盖的组件清单（F6）。
  2. Phase 1：合约树、存储树、地址派生的 BLAKE2 迁移进了哪个版本，哪天上主网（F4、F7）。
  3. 旧状态：旧合约存储迁移工具是否有规范和实现（F7）。
  4. 共识：投票签名用什么方案，是否直接上 PQ；验证者集合怎样去中心化（F7）。
  5. L1 本身：DA、结算、最终性的规范；StarkGate 上存量资产的处置方案（F7、F8）。
  6. 账户：主流钱包是否发布 PQ signer 和迁移流程；迁移是否同时移除旧签名路径（F3、F15）。
  7. Falcon：是否有审计；FIPS 206 定稿后用哪个变体（F5）。
  8. 隐私：STRK20 是否引入 PQ 密钥封装；历史密文怎么处理（F11、F14）。
CAUTION

引用 Starknet 的 PQ 进展时，按组件写状态，并注明版本和日期。“Starknet 已抗量子”和“Starknet 将在 2027 年成为 PQ L1”这两种说法，目前都没有一手证据支持。

R

局限与开放问题

  • 没有复跑：本机没有 scarb / snforge，Falcon 成本取自仓库基准，没有本地复跑。
  • Falcon 成本差异：主网 receipt（6,393 万 L2 gas）与 devnet 同一变体（约 1.399 亿）相差约一倍，原因未查明。演示账户的 class 也没能和构建产物比对（v0.14.4 下线了 feeder 的 get_class_hash_at）。
  • 主网与源码是否一致：隐私池、anonymizer 的链上 class 只核对了版本号 '2.1' 和 ABI，没有编译比对。sequencer 主干代码与主网实际运行的配置也可能不同（例如共识签名）。
  • 审计覆盖：审计 commit c5e2fb5 之后新增的代码（snip12 遗留签名路径、ComputeAndInvoke、anonymizer）没有公开审计。
  • 证明参数：主网区块证明的 S-two 用哪种 hash、多少安全位，以及私有交易证明何时进入 L1 结算，都没有找到一手证据。
  • 未核实：“S2morrow 2026-04-01 在主网投入生产”的原始出处（C62）；Ready App 默认 signer（A45）；共识认证密钥的曲线类型（R35）；钱包是否把 dapp_name 绑定到网站来源（W51）；“under ten cents”在 2.5 STRK 池费下的成立条件（S57）。
  • 官方材料自身的矛盾：谁生成证明（interactive 页、architecture 页、starkzap 三种说法）；筛查服务商（Elliptic 还是 FPI）；docs 的 Version Notes 只写到 v0.14.1。

U

术语表

原生账户native account
每个账户都是合约；协议调用它的 __validate__ 与 __execute__，签名算法由合约决定。不是 ERC-4337 那样在协议外的账户
Shor 算法Shor's algorithm
量子算法，能在多项式时间内解离散对数与大数分解，破坏 ECDSA、ECDH、Pedersen。不影响 hash 函数
Grover 算法Grover's algorithm
量子搜索算法，对 hash 原像搜索有平方级加速，可用加大参数应对。不是能破解 hash 的算法
HNDL先收集、后解密
harvest now, decrypt later：今天记录密文与公钥，等量子计算可行后再解密。不需要今天就有量子计算机
STARKScalable Transparent ARgument of Knowledge
只依赖 hash 的证明系统，证明一段计算按规则执行。Starknet 用 S-two 实现。不等于“被证明的程序抗量子”
PedersenPedersen hash
Stark 曲线点的线性组合取 x 坐标，安全性依赖离散对数。名字叫 hash，但不是 PQ
PoseidonPoseidon hash
面向证明系统的代数 hash（Hades 置换），Starknet 用于 v3 交易 hash、外层状态承诺、隐私池派生。官方没有给它 PQ 评级
BLAKE2sBLAKE2s-256
传统位运算 hash，路线图选它替换 Pedersen。与 Poseidon 不是同一类
Falcon-512FN-DSA（FIPS 206）
基于 NTRU 格的签名；公钥 897 字节，签名 666 字节。FIPS 206 尚未定稿
hash-to-point—
Falcon 把消息映射成多项式 c 的步骤；标准用 SHAKE-256。BLAKE2s / Poseidon 变体不与标准签名器互通
MV-PQminimum viable post-quantum
EF 在 J* 设置的备用里程碑，在 Q-day 后以较弱保证维持 Ethereum 运行。不是完整的 PQ 迁移
隐私池privacy pool
一个用 note 记账的合约，STRK20 的核心。不是独立的链
note票据
隐私池里的一笔余额记录，金额用通道密钥掩码。不是 UTXO 链的原生输出
nullifier作废标记
花掉 note 时写入的唯一值，由私钥派生，只能写一次。不等于 note_id
viewing key隐私私钥
STRK20 用户的 Stark 曲线私钥 k；用于解密、派生 nullifier 和 Shadow 身份。公钥上链，只能注册一次。不只是“只读钥匙”
auditor审计方
一个全局公钥；每个用户注册时，viewing 私钥用 ECDH 加密给它。能看，不能花。不是合约审计机构
ECDH椭圆曲线 Diffie-Hellman
双方用椭圆曲线算出同一个共享密钥；STRK20 用 Stark 曲线实现。不是 PQ 密钥封装
虚拟 OSvirtual Starknet OS
在链下运行的 Starknet OS，执行隐私池的私有逻辑并生成证明。不是另一条链
proof facts证明事实
证明附带的公开输出（程序哈希、基准区块、消息哈希），由网关和合约校验。不是证明本身
anonymizerShadowAccountAnonymizer
只接受隐私池调用的合约，负责部署和驱动 Shadow Account。不是混币器
Shadow Account影子账户
每个 (用户, anonymizer, dapp_name, nonce) 一个的无密钥代理合约，只隐藏与主钱包的关联。不是协议账户，没有私钥
PrimerPrimer 合约
固定 class 的占位合约；先按它算地址并部署，再换成 Shadow class。不是 Shadow 的运行时 class
