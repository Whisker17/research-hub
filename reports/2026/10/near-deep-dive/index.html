结论

共享的是账户、账本和 MPC，不是 VM
  • 架构：异步 receipt 让原子性只存在于单个合约内；Intents 用一个合约账本解决结算，用 MPC 和三座桥解决出入金（F1、F2、F5、F6）。

前置知识

B-0

账户与访问密钥（access key）

~4min
是什么

NEAR 账户是一个可读的名字，例如 alice.near。名字和密钥分开，一个账户可以挂多把 access key。key 分 FullAccess 和 FunctionCall key 两类 [1][3]。

为什么这里需要

本文的几个产品都建在这一层上。Chain Signatures 按调用账户派生外链地址；Intents 的 relayer 用一把 FunctionCall key 提交结算；NEAR AI 用账户签名登录。

最小例子
FunctionCall key = { receiver_id: "intents.near",
  method_names: ["execute_intents"], allowance: 无限 }
常见误解

误解：FunctionCall key 的 allowance 是资产额度。事实：它只限制 gas 费，key 也不能附带 NEAR [3]。

深入

[3] docs.near.org “Access Keys”

B-1

异步 receipt：跨合约调用不在同一笔交易里完成

~5min
是什么

交易先在签名者的分片变成一个 receipt。合约 A 调 B，会生成新的 receipt，在后面的区块执行；结果再通过 callback 回到 A [1][3]。

为什么这里需要

这决定了 NEAR 上的原子性边界。只有同一个 receipt 内的动作是原子的。B 失败时，A 已提交的状态不会回滚。

最小例子

A 在块 H+1 执行，B 在 H+2 执行，A 的 callback 在 H+3 执行（见 Fig 3）。

常见误解

误解：两个合约在同一个分片就是同步调用。事实：同分片也走 receipt，官方文档要求按“每个账户都在不同分片”来设计 [1]。

深入

[1] nearcore docs/architecture/how/cross-shard.md

依赖: B-0

B-2

分片与无状态验证（stateless validation）

~5min
是什么

状态按账户名区间切成多个 分片。每个分片的 chunk producer 持有状态，产出 chunk 和 state witness。被抽样的 chunk validator 不存状态，拿 witness 重新执行 [2]。

为什么这里需要

这解释了 NEAR 能加分片，也解释了它的限制：一个账户只能在一个分片里，热点合约拆不开。

最小例子

主网现在有 10 个分片，game.hot.tg 一个账户独占一个分片 [4]。

常见误解

误解：stateless validation 是 ZK 证明。事实：witness 是状态子集加包含证明，validator 要重新执行，不是简洁证明 [2]。

深入

[2] NEP-509

依赖: B-1

B-3

MPC 门限签名

~4min
是什么

一把私钥被拆成多个份额，分给多个节点。至少达到门限数量的节点合作，才能产出一个签名；单个节点拿不到完整私钥 [8]。

为什么这里需要

Chain Signatures 就是 NEAR 合约加一个 MPC 网络。NEAR 账户靠它控制 BTC、ETH 等外链地址；Omni 桥出金也靠它签名。

最小例子

主网 v1.signer：17 个参与者，门限 11 [4]。

常见误解

误解：NEAR 有几百个验证者，所以 MPC 也同样去中心化。事实：MPC 网络是另一组运营方，安全性看 11/17，不看 L1 验证者 [10]。

深入

[8] near/mpc README

依赖: B-0

B-4

TEE 与远程证明（attestation）

~4min
是什么

TEE 是 CPU 或 GPU 里的隔离执行环境，例如 Intel TDX。attestation 是硬件签发的报告，证明“这台机器在跑哪个镜像”[22]。

为什么这里需要

这些地方都依赖它：NEAR AI Cloud 机密推理、MPC 节点镜像校验、Confidential Intents 产品页所说的“TEE 桥”。

常见误解

误解：attestation 证明输出是对的。事实：它只证明环境和软件身份，不证明代码没有 bug，也依赖 Intel / NVIDIA 的信任根 [23]。

深入

[22] docs.near.ai “Gateway Attestation”

B-5

intent 与 solver

~4min
是什么

用户不签“调用哪个合约”，只签“我愿意付出什么、换到什么”。solver 报价并签对手方的那一半。双方签名一起交给 verifier 合约结算 [13]。

为什么这里需要

NEAR Intents 的 token_diff 就是这种签名。它让外链钱包不用开 NEAR 账户也能交易。

最小例子
{"intent":"token_diff",
 "diff":{"nep141:usdc…":"-1000","nep141:btc…":"0.0081"}}
常见误解

误解：intent 是让大模型理解自然语言。事实：它是一条带签名的结构化余额变化。

深入

[13] docs.near-intents.org “Intent types and execution”

依赖: B-0、B-1

L1 架构：异步、分片与验证

Fig 2 先给出全貌。NEAR 的产品不在同一个执行环境里。链上只有两个结算账本和一个 MPC 合约；推理、报价、私有链都在别处 [12][17][22]。

F1

三条叙事共用账户、一个合约账本和一个 MPC 网络，不共用执行环境

置信度: high
论断

公链上只有 intents.near、v1.signer 等合约；报价在链外 relay，私有成交在 FAR，推理在链外 TEE。每一层有自己的信任假设。

证据

observed verifier 与 far 构建 [12]（I1、I3、I58）；FAR 架构 [17]（I34）；MPC 合约状态 [4]（O7）；NEAR AI 推理不上链 [22]（N21）。inferred “共用三样东西”是对这些组件的归纳（O12）。

影响

不能用 NEAR L1 的安全性概括整个产品栈。每个产品要按它实际经过的组件评估。

异步执行是根本取舍。 Fig 3 用 A 调 B 的例子说明。A 在块 H+1 执行时，它的状态已经提交。B 在 H+2 执行，结果在 H+3 回到 A 的 callback [1][3]。只有同一个 receipt 里的动作是原子的；对同一个合约的 batch call 也算一个单元 [3]。

异步 receipt 让原子性只存在于单个合约里，Intents 因此把余额集中到一个账本

置信度: high
论断

跨合约调用在不同区块执行，失败不回滚前序状态。execute_intents 在一个 receipt 内完成多方验签、记账和配平检查，任一失败整笔 panic。

证据

observed cross-shard.md、tx_receipts.md、docs 跨合约调用页 [1][3]（A16–A20）；verifier 源码 [12]（I8–I10）。inferred “集中余额是为了绕开异步”是推论，官方文档没有明说（I53）。

影响

在 NEAR 上做多步业务要写显式状态机和补偿逻辑；EVM 链没有这个约束。

分片：一个账户只能在一个分片里。 分片按账户名区间划分 [1]。Fig 4 是 2026-10-07 主网的真实布局 [4]。红框是只包含一个账户的分片：Aurora 和 HOT 的 game.hot.tg 各自独占一个。

边界是一步步加上去的 [1]：PV 64 加 tge-lockup.sweat（Sweat），PV 65 加 game.hot.tg（HOT），PV 75 加 game.hot.tg-0，让 HOT 合约独占一个分片，PV 76 加 earn.kaiching（KaiChing）。nearcore 1.39 还为 sweat 和 kaiching 合约写了专门的 prefetcher [1]。

动态 resharding 在 nearcore 2.13 稳定 [1]。当前布局的 last_split 是分片 5，新边界 wallet.ka 不在任何静态布局里。所以主网已经自动拆过一次（9 → 10），并碰到了上限 10 [4]。

置信度: high
论断

拆分边界是账户名，一个账户不能跨分片。HOT 的游戏合约从 PV 75 起独占一个分片；动态拆分已从 9 拆到 10，上限是 10。

“加分片”只帮到能分散到多个账户的负载。intents.near 这种单合约账本，吞吐受单个分片限制（I54）。

验证：重新执行，不是证明。 Fig 5 是 stateless validation 的角色分工 [2]。block producer 不再跟踪分片，只收 endorsement。chunk 必须拿到“分配给该分片的 stake”的 2/3 以上才能进块。

链抽象层：一个 MPC 网络，三种用途

Chain Signatures 是一个 NEAR 合约（主网 v1.signer）加一个链外 MPC 网络 [8][9]。Fig 6 是一次签名的完整时序。合约用 yield/resume 把请求挂起，最多等 200 个区块 [8]。MPC 节点算出签名后调用 respond，合约先用派生公钥验签，再把签名还给调用者 [8]。

外链地址按“调用账户 + path”加法派生 [8]：

请求本身很小：一个 path、一个待签哈希、一个 domain（README 示例）[8]：

派生绑定的是直接调用 v1.signer 的账户。所以一个策略合约去调用时，外链地址归这个合约控制，不归最初签交易的人 [8]。签名请求要附 1 yoctoNEAR，目的是强制使用 FullAccess key，防止恶意前端用受限 key 静默发请求 [8]。

同一个网络现在有 4 个 domain [4]：

domain 协议 用途 主网调用方（示例）
0 CaitSith（secp256k1） 签名 钱包、Omni 出金
1 FROST（Ed25519） 签名 tx-bench.near 等
2 CKD（BLS12-381） CKD outlayer-admin.near
3 CaitSith 外链交易验证 mpc-prover.bridge.near

domain 3 让 MPC 节点去外链查交易，再对查到的结果做门限签名。它的安全性来自“至少 11 个节点各自查询自己配置的 RPC 并得到一致结果”，不是 light client [8]。

F5

一个 MPC 网络在主网同时做签名、密钥派生和外链验证；“只能 outbound”已经过时

置信度: high
论断

v1.signer 有 4 个 domain，门限都是 11/17。Omni 的 Aptos / Starknet 路由已在调用 verify_foreign_transaction。17 个运营方里 13 个提交了真实 TDX attestation，4 个没有。

证据

observed 主网 RPC 合约状态 [4]（O7）；nearblocks 交易记录 [10]（C20、C21、C33、C45）；mpc 源码 [8]（C32、C35）。inferred docs.near.org 的“8 nodes”“one way”已过时（C22、C34）。

影响

用 Chain Signatures 的产品要按“11/17 门限 + TEE + 外链 RPC”评估信任，不能用 L1 验证者数量代替。

把协议改动按“谁提出的动机”分三类 [1][2]。Fig 12 左边两组由产品拉动，右边一组由协议自身的目标推动。

Q

对 Mantle 的意义

前提：Mantle 是 OP Stack 系 rollup，状态由 OP Succinct 有效性证明验证，gas 代币是 MNT，执行层是同步 EVM [33]。下面的建议都是推论，不是路线承诺。

F13

NEAR Intents 目前不支持 Mantle；接入门槛在需求和流动性，不在技术

置信度: high
论断

1Click 的 204 个资产分布在 37 条链上，没有 Mantle。新链评估看用户需求、技术兼容、流动性和审计，优先考虑已有做市商流动性和兼容的签名标准。

证据

observed 1Click /v0/tokens 与 chain-support 页 [32]（O8、O9）。inferred Mantle 是 EVM 链，erc191 签名已支持，所以门槛主要在需求与做市商（O10）。

影响

在自建 solver 网络之前，先争取被现有 intent 网络接入，成本低得多。

按可执行程度排序：

  1. 把能力包装成被分发的服务接口。 目标场景是“从任何链、任何钱包买到 Mantle 核心资产（例如代币化股票）”。把它做成报价 API，交给钱包和聚合器分发。NEAR 的收入来自这一层，不来自 gas（F9，O14）。
  2. 先接入现成网络，再决定自建。 先争取 NEAR Intents 或同类网络支持 Mantle，用真实订单验证需求（F13）。
  3. 不要照搬托管账本。 NEAR 把余额集中进一个合约，是为了在异步模型下得到原子结算。Mantle 的 JIT 路由已经能在一笔交易内读状态、重算、执行；照搬只会多出存入、提现、桥和升级权限的风险（F2，O15）。
  4. 隐私先做 RFQ 层（推测）。 先验证“订单成交前不暴露、maker 报价不泄露”的需求。确实要隐藏余额时，再评估私有 L3，并把运营方权限和退出路径写清楚（F7，O16）。
  5. agent 先做受限执行与支付（推测）。 链能提供的是额度、收款方、目标合约、撤销这些授权约束，以及结算（F8，O17）。
  6. 账户数不等于需求。 用非激励的重复交易、含全部费用的成交价、退款尾延迟、渠道收入做核心指标（F10，O18）。
  7. 按接口审计组合系统。 桥、结算合约和链下服务组合成一个产品时，接口是最大的风险点（F12）。
CAUTION

NEAR 的分片和异步执行是为横向扩展付出的代价，不是产品优势本身。Mantle 的核心交易路径依赖同笔交易内的原子性；不要为了“intent”这个名字放弃它。

按账户名区间划分的状态分区。一个账户只能在一个分片里。
chunk分片块
一个分片在一个区块里的交易与 receipt 集合。
chunk producer分片出块者
持有分片状态、产出 chunk 和 state witness 的验证者。
chunk validator分片验证者
不存状态、按 stake 抽样分配，用 witness 重新执行并签 endorsement 的验证者。
state witness状态见证
执行一个 chunk 所需的状态子集加包含证明。不是 validity proof
stateless validation无状态验证
NEP-509 的验证方式：抽样的 validator 拿 witness 重新执行，2/3 分片 stake 背书后 chunk 才能进块。
dynamic resharding动态分片
分片内存超过阈值时，在 epoch 边界自动拆分。主网上限目前是 10 个分片。
congestion control拥塞控制
目标分片拥塞时限制新交易和发往它的 receipt，防止队列无限增长。
yield/resume挂起与恢复
合约挂起一个回调，等链外结果到达再恢复；最多等 200 个区块。
global contract全局合约
部署一次、多个账户引用的合约代码。可以按 hash（不可变）或按账户（可升级）引用。
storage staking存储质押
按状态字节锁定 NEAR，主网是每 100 KB 锁 1 NEAR。
PV协议版本
NEAR 的协议版本号，主网当前为 86。代码里的特性版本号不等于主网激活版本。
SPICE共识与执行分离
Near One 正在研究的架构：链只排序，执行和数据分发异步推进。代码里还不在 nightly。不是现状
Chain Signatures链签名
NEAR 合约 v1.signer 加 MPC 网络，让 NEAR 账户控制其他链的地址。不是跨链桥本身
MPC多方计算
多个节点各持私钥份额，达到门限才能合作产出签名。主网门限 11/17。
domain签名域
MPC 合约里的一组根密钥及其用途。主网有 4 个：两个签名、CKD、外链交易验证。
CKD机密密钥派生
MPC 网络给 TEE 应用派生确定性密钥，并加密返回。MPC 合约本身不检查 TEE。
foreign-tx外链交易验证
MPC 节点查询外链交易，再对查询结果做门限签名。信任 RPC 一致性，不是 light client。
TEE可信执行环境
CPU 或 GPU 里的隔离环境，外部包括运营方无法读写其中的内存。
TDXIntel Trust Domain Extensions
Intel 的虚拟机级 TEE，NEAR AI 和 MPC 节点都用它。
attestation远程证明
硬件签发的报告，证明机器运行的镜像和配置。不证明输出正确
verifier验证合约
NEAR Intents 的结算合约 intents.near，一个多资产账本。
token_diff余额变化 intent
签名者声明自己各 token 余额的增减。对手方签相反的一份，合约检查配平。
solver求解者
报价并提供对手方流动性的做市方。链上不设白名单，链下 relay 需要 JWT 与 KYC。
Message Bus消息总线
链外 RFQ 中继：广播报价请求、收集 solver 签名、打包提交结算。
1Click一键 API
把报价、入金、结算、出金、退款包成一个 HTTP API 的分发接口。
relayer key中继密钥
intents.near 账户上只能调用 execute_intents 的 FunctionCall key。
Omni BridgeOmni 桥
Near One 运营的桥。入站用 light client 或 Wormhole，出站用 NEAR MPC 签名。
PoA Bridge权威证明桥
中心化运营方负责铸造与外链放款的桥，只有 owner 能 mint。
HOT BridgeHOT 桥
HOT Protocol 的桥，用它自己的 MPC 验证者签署出入金证明。
FAR私有 NEAR 分叉
Confidential Intents 用的许可制 NEAR 实例，没有公网 P2P，RPC 需认证。
IMTIntents 多资产代币
FAR 上的私有资产，形如 imt:<Treasury>:nep141:<token>，由公链 Treasury 1:1 托管。
shield屏蔽
把公链资产转进 Treasury，并在 FAR 上铸造等额 IMT。反向操作叫 unshield。
SHIELDIntents 安全层
Intents / 1Click 的事件与策略服务，可按规则延迟可疑报价。不是 shield 操作
NEP-413链下签名消息标准
NEAR 钱包签名任意消息的标准，Intents 和 NEAR AI 登录都用它。
Incognito匿名转发路由
NEAR AI Cloud 把请求转发给 OpenAI 等第三方模型的路由。模型不在 TEE 里。
IronClawagent runtime
NEAR AI 的 Rust agent 运行时，用 WASM 沙箱和能力授权约束工具调用。
Shade Agents影子 agent 框架
TEE agent 加链上合约验证加 Chain Signatures 的框架，2026-04-19 起不再维护。
Agent Marketagent 市场
NEAR AI 的任务市场，经 Intents 结算，2026-05 起支持私有 USDC。
