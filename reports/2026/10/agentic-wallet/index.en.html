Agentic Wallets: Product Design, Technical Principles & Where Agents Can Act

Most agent wallets are a separate budget wallet with off-chain vendor policy. Verifiable on-chain limits exist only on the smart-account path, and real paid demand is still small.

Bottom line: most agent wallets today are "a separate budget wallet plus off-chain vendor policy". The key sits in a TEE or MPC setup, and the vendor's server enforces the limits. "Confirm every action" is mostly a skill rule that the agent follows by itself (F1, F2). Verifiable on-chain limits appear only on the smart account path.

Your five assumptions point the right way, but three need a rewrite. The real risk is signing power with no bounds, not key visibility. A spending limit is not a loss cap. An on-chain identity does not make an agent a first-class citizen (F3–F6).

Real paid demand is still small: x402 moves about $44K per day across all networks (F7). Mantle already has most chain-level parts; it lacks a production x402 settlement path and wallet-side coverage (F10).

H

Context

The problem: an agent that takes part in the on-chain economy must sign and pay. Giving it the private key is too risky. Asking a human to confirm every action removes the reason to use an agent.

Every agent wallet answers one question: how much power to give, and which layer enforces the limit.

Why now:

  • From February to August 2026, Coinbase, OKX, Binance and MetaMask each shipped an agent wallet (see E) [7][15][16][20].
  • The MetaMask post you shared dates to about 2026-10-14. It announces Agent Wallet going live on a bot; it is not the launch post [7].
  • BNB Chain bundles wallet, deployment, payments and identity in Agent Studio. From v2, agents can get paid [23].

Scope: product design, technical principles and limits of the big four; the wider ecosystem on the same dimensions; the protocols around the wallet; use cases; Mantle implications.

Non-goals: tests with real funds and security audits; investment advice; field-by-field protocol details.

Running example (illustrative, not a real product setting): a research agent spends at most 10 USDC per day on paid data APIs. It pays per request with x402. Each panel first shows how this payment flows in a given product.

I

Background

B-0

Trusted execution environment (TEE)

~5min
What it is

An isolated execution area inside the CPU. Keys are created and used inside it, and the host system and its operators cannot read them.

Why it matters here

MetaMask server-wallet, Coinbase, OKX and Phantom keep agent wallet keys in a TEE. The agent only holds a credential that asks for signatures.

Minimal example
agent → wallet service: sign(tx)
TEE: check policy → sign with the inner key → return the signature
the agent never sees the private key
Common misconception

Myth: a key in a TEE makes the agent safe. Fact: the TEE protects only the key. Policy decides which signatures the agent can get.

Go deeper

[32] Privy Policies docs, "Policy evaluation"

B-1

Threshold signing (MPC)

~l2
What it is

The private key is split into shares on different machines. The parties sign together, and no single place ever rebuilds the full key.

Why it matters here

Binance Agentic Wallet uses an MPC keyless design, with its rules enforced at the Binance API layer.

Go deeper

[17] Binance developer docs, Welcome page, "MPC Keyless Security"

B-2

Smart accounts and session keys

~8min
What it is

A smart account is a contract account whose signature rules live in code. A session key is a temporary key issued by the owner. The owner can limit it to listed contracts and functions, a cap and an expiry. Calls outside those limits revert on chain.

Why it matters here

Only this path keeps policy on chain, where it still holds if the vendor goes away. EIP-7702 lets an EOA delegate to contract code; ERC-4337 adds a paymaster that pays gas.

Minimal example
session = { calls: [Router.swap], spend: 100 USDC/day, expiry: 30 days }
agent calls Vault.withdraw → validation fails → revert
Common misconception

Myth: a session key is safe by default. Fact: with no calls list, an Altana session can call any contract within its spending cap.

Go deeper

[26] Altana Sessions docs

B-3

Signed approvals: Permit2 and EIP-3009

~6min
What it is

You sign one off-chain message instead of sending a transaction, and someone else gets the power to spend. Permit2 lets a third party pull tokens from your address. EIP-3009 authorizes one transfer of a set amount, and anyone can submit it while it is valid.

Why it matters here

Many wallets count only sent transactions against the limit, not signed approvals. MetaMask's limit does not count Permit2 signatures [3].

Minimal example
3009 authorization: from, to, value, validAfter, validBefore, nonce
after the agent is paused, this authorization can still be submitted in its window
to cancel it: cancelAuthorization, or wait for expiry
Common misconception

Myth: revoking the agent voids what it already signed. Fact: an off-chain signature ends only through an on-chain cancel or expiry.

Go deeper

[48] USDT0 docs, EIP-3009 section

Needs: B-0

B-4

x402 (pay per request over HTTP 402)

~6min
What it is

The server answers with HTTP 402 and a price. The client signs a payment authorization and sends the request again with it. A facilitator verifies the signature and settles on chain; it does not hold funds.

Why it matters here

This is the main path for agents to buy data and APIs. By default the server verifies first and settles later: it serves the resource, then collects payment [34].

Minimal example
GET /data → 402 { price: 0.01 USDC, payTo, network }
sign an EIP-3009 authorization → resend GET + PAYMENT header
→ 200 data; the facilitator settles on chain afterwards
Common misconception

Myth: x402 always takes payment before delivery. Fact: the default authorization flow settles after the server handler runs.

Go deeper

[34] x402 docs, Payment Schemes

Needs: B-3

B-5

MCP and skills

~l2
What it is

MCP is a protocol for agents to call external tools. A skill is a set of notes and scripts for the agent that says when to run which command and what to do first.

Why it matters here

Most agent wallets install their CLI through a skill. Many "confirm every action" rules live only in the skill, and the agent enforces them on itself.

Go deeper

[19] binance-skills-hub, Agentic Wallet SKILL.md

Checks on one action

Evidence for each layer in the figure:

  • Layer 2: MetaMask's rules ask the agent to show parameters and get a yes before a transfer, swap or x402 payment. This is a skill rule; the server forces 2FA only when an action breaks a limit or is flagged as risky [2][4]. When the OKX backend returns confirming, the skill says to rerun with --force only after the user agrees. A client that holds the session can skip that step [21].
  • Layer 3: MetaMask stores the Guard Mode allowlists and the rolling 24-hour outflow limit as YAML on the server wallet [2]. Binance enforces the daily limit and token scope at the API layer [17].
  • Layer 4: the Turnkey and Privy policy engines run inside an enclave and deny by default [27][32].
  • Layer 5: an Altana session that goes out of bounds reverts at validation time, with no off-chain trust assumption [26]. MetaMask Advanced Permissions use on-chain caveat enforcer contracts [9].

MetaMask Agent Wallet:

  • Two key modes. The server-wallet key sits in a server-side TEE. BYOK keeps the seed phrase in an environment variable and signs locally [1].
  • Guard Mode has threat scanning, network / address / recipient allowlists and a rolling 24-hour limit. Beast Mode keeps only threat scanning. Switching to Beast needs 2FA [2].
  • When native gas is short, ERC-20 transfers and swaps use an EIP-7702 relay that takes the fee from the token sent. On supported chains, ERC-7821 merges approve and trade into one call [1].
  • x402 runs through a script in the skill and supports only exact + EIP-3009. The script keeps no state, so a rerun pays again [6].
  • Export: the August launch post says you can export the seed phrase at any time; the October 8 guide says server-wallet export is not available yet [7][8].
  • Advanced Permissions is a different product. A dapp asks the MetaMask extension for permissions through ERC-7715, a session account redeems them through ERC-7710, and on-chain caveat enforcers apply the limits [9].

Coinbase / Base: three paths.

  • Agentic Wallet (separate budget wallet): the CLI can send USDC, trade on Base and pay x402. The MCP version can only find and pay for x402 services; it cannot send or trade [10][11]. MCP caps per call and per session are set only in the wallet UI, and the agent cannot change them [12].
  • Wallet MCP (formerly Base MCP): connects to the user's own Coinbase Wallet; the user approves every write action [14].
  • Spend Permissions: an on-chain contract that lets a spender use set tokens, up to a cap, per period. It differs from CDP Policies, which are off-chain rules in the Coinbase TEE [13].

Binance Agentic Wallet:

  • A separate keyless wallet under the Binance account, apart from the main MPC wallet. With Secure Auto Sign on, actions run without per-action prompts [16].
  • Security rules can be changed only in the Binance app; the agent can only read them. Pairing requires checking a 6-digit code and the request origin in the app [17].
  • Transfers can go only to address-book allowlist entries, and this cannot be turned off. Swap and transfer, DeFi, x402 and Developer Mode each have their own 24-hour limit, with no total cap [18].
  • Only Developer Mode opens arbitrary contract calls. Only the app can turn it on, and it expires. Its default limit is 1,000 USDT, and it cannot start when the wallet holds more than 10,000 USDT [17][18].

OKX Agentic Wallet:

  • The execution part of Onchain OS. Login by email, Google or Apple; keys are created and used inside a TEE; one wallet can derive up to 50 sub-wallets [20].
  • Broad default scope: contract-call accepts any calldata, and sign-message defaults to personalSign [21].
  • Only four policy rules: per-transaction limit, daily transfer limit, daily trade limit and a transfer allowlist, set by the user in the web portal [21].

BNB Agent Studio: not a wallet but a platform that bundles deployment, wallet, model payments (x402), identity (ERC-8004) and jobs (ERC-8183) [23].

  • Swappable wallet backends: a local keystore by default, plus TWAK (local encryption), Altana (on-chain session) and Turnkey (enclave policy) [23][24].
  • Signing is fixed code, not a tool the LLM can call. The MCP server in the IDE has read-only tools [24].

M

Findings

F1

The mainstream design is "separate budget wallet + off-chain vendor policy"

confidence: high
Claim

Each of the big four gives the agent a separate wallet. The vendor's server, API or TEE enforces limits and allowlists, or the layer is not disclosed. Limits enforced by an on-chain contract appear only on the smart-account path.

Evidence

observed MetaMask stores policy as YAML on the server wallet [2]; Binance applies rules at the API layer [17]; OKX policy is set in the web portal [21]. observed Altana reverts out-of-bounds calls [26]; Crossmint permissions are enforced by contract [30]; Coinbase Spend Permissions are on chain [13]. speculative Coinbase Agentic Wallet caps run on a server or in a TEE; the docs do not say.

Implication

To judge an agent wallet, ask first where its policy runs and whether it still holds if the vendor goes offline.

F2

"Confirm every action" is mostly a skill rule, not a server guarantee

confidence: high
Claim

Per-action confirmation mostly lives in the skill or tool layer, and the agent enforces it on itself. MetaMask and Binance also have documented server-side or app-side checks. OKX and Phantom expose different confirmation paths, and their server-side conditions are not fully disclosed.

Evidence

observed MetaMask rules require a yes first; the server forces 2FA past limits, on high risk, on limit increases and on policy changes [2][4]. observed The Binance skill says confirmation can be skipped "unless the user explicitly asks"; trades with a risk score of 4 or more go to the app for approval or are rejected [18][19]. inferred An OKX confirming response can be rerun with --force [21]. inferred Phantom's confirmed: true is only a parameter, and perps write tools submit on call [29].

Implication

An injected agent may bypass the skill layer. Count only documented server-side, enclave or on-chain checks in a safety argument (layers 3–5 in J).

F3

The risk is unbounded signing power, not seeing the key

confidence: high
Claim

Your assumption 1 points the right way but needs a rewrite. BYOK and TWAK keep the key on the agent's host, so any process that reads environment variables can sign. In the other direction, a custodial wallet with an empty policy is economically close to handing over the key.

Evidence

inferred MetaMask BYOK keeps the seed phrase in MM_MNEMONIC, with no server-side limit [1][2]. inferred The TWAK signing password can come from an environment variable [28]. observed Altana: "permissions.calls omitted = unrestricted" [26]. observed Turnkey: "Root users bypass the policy engine entirely" [27]. observed A Crossmint signer with no scope can spend tokens without limit [30].

Implication

Scope agent permissions by target contract, method, amount and expiry, and confirm the agent is not a root user.

F4

A spending limit is not a loss cap

confidence: high
Claim

Your assumption 2 needs one more line. Limits count only sent transactions; they leave out signed approvals and existing allowances. Pausing the agent does not void them either.

Evidence

observed MetaMask: Permit2 and other signatures are not counted; transactions not sent through its backend are tracked imprecisely; 10 USDC→ETH→DAI counts as two $10 outflows [3]. observed An EIP-3009 authorization can be submitted by anyone in its window and ends only through a cancel or expiry [48]. inferred OKX policy has no contract or approval dimension [21]. speculative OKX limits do not cover third-party transfers after an approval (a claim in the GPT source; the page needs a login and was not checked).

Implication

A shutdown procedure must cancel signed authorizations and revoke allowances, not only show "paused" in the UI.

F5

"Deterministic execution, less reasoning" is already common practice

confidence: medium
Claim

Your assumption 3 holds, and vendors already work this way: fixed code signs and validates, and the LLM only chooses and plans.

Evidence

observed BNB Agent Studio: signing is fixed code, not a tool the LLM can call [24]. observed AP2: validation for each role "MUST happen in deterministic code" [37]. observed The default x402 flow verifies and settles in code [34].

Implication

Give agents tools with clear meaning (quote, build, validate, submit, check status), not one "send any transaction" tool.

F6

An on-chain identity does not make an agent a first-class citizen

confidence: medium
Claim

Your assumption 4 needs to be concrete. ERC-8004 provides identity, reputation and validation registries. It does not handle payment, and it admits that reputation can be gamed. A first-class agent also needs a budget, income, revocation and audit. BNB Agent Studio lets agents get paid from v2.

Evidence

observed EIP-8004: "Payments are orthogonal"; Sybil attacks can inflate fake agents' reputation [35]. inferred Only 3%–15% of registrations carry a valid service endpoint [43]. observed 8004scan shows 819,538 agents, and the newest entries have zero feedback [43]. observed Agent Studio v2 lets agents be hired and paid [23].

Implication

Measure an agent ecosystem by paid jobs and income, not by registrations.

F7

Real paid demand is small, and transaction counts include heavy wash trading

confidence: high
Claim

Your assumption 5 (give agents room to act) points the right way, but the data does not support "demand has exploded". x402 moves about $44K per day, and 30-day transactions fell 46%. BNB Chain itself says application-level demand still has to be proven.

Evidence

observed Artemis (updated Oct 19): 101.7K txs, $44.2K, $0.40 average in 24 h; −45.88% over 30 days [42]. observed Artemis tracks "Real vs. Gamed Transactions" as a separate chart [42]. inferred A second-hand summary of the Artemis Dec 2025 report: about 48% of txs and 81% of value tie to gamed volume [42]. observed BNB Chain: "application-level demand … still has to be proven" [25]. observed None of the three exchange wallets publishes wallet-level usage [16][20].

Implication

Track independent paying users and repeat use, not wallet or transaction counts.

F8

Two design approaches: narrow by default, or broad by default plus policy

confidence: medium
Claim

Binance opens only verified operations by default, and Coinbase MCP can only pay x402. OKX allows any calldata by default, and MetaMask Beast Mode drops allowlists. Narrow scope costs generality: Binance cannot do SIWE login or airdrop claims.

Evidence

observed Binance does not start arbitrary transactions and allows only EIP-712 message signing [17]. observed Coinbase MCP cannot send or trade [10]. observed OKX contract-call accepts any calldata [21]. observed Beast Mode keeps only threat scanning [2].

Implication

Grant permissions per use case: an agent that only buys data needs no transfer or trading power.

F9

Four problems your list missed

confidence: high
Claim
  1. Prompt injection abuses permissions the agent already has, not only key theft. 2) Revocation does not void signed approvals (see F4). 3) Automations need a long-running process. 4) Payments can repeat: a stateless script pays again on a retry after timeout.
Evidence

observed Anthropic: 1.4% attack success with defenses, and "No browser agent is immune" [40]. observed OpenAI advises keeping tool approvals on for MCP tools and keeping untrusted data from driving agent behavior [41]. observed TWAK automations run only while the watcher runs [28]. observed The MetaMask x402 script keeps no state, and its rules allow one payment per resource [4][6]. observed x402 uses settlement_pending reconciliation to stop double charges [34].

Implication

Put "outside content cannot change policy or payee" into layers 3–5, and give each payment an idempotency key.

F10

Mantle has most chain-level parts; it lacks an x402 settlement path and wallet coverage

confidence: medium
Claim

7702 is live, 4337 has bundlers and paymasters, the ERC-8004 identity and reputation registries are deployed, and both USDC and USDT0 implement EIP-3009. The official x402 docs list no default asset or facilitator for Mantle. Among wallets, Coinbase, Binance and Phantom do not support Mantle; MetaMask does, without threat scanning.

Evidence

observed The Skadi upgrade brought EIP-7702 [44]; Pimlico supports EntryPoint V06–V09 on Mantle [45]; 8004 registry addresses [46]. observed The x402 default asset table and facilitator list have no Mantle entry [34]. observed Mantle USDC accepts only v,r,s signatures for 3009 [47]. observed MetaMask's Mantle row shows Transaction Shield = No [5].

Implication

See Mantle implications.

The protocol stack beyond the wallet

Protocol Covers Explicitly does not cover Status
x402 Price, payment authorization and settlement over HTTP 402 Identity, delivery quality v2
ERC-8004 Identity, reputation, validation registries Payment; Sybil-proof reputation Draft
ERC-8183 Job escrow, submission, evaluator decision, refund on expiry Dispute arbitration Draft
AP2 Purchase and payment mandates, plus receipts Dispute process; does not fix the payment method v0.2
ERC-7715 / 7710 Request permissions from a wallet / redeem and check on chain 7710 does not define how to request Draft
ERC-4337 / EIP-7702 Contract accounts, paymaster, 2D nonce / EOA delegation 7702 has no permissions at protocol level Final
  • x402 is not "pay first": the four schemes are exact, upto, batch-settlement and auth-capture. The default authorization flow verifies first and settles after the server handler runs. auth-capture holds funds in escrow, then captures or refunds after delivery [34].
  • ERC-8183 trusts the evaluator: it can complete or reject any job; the spec has no arbitration, and reject and expiry are final [36].
  • AP2 treats crypto as one payment method: the spec stays open on payment methods. With no human present, the user signs a constrained open mandate that must include the agent's public key [37].
  • MPP: co-authored by Stripe and Tempo; it also uses HTTP 402 and is not tied to one rail (stablecoins, cards and Lightning all work) [33].

Glossary

TEEtrusted execution environment
An isolated area inside the CPU where keys are created and used; the host system cannot read them.not the same as safe policy
MPCthreshold signing
The private key is split into shares on different machines that sign together; no single place can rebuild the full key.
smart accountcontract account
An account whose signature rules live in a contract, so it can reject transactions by rule.not an EOA
session key
A temporary key issued by the owner, usable only on set contracts and functions, within a cap and before an expiry.not the main key
EIP-7702EOA delegation
Lets an EOA delegate to contract code; the protocol itself has no permission system.
ERC-4337account abstraction
A contract-account design with no consensus change: EntryPoint, bundler, paymaster and 2D nonce.
paymastergas sponsor contract
An ERC-4337 contract that pays gas for the user and may charge an ERC-20 instead.
ERC-7579modular account standard
Defines module interfaces for contract accounts; Crossmint wallets use it.
ERC-1271contract signature check
A standard interface for contract accounts to validate signatures.not an ECDSA v,r,s signature
ERC-7715permission request
The wallet RPC wallet_requestExecutionPermissions, which dapps use to request permission to act for the user.
ERC-7710delegation redemption
The redeemDelegations interface: check the delegation, then execute for the delegator.
caveat enforcer
An on-chain contract in the MetaMask Delegation Framework that applies a limit and reverts when it fails.
EIP-3009transferWithAuthorization
One signed off-chain authorization moves a set amount; anyone can submit it while it is valid.revoking the agent does not void it
Permit2
Uniswap's approval contract; one signature hands token spending power to a third party.
x402HTTP 402 payments
A pay-per-request protocol: the server returns 402 and a price, and the client resends with a signed payment.
facilitator
The x402 service that verifies payments and settles them on chain for the server; it holds no funds.
Bazaarx402 service directory
Coinbase's directory for finding x402 services.
MPPMachine Payments Protocol
A 402 payment protocol by Stripe and Tempo that is not tied to one payment rail.
AP2Agent Payments Protocol
Uses checkout and payment mandates plus receipts to record purchase authority and dispute evidence.
ERC-8004trustless agents
Identity, reputation and validation registries; does not handle payment.not a trust certificate
ERC-8183job escrow
A state machine for job escrow, submission, evaluator decision and refund on expiry.
MCPModel Context Protocol
A protocol for agents to call external tools.
skillagent skill
Notes and scripts for the agent that say when to run which command.not a server-side limit
BYOKbring your own wallet
MetaMask's local signing mode: the user supplies a seed phrase in an environment variable.
Guard Mode
MetaMask's protective mode: threat scanning, network / address / recipient allowlists and a rolling 24-hour limit.
Beast Mode
MetaMask's open mode: threat scanning only, no allowlists or limits.
outflow limit
MetaMask's rolling 24-hour limit on simulated USD outflow; signed approvals are not counted.not a loss cap
Transaction Shield
MetaMask's threat scanning and transaction protection; not available on Mantle.
Secure Auto Sign
Binance's service that runs actions without per-action prompts after one approval.
Developer Mode
Binance's controlled exception that opens arbitrary contract calls; app-only, with its own limit and an expiry.
Onchain OS
OKX's data and trading tool platform; Agentic Wallet is its execution part.
TWAKTrust Wallet Agent Kit
Trust Wallet's agent CLI, which creates and encrypts the wallet locally.
KYTknow your transaction
Transaction risk screening; Coinbase blocks flagged transfers before they reach the chain.
root userTurnkey root
A Turnkey user that bypasses the policy engine; an agent must not be one.
Prompt injection
Instructions hidden in outside content that push the agent into actions the user did not ask for.
wash trading
Trading with yourself to create fake volume.
