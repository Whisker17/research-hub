公链 PQ 实践与分层演进对比

“支持抗量子”在公链技术语境中存在四层不同的防御边界：账户授权、状态证明、共识身份与隐私通信。账户授权具备 PQ 能力，绝不意味着整条链已抗量子（台账 #1, #3, #5）。

下图中展示了 Algorand 历时数年的抗量子落地路径与 Mantle 推荐工程路线的映射关系：

F1

Algorand 演进经验：先做可编程验签，再做原生账户

置信度: high
论断

Algorand 采取了“State Proofs 跨链边界 (Falcon-1024) → LogicSig 合约验签 (AVM FALCON_VERIFY) → v5.0.0 原生账户 (Falcon-1024)”的三阶段演进路径。其主网共识消息仍使用 Ed25519，VRF 仍依赖椭圆曲线。

证据

observed Algorand Technical Brief: Quantum-Resistant Transactions on Algorand with Falcon Signatures；Algorand v5.0.0 Release Notes（台账 #1, #2, #3）。

影响

证明了“无需等待全链共识修改，先给预编译再做智能合约账户”是完全行得通的工程解法；“原生 PQ 账户上线”与“全链已抗量子”必须严格区分。

Starknet 依托原生账户抽象（Native Account Abstraction），所有账户天生即为智能合约。社区已在主网完成 Falcon-512 实验性账户交易，验证逻辑直接写在 Cairo 合约中，其底层的 STARK 证明系统纯基于哈希，天然具备抗量子特性（台账 #4, #5）。这印证了解耦账户模型能赋予生态极高的密码学敏捷性。

F2

Starknet 原生 AA 赋予了极高的密码学敏捷性

置信度: high
论断

Starknet 原生 AA 允许用户在 Cairo 合约中直接实现并测试 Falcon-512 验签逻辑，无需共识硬分叉。其底层 STARK 证明系统基于哈希天然抗量子，但 L1 结算仍依赖以太坊共识。

证据

observed Starknet Blog: Quantum Resistance on Starknet；OpenZeppelin cairo-pq-verifiers 仓库（台账 #4, #5）。

影响

合约化账户将签名验证与交易协议层解耦；Mantle 依托 ERC-4337 能够复现同等的密码学敏捷性，避免把所有算法逻辑绑死在协议层。

反观 Solana 生态，社区项目（如 Winterwallet）曾尝试基于 Winternitz 一次性签名（WOTS）构建抗量子金库（台账 #6）。WOTS 与 XMSS/LMS 属于有状态哈希签名（Stateful Hash-Based Signatures），存在不可调和的工程缺陷：私钥索引绝不能被重复使用。一旦在网络异步、多设备登录、钱包重试或链回滚时针对两条不同消息使用了同一私钥索引，攻击者就能瞬间反解出完整私钥并转移所有资产（台账 #7）。

F3

有状态哈希签名存在致命的状态回滚与重用隐患

置信度: high
论断

WOTS、XMSS 等有状态哈希签名若在重试、回滚或多设备上重复使用同一私钥索引，会导致私钥立即泄露。Solana Winterwallet 等应用级尝试均对密钥重用发出严重警告。

证据

observed NIST SP 800-208 规范；Solana Winterwallet Security Documentation（台账 #6, #7）。

影响

Mantle 无论在协议层还是账户层，严禁引入有状态哈希签名作为默认机构方案，必须坚持使用无状态算法（ML-DSA 或 Falcon）。

I

PQ 签名算法候选深度评估

在抗量子密码学体系中，必须严格区分密钥封装（KEM）与数字签名（DSA）。NIST FIPS 203 标准化的 ML-KEM（Kyber）专门用于建立会话共享密钥以防范“先收集后解密（HNDL）”，根本无法用于区块链交易签名（台账 #8）。替代 ECDSA 的只能是数字签名算法。

F4

数字签名是唯一正确的账户候选；FIPS 204 是核心基准

置信度: high
论断

NIST FIPS 203 为 ML-KEM（密钥封装），仅用于密钥协商，不能用于交易签名；FIPS 204（ML-DSA）与 FIPS 205（SLH-DSA）才是数字签名标准；Falcon 对应的 FIPS 206 仍在制定中。

证据

observed NIST FIPS 203、FIPS 204、FIPS 205 官方发布文本；NIST CSRC PQC 标准化进程文档（台账 #8, #9, #10, #11）。

影响

方案设计必须彻底排除 KEM 类算法；所有研发资源应当聚焦在标准数字签名算法的验签与工程接入上。

在数字签名候选算法中，Mantle 短期的最优工程基准是 ML-DSA-65：

  • 标准完全冻结：NIST FIPS 204 于 2024 年 8 月正式发布，参数、编码与上下文规范已完全敲定，不存在后续分叉修改算法规范的向后兼容风险（台账 #9）。
  • 机构级 HSM 硬件支持：AWS KMS 已正式支持 ML-DSA-44/65/87 在 HSM 内部直接生成私钥与出签（台账 #16）。对于机构储备与大资金托管，私钥不出硬件安全模块是硬性合规底线。
  • 纯整数算术与确定性：基于模格（Module-LWE），全部为模数 q=8380417 的模整数运算，无浮点数陷阱，多语言与 zkVM 移植成本极低。
F5

ML-DSA-65 应当作为 Mantle 机构账户的首选基准

置信度: high
论断

ML-DSA-65（FIPS 204，NIST Category 3）标准已正式冻结，且已获得 AWS KMS 等企业级硬件模块原生支持，安全余量对标 AES-192，是机构长期冷储备资产的最优工程基准。

证据

observed NIST FIPS 204 规范；AWS KMS 官方开发指南关于 PQC 的支持文档；inferred 机构资金合规底线要求 HSM 支持，标准稳定性高于节省带宽（台账 #12, #16, #39, #48）。

影响

Mantle 第一版预编译应锁定 FIPS 204 ML-DSA-65 档案；这能让机构客户无需等待自研硬件，直接复用成熟的云端 KMS 资产管理流。

Falcon-512 的主要吸引力在于其签名极小（仅 ~666 字节，公钥 897 字节，台账 #13）。但必须看到其工程制约：

  1. FIPS 206 仍在制定中：Thomas Pornin 等原作者明确警告，在最终标准发布前，不能保证编码向后兼容（台账 #11）；
  2. 签名端采样算法极度复杂：Falcon 基于 NTRU 格与陷门高斯采样（Fast Fourier Sampling），防侧信道防护与硬件化极度困难，主流 HSM 硬件对其原生支持预计滞后 ML-DSA 2–3 年（台账 #48）。 不过，Falcon 的验签过程完全是确定性的，不需要浮点数运算，不存在共识不确定性（台账 #15）。因此，Falcon 应作为备用对照方案，待 FIPS 206 正式定稿后再评估是否扩展支持。
F6

Falcon-512 签名小但标准未定，可作轻量对照

置信度: high
论断

Falcon-512 签名紧凑（约 666 字节）且验签完全确定性无浮点运算；但其对应的 FIPS 206 标准尚未敲定，签名端采样复杂且缺乏通用 HSM 支持。

证据

observed Falcon 算法技术规范；algorand/falcon 源码与 Thomas Pornin 实现警告（台账 #13, #15, #48）。

影响

不建议 Mantle 第一版将所有押注放在 Falcon 上，但可以将其作为基准测试对照组，待标准敲定后引入第二预编译。

活跃开源密码学工程库调研与共识一致性警示

密码学库的选择不仅关乎速度，更关乎区块链共识的死生。历史常用的基准库 PQClean 已于 2026 年 8 月正式归档，其 README 明确建议开发者迁移至由 Linux 基金会后量子密码学联盟（PQCA）主导的 PQ Code Package（台账 #20）。

当前可直接用于 Mantle 客户端工程调研的核心库评估如下：

  • mldsa-native (PQCA / Linux Foundation)：C90 标准实现，包含 CBMC 形式化验证与针对 AArch64/x86-64 的汇编加速，覆盖内存安全与无定时泄露测试。极其适合作为跨客户端对比的标准参考实现（台账 #17）。
  • Cloudflare CIRCL (sign/mldsa)：纯 Go 语言实现，并附带针对 AVX2/NEON 的性能优化汇编，接口清晰。极其适合直接集成进 op-geth 的预编译注册模块中（台账 #18）。
  • RustCrypto signatures/ml-dsa：纯 Rust 实现，无 unsafe 代码。完全适配 Kona 以及在 SP1 zkVM RISC-V 目标架构下的编译（台账 #19）。
F7

PQCA mldsa-native 与 Cloudflare CIRCL 是最佳工程参考

置信度: high
论断

PQClean 于 2026 年 8 月归档，不再作为活跃上游；Linux 基金会 PQCA 的 mldsa-native 提供了经形式化验证的 C 参考实现；Cloudflare CIRCL 提供了适合 op-geth 的高质量 Go 实现。

证据

observed PQClean GitHub 归档声明；PQCA 官方公告；Cloudflare CIRCL 源码仓库（台账 #17, #18, #20）。

影响

Mantle 执行端无需从头造轮子，可直接采用 CIRCL 接入 op-geth，并以 mldsa-native 作为自动化交叉测试的标准基准。

在引入第三方密码学库时，必须极度警惕边缘情况下的共识分歧。RustCrypto ml-dsa 在 2026 年曾爆出 CVE-2026-24850（GHSA-5x2r-hc65-25f9） 漏洞：在版本 0.0.4 中，代码将检查提示向量（hint）索引严格单调递增的严格小于号（<）误改成了小于等于号（<=），导致库能够接受包含重复 hint 索引的畸形签名，直到 0.1.0-rc.4 才被修复（台账 #19）。在传统互联网应用中，这只是轻微的签名可塑性（malleability）问题；但在区块链网络中，如果出块节点使用 CIRCL 拒绝了这笔交易，而某个运行 Rust 客户端的验证节点或证明器接受了这笔交易，就会直接导致区块链共识分裂（Chain Split）或证明生成失败！

F8

密码学库细微边界差异可引发灾难性共识分歧

置信度: high
论断

RustCrypto ml-dsa 曾因 hint 索引单调性检查符号误改（< 变 <=）导致接受含重复 hint 的畸形签名（CVE-2026-24850），该差异若跨客户端并存将直接引发链分叉或证明失败。

证据

observed GitHub 安全公告 GHSA-5x2r-hc65-25f9；CVE-2026-24850 记录（台账 #19）。

影响

必须对 op-geth (Go) 与 Kona (Rust) 进行全方位的差分模糊测试（Differential Fuzzing），并确保 Rust 侧依赖严格锁定在 ≥ 0.1.0-rc.4。

K

Mantle 最小实现：预编译设计边界

为什么 Mantle 应当提供无状态的独立签名验签预编译，而不是通用 NTT 多项式数学原语？

F9

专用签名验签预编译是收敛审计边界的唯一合理选择

置信度: high
论断

专用签名验签预编译将多项式算术、拒绝采样与范数约束完整封装在客户端底层，智能合约仅需校验验签布尔结果；通用 NTT 原语会把致命的密码学组装责任推给应用合约。

证据

inferred 密码学 API 设计原则；EIP-8355 规范设计理念（台账 #37）。

影响

Mantle 严禁在第一期尝试通用数学算子，必须提供端到端原子化的 ML-DSA 验签接口。

纯智能合约验签不可行：Fireblocks 的实验性 ML-DSA-44 EVM 验签器在纯 EVM 字节码下单次验签消耗高达 1,230,000 gas（台账 #21）。而根据以太坊标准 ERC-7562（账户抽象内存池验证规则），单个 UserOperation 在验证阶段允许消耗的 gas 上限严格为 500,000，且 UserOp 序列化后最大字节不能超过 8,192 字节（台账 #22）。这意味着纯合约方案不仅极其昂贵，而且根本无法被标准 ERC-4337 Bundler 接收和打包（台账 #42）！

F10

纯 EVM 合约验签受限于 ERC-7562 规则，无法进入公共内存池

置信度: high
论断

Fireblocks ML-DSA-44 EVM 验签器消耗约 1.23M gas，远超 ERC-7562 规定的 500k 验证 gas 上限；加上 ML-DSA-65 签名体积，纯合约验证无法通过标准 Bundler 内存池。

证据

observed Fireblocks evm-ml-dsa-verifier 基准报告；ERC-7562 验证规范（台账 #21, #22, #42）。

影响

必须由底层协议引入原生预编译，将 gas 降至数万水平，才能让 PQ 智能账户在 ERC-4337 基础设施中顺畅流转。

预编译规范与 Fail-Closed 原则

预编译合约的接口设计可借鉴 Danno Ferrin 提出的 EIP-8355 草案规范：

  • 输入编码：public_key (1952 B) || signature (3309 B) || message (32 B digest)
  • 输出：32 字节。成功返回 0x00...01，失败返回 0x00...00。
  • Fail-Closed 编程规范：调用预编译必须使用 staticcall。在以太坊虚拟机中，调用一个没有代码也没有激活预编译的地址，staticcall 同样会成功返回空数据（returndatasize == 0）！因此，智能合约必须严格执行校验：
    (bool success, bytes memory data) = PQ_PRECOMPILE.staticcall(payload);
require(success && data.length == 32 && abi.decode(data, (uint256)) == 1, "PQ verification failed");
    缺少长度与值检查的合约会在预编译未激活时产生致命的假阳性放行漏洞（台账 #28）。
F11

预编译调用必须严格遵循 Fail-Closed 原则，防范空地址假阳性

置信度: high
论断

EIP-8355 规范采用输入拼接与 32 字节返回值；调用方合约必须严格校验执行成功、返回长度恰好为 32 字节且值为 1，避免调用空地址时静默放行。

证据

observed EIP-8355 草案文本；EVM 空地址执行特性（台账 #28）。

影响

智能账户 SDK 与官方验证器模块必须由 Mantle 核心团队统一提供经过审计的模板代码，严禁开发者随意自写未加防御的 staticcall。

全栈一致性：从 op-geth 到 OP Succinct (Kona / SP1)

Mantle 的主网状态证明已经接入了 OP Succinct 架构。这意味着 Mantle 绝不能只在 op-geth 里增加一个预编译，而必须完成全栈双端等价工程（台账 #31, #33）。

F12

Mantle 预编译必须在 Go (op-geth) 与 Rust (Kona) 双端完全等价

置信度: high
论断

Mantle 已部署 OP Succinct，其状态转换由 Kona 运行在 SP1 zkVM 中；执行端 op-geth (Go) 与证明端 Kona (Rust) 必须对预编译输入、错误处理和 gas 产生完全一致的行为。

证据

observed blog.succinct.xyz 关于 Mantle OP Succinct 的官方案例报告；Kona 架构文档（台账 #31, #33）。

影响

预编译的开发必须作为包含 Go 与 Rust 双实现的联合工程，任何单端上线都会直接导致生成证明失败，使整个 Rollup 停摆。

很多工程师容易混淆两种“预编译”：

  • EVM 预编译：智能合约通过字节码 STATICCALL 调用的功能扩展。
  • SP1 内部电路预编译（Core Circuit Precompile）：Succinct SP1 为了加速特定耗时哈希（Keccak-f1600）或曲线配对而在 RISC-V 虚拟机底层构建的专用 ZK 证明约束电路（台账 #32）。 初期无需定制 SP1 电路预编译：在第一阶段，Kona 内部直接以纯 Rust 软件运行 ml-dsa。虽然在 RISC-V 中验证 ML-DSA-65 会消耗数百万周期，但机构储备资金调用频率极低（每天数笔到数十笔），对整个区块数亿周期的证明总预算影响微乎其微。只有当 PQ 交易量占单日区块 Gas 比例超过 5% 时，为 SP1 专门开发硬件约束电路级 PQ 预编译才具有成本正收益（台账 #45, #49）。
F13

EVM 预编译不同于 SP1 电路预编译，初期纯软件证明完全够用

置信度: high
论断

EVM 合约预编译与 SP1 zkVM 底层约束电路预编译不同；低频机构金库调用下，Kona 内部纯 Rust 软件验签足以满足需求，初期无需定制昂贵的 SP1 专用电路约束。

证据

observed Succinct SP1 预编译开发规范；inferred 机构金库调用频次与 ZK 证明周期开销分析（台账 #32, #45, #49）。

影响

极大地降低了第一阶段的工程复杂度和上线门槛，避开了定制 ZK-SNARK 约束电路这一高风险环节。

M

适配 Mantle“双硬分叉”：Rebase 隔离策略

以太坊 L1 通常每年进行一次重大硬分叉。针对每次升级，Mantle 团队在工程实践中执行两次硬分叉：

  • 第一次分叉（兼容性分叉）：与 L1 升级严格同步，调整区块派生规则与引擎 API，确保 Rollup 节点不与 L1 脱节，防止链 halt；
  • 第二次分叉（特性引入分叉）：滞后一段时间，将 L1 新特性（新操作码、新系统预编译）引入 Mantle（台账 #34）。

在这一节奏下，自定义预编译必须防范三大升级陷阱：

  1. 地址冲突（Address Collision）：以太坊社区同时存在 EIP-8355 与 EIP-8051 等草案，分别建议使用 0x12 或 0x13（台账 #29）。如果 Mantle 盲目抢用 0x12，当以太坊在后续硬分叉中把 0x12 分配给其他功能时，Mantle 的状态机就会彻底陷入与上游冲突的泥潭（台账 #35）！
  2. Rebase 覆盖：在跟随 upstream geth 进行兼容性升级时，上游的代码变动很容易覆盖本地预编译映射表。
  3. 接口漂移：以太坊未来定稿的官方预编译可能采用不同的输入排序或消息打包格式。

Mantle 的隔离工程策略：

  • 地址隔离：参考 OP Stack 引入 P256VERIFY 的成熟先例（分配在 0x0100，台账 #30），将 Mantle 的 ML-DSA-65 预编译分配在独立的扩展命名空间（如 0x0101，台账 #36）。
  • 插件化注册层：将预编译映射代码收敛在独立的 mantle_precompiles.go 中，并通过 Hook 注册到各个分叉配置中，CI 建立自动化回归套件。
  • 版本化适配合约：智能账户绝不直接硬编码预编译地址，而是调用 PQVerifierAdapterV1。未来以太坊出台官方预编译后，只需部署 PQVerifierAdapterV2，用户账户即可无缝升级调用官方标准，实现旧资产平滑兼容。
F14

抢占未定稿以太坊低位草案地址将带来破坏性冲突

置信度: high
论断

EIP-8051 与 EIP-8355 等互相竞争的草案均曾涉及 0x12、0x13 地址；提前占用低位草案地址在上游硬分叉时面临冲突覆盖与状态机不一致风险。

证据

observed EIP-8051 与 EIP-8355 草案地址提议；inferred 跨链硬分叉历史命名空间冲突分析（台账 #29, #35）。

影响

绝对禁止将 Mantle 自定义预编译部署在 1–30 号以太坊系统保留区间内。

F15

扩展命名空间与适配器模式可彻底隔离 Rebase 风险

置信度: high
论断

借鉴 OP Stack P256VERIFY（0x0100）的成功经验，置于独立扩展区间（>0x0100）并结合版本化适配器合约，可在历次 L1 分叉与 rebase 中保持完全隔离。

证据

observed OP Stack Specification 预编译定义；inferred 智能合约版本化代理设计模式（台账 #30, #36）。

影响

保证 Mantle 即使经历 5 次以上的 upstream rebase，PQ 账户和预编译逻辑也完全不受代码合并污染。

N

深度剖析：为什么 EIP-7702 不能作为容灾安全边界？

市场上存在一个严重误区：“当前用户先广泛使用 EIP-7702，将 EOA 委托给一个支持 PQ 验签的钱包合约；一旦 ECDSA 出现破解迹象，一键切换成 PQ 验签，资产就安全了。”

必须以严谨的 EVM 规范戳破这一幻想：7702 无法提供任何后量子安全边界！

攻击路径一：直接发起顶层交易（Bypass Execution）

  • EIP-7702 规范核心：EOA 设置代码（0xef0100 || address）后，依然是一个合法的交易发起者（Transaction Sender）。
  • EIP-3607 例外：以太坊 EIP-3607 规定“禁止已拥有代码的地址作为交易发起者”，但 EIP-7702 为了允许委托 EOA 继续发送交易，明确在协议层将带有委托前缀的 EOA 排除在 EIP-3607 检查之外（台账 #23, #24）。
  • 致命绕过：假设 Alice 的 EOA 委托给了一个要求 PQ 签名的合约。攻击者用量子算法反解出 Alice 的 ECDSA 私钥后，根本不需要调用 Alice 委托的那个智能钱包，而是直接构造一笔标准以太坊转账：
    from: Alice
to: TokenContract (USDT)
data: transfer(AttackerAddress, 1,000,000)
signature: ECDSA_Sign(AlicePrivKey, tx)
    在 EVM 执行层，msg.sender 就是 Alice！Token 合约立刻将 Alice 的代币全额转给攻击者！ 整个过程中，Alice 委托的智能合约代码连一次都没有被加载执行！其内部编写的任何抗量子检查完全形同虚设！（台账 #25）
F16

7702 账户的顶层发交易权限使其完全无法防御 ECDSA 破解

置信度: high
论断

EIP-7702 EOA 保留了顶层交易发起权并被豁免于 EIP-3607；攻击者掌握 ECDSA 私钥后可直接向外部代币合约发起转账，完全绕过委托合约中的 PQ 验签代码。

证据

observed EIP-7702 规范全文；EIP-3607 交互条款；以太坊官方 7702 指引（台账 #23, #24, #25）。

影响

必须向团队与社区明确澄清：7702 不能作为 PQ 容灾方案的最终形态，宣传“7702 一键抗量子”在密码学上是不负责任的。

攻击路径二：协议层覆盖与撤销（Revocation & Delegation Overwrite）

即使攻击者不发直接转账，7702 规范明确规定：只要拥有 EOA 的私钥签名，就可以签署新的授权元组（authorization tuple），将委托地址覆盖为一个恶意合约，或者指向 address(0) 彻底清除委托（台账 #26）。 在委托合约的代码里写 bool isRevocable = false 没有任何用处，因为 7702 委托关系的建立和撤销发生在协议执行层，在调用任何合约代码之前就已经被处理了！

F17

攻击者可随时通过协议层授权覆盖撤销 7702 委托

置信度: high
论断

掌握被破解 ECDSA 私钥的攻击者可签署新的 authorization tuple，在协议层直接覆盖或清除 7702 委托，合约内部防撤销逻辑无法拦截协议层动作。

证据

observed EIP-7702 授权元组与撤销规则说明（台账 #26, #38）。

影响

7702 的这一定位决定了它只能用来做“批量转账的辅助跳板”，绝不可用作承载核心资金的资产金库。

真正的容灾：受 EIP-3607 保护的 Smart Contract Account

相比之下，由 CREATE / CREATE2 部署的纯智能合约账户具有本质上的安全优越性：

  • 根据 EIP-3607，协议层严格禁止任何含有原生代码的合约地址作为顶层交易的 from 发送者（台账 #27）。
  • 这意味着：任何人都无法拿着这把地址对应的私钥（哪怕有）直接从它发起外部转账！
  • 所有进出该地址的资金操作，必须穿透该合约暴露的执行函数（如 execute()）。而在该函数内部，Mantle 的验签逻辑强制要求合法的 ML-DSA-65 签名。攻击者即便掌握了历史上该合约所有者的 ECDSA 私钥，也根本无法绕过合约内部的安全检查！
F18

受 EIP-3607 保护的真正智能合约账户是唯一的有效防线

置信度: high
论断

真正的智能合约账户受 EIP-3607 严格保护，无法作为顶层标准交易的发送者，所有资产转移必须穿透合约内部执行函数，从而能够强制执行不可绕过的 PQ 验签。

证据

observed EIP-3607 规范文本；ERC-4337 智能账户执行模型（台账 #27）。

影响

Mantle 的后量子容灾方案必须确立为“真正的合约账户体系”，引导高价值机构资产进入专用智能金库。

O

机构 PQ 智能账户模型与生命周期

为兼顾机构用户日常运营的高性能、低 Gas 诉求与应对突发量子威胁的极端安全性，设计双轨运行权限状态机：

F19

双轨权限状态机实现了日常效率与抗量子容灾的平衡

置信度: high
论断

机构智能账户采用“日常经典 AND PQ 组合审批，极端时由预设 PQ 密钥单向接管转为 PQ-only”的状态机设计，既不增加日常操作摩擦，又提供了不可逆的抗量子安全闭环。

证据

inferred 机构资产管理多签模型与容灾状态机设计模式（台账 #40, #43）。

影响

机构用户平时无需忍受复杂流程，遇到威胁时可一键进入绝对安全态，彻底废除被攻破的经典私钥。

关键防线：公钥提前绑定

公钥（或其哈希承诺）必须在和平时期完成链上初始化登记。如果等到量子计算机已经能破解 ECDSA 之后再去临时“登记 PQ 公钥”，攻击者同样可以冒充受害者在合约上登记攻击者的 PQ 公钥，导致灾难性的“抢跑注册”（台账 #41）。因此，机构开户必须包含原子化初始化与预先公钥承诺。

F20

PQ 密钥身份必须在和平期提前绑定，防止攻击发生时被抢跑

置信度: high
论断

一旦 ECDSA 失效，攻击者可冒充用户发起公钥登记；因此 PQ 公钥或其哈希承诺必须在经典密码学仍可信时完成链上绑定。

证据

inferred 密钥泄露抢跑攻击模型分析（台账 #41）。

影响

容灾方案的价值在于“提前建好避难所”，而不是“着火后再造灭火器”；开户工具链必须引导机构提前完成公钥部署。

残余风险：DeFi 历史授权（Allowance）暴露

即使智能合约账户自身的代码无可挑剔，如果该账户曾在历史上对某个第三方 DeFi 协议（例如某个 AMM Router、借贷池合约）赋予了无限 approve，且该第三方合约本身的升级管理员私钥使用的是经典 ECDSA，攻击者通过攻破第三方协议的管理员权限，依然可以通过 transferFrom 间接卷走资金（台账 #46）。 因此，机构 PQ 智能账户第一版应严格定义为低授权暴露的机构冷储备与资产结算金库，在交互外部协议时推行单次限额授权与自动撤销。

F21

第三方合约的 Allowance 是智能账户必须划定的残余风险边界

置信度: high
论断

智能账户即便自身代码安全，其历史上授予第三方 DeFi 合约的 token allowance 仍可被攻破该协议的攻击者利用 transferFrom 转移。

证据

inferred ERC-20 授权机制与智能合约权限传播链分析（台账 #46）。

影响

机构 PQ 账户产品宣传必须坦诚说明这一系统边界，并提供一键清理历史 allowance 的辅助工具。

P

Mantle 工程实施路线图

建议 Mantle 团队按照“安全闭环优先于功能数量”的原则，分四阶段推进抗量子落地：

  1. 阶段 1：账户与威胁模型 PoC验证真合约账户与 7702 绕过攻击演示；完成无 ECDSA 旁路的合约账户与状态机测试
  2. 阶段 2：算法全栈基准Cloudflare CIRCL 与 RustCrypto ml-dsa 对比测试；测量 EVM 与 SP1 zkVM 周期开销
  3. 阶段 3：预编译测试网集成执行端 op-geth 接入 0x0101 预编译，Kona 完成同步；跑通 OP Succinct 端到端证明
  4. 阶段 4：机构受限试点联合合规托管商与 AWS KMS；推出面向高净值与储备资金的 PQ Smart Account 试点

必须纳入验收的测试与失败场景

  1. 差分模糊测试（Differential Fuzzing）：针对 op-geth（Go）与 Kona（Rust），注入超过 1000 万个随机畸形公钥、截断签名、越界 hint 索引与无效消息，确保两端绝对给出完全相同的错误码与 gas 消耗；
  2. 7702 绕过攻击演练：在测试网构建 7702 委托账户与真正的智能合约账户对照组，模拟拥有 ECDSA 私钥的黑客攻击，验证 7702 资金被直接搬空，而智能合约账户成功防御；
  3. 分叉回放测试（Replay Safety）：回放激活区块前后的历史区块，验证在激活高度前调用预编译地址时返回空数据且消耗基础 gas，防止全节点历史同步分叉；
  4. SP1 证明端到端生成：在测试网上打包包含 10 笔 ML-DSA-65 验签操作的 Rollup 区块，使用 SP1 Prover 完整生成证明并提交至 L1 测试网验证合约，验证端到端证明耗时在可接受区间（< 15 分钟）。
Q

残余风险边界与常见误区清册

为防止团队与外部机构在沟通时产生不切实际的安全幻觉，明确列出以下边界：

流行误区 技术实质与真相 正确的工程表述
“给 7702 EOA 装个 PQ 模块就安全了” 错误。攻击者持 ECDSA 私钥可直调外部合约搬空资产，或覆盖委托（台账 #25, #26） 7702 只是迁移跳板；真正的安全必须进入真正的智能合约账户
“EVM 验签便宜，就等于证明端便宜” 错误。EVM 预编译只决定 gas；SP1 证明器仍需在 RISC-V 虚拟机内证明该计算（台账 #31, #32） 必须实测 Kona 在 SP1 内的周期消耗，综合评估全栈成本
“只要有 PQ 账户，全链资产就无懈可击” 错误。账户 PQ 无法抵御 L1 共识、KZG DA 或 Mantle 结算证明验证器的量子风险（台账 #44） 方案定位为“账户级授权容灾”，全链抗量子需与以太坊 L1 协同推进
“可以等以太坊 Native AA 定稿再做” 消极。以太坊 Native AA 预计 2028-2029 年前难以定稿（台账 #47） Mantle 可依托 ERC-4337 抢先建立机构安全心智与护城河
F22

账户级 PQ 保护不等同于全链抗量子

置信度: high
论断

账户级 PQ 智能账户仅解决账户授权与治理转移的安全性；Mantle 状态结算依赖的 L1 共识、KZG 数据可用性以及 Groth16/PLONK 证明验证器属于独立迁移边界。

证据

inferred 分层密码学依赖与系列前篇报告《后量子从入门到路线》（台账 #44）。

影响

对外沟通必须保持严谨中立，明确该产品是“后量子智能合约账户（PQ-Protected Smart Account）”，而非宣称“Mantle 已是后量子链”。
