# 高性能区块链的系统设计：从通用架构、分层瓶颈到 Mantle 工程路线

一条区块链的性能，不能用执行器的速度来代表。

用户提交交易以后，系统需要验证授权、接收和传播交易、确定顺序、执行状态转换、保存结果、让其他参与者能够验证，并最终让应用读取到可靠的新状态。这些工作会消耗不同资源，也存在不同的依赖关系。

因此，“建设高性能链”的正确起点不是选择并行 EVM、JIT 或某一种数据库，而是先回答：

> <b>区块链必须完成哪些工作？这些工作为什么会成为瓶颈？哪些工作可以加速，哪些可以并行，哪些可以移出实时路径，哪些则无法省略？</b>

本文先建立通用区块链的系统模型，再分析各层瓶颈与 L1/L2 差异，随后把已有研究和现实项目方案放回对应位置，最后推导 Mantle 面向 mStocks 的工程优先级。

# 一、从系统整体出发：区块链究竟在完成什么工作？

## 1.1 区块链首先是一套“可独立验证的共享状态系统”

可以从一个普通数据库开始理解。

如果 Alice 要把资产转给 Bob，一个中心化数据库只需要检查权限与余额，更新两人的账户，然后返回成功。系统的其他使用者相信数据库运营方没有伪造结果。

区块链增加了一组要求：参与者不能只相信某台服务器返回的结果，而需要能够确认输入的授权、交易的顺序、执行的正确性，以及重建或验证状态所需的数据。以 Ethereum 为例，执行客户端负责交易执行和状态维护，共识客户端负责共识相关工作，两者共同组成节点。[ethereum.org](https://ethereum.org/en/developers/docs/nodes-and-clients/)

对于支持智能合约的链，可以将状态转换抽象为：

\\\[<br />(S\_\{h+1\},R\_h)=F(S\_h,T\_h,E\_h)<br />\\\]

其中：

- \\(S\_h\\)：执行前的状态，例如账户余额、nonce、合约存储。
- \\(T\_h\\)：具有明确顺序的一组交易。
- \\(E\_h\\)：执行环境，例如区块属性、协议版本，以及 L2 使用的 L1 来源信息。
- \\(F\\)：确定性的状态转换规则。
- \\(R\_h\\)：回执、日志、Gas 使用等执行结果。

这个表达式说明：<b>执行器只是计算 \\(F\\) 的组件。系统还需要解决 \\(T\_h\\) 从哪里来、顺序由谁决定、\\(S\_h\\) 如何取得、结果如何保存，以及其他人如何验证。</b>

因此，区块链的性能优化既是计算问题，也是通信、存储、协调和验证问题。

## 1.2 不应把区块链理解成一条严格串行的“七层网络协议栈”

为了分析性能，可以将系统拆成八个逻辑层。但这些层是<b>职责边界</b>，不一定对应八个进程，也不意味着每笔交易都必须严格按图中的顺序走完。

```txt
                         用户 / 钱包 / 应用 / Agent
                                     │
                         ① 账户、交易表达与准入
                                     │
                         ③ 排序、共识与区块构建
                                     │
                         ④ 执行调度与虚拟机
                                     ↕
                         ⑤ 状态访问、承诺与持久化
                                     │
                         ⑧ 回执、查询、索引与状态流

② 网络传播：连接入口、生产者、验证者、跟随节点和应用服务
⑥ 数据可用性：确保验证、重建或退出所需的数据能够取得
⑦ 验证与结算：确定哪些结果可以被系统接受，以及何时不可逆

横切能力：资源计量、费用、容量分配、同步、故障恢复和升级
```

这里有三个重要的边界。

- \*网络传播不等于数据可用性。\*\*把区块发给几个节点，是传播行为；确保系统在生产者失效或作恶时仍能取得必要数据，是更强的要求。
- \*执行完成不等于验证完成。\*\*生产者算出了结果，不意味着其他节点已经检查过它，或结算层已经接受它。
- \*状态更新不等于用户已经观察到更新。\*\*执行节点的新状态，可能尚未传播到 RPC、索引器、Router 或做市商。

这些区别决定了为什么单个组件的 benchmark，不能直接代表整条链的用户体验。

## 1.3 L1 与 L2 的差别，是这些职责如何部署，而不是 L2 少做了几件事

对于典型智能合约 L1，排序、数据传播、状态执行和验证，由自身网络及共识协议共同完成。

对于 Rollup 类 L2，这些职责分成了两条不同时间尺度的路径：

```txt
实时交互路径
用户 → 准入 → Sequencer 排序 → 执行 → 预确认 / 状态流

安全与结算路径
L2 数据 → 批处理 → DA → 独立派生与验证 → 证明或争议 → L1 结算
                              ↑
                       L1 输入与协议规则
```

这是一张职责关系图，不代表所有 Rollup 都以同样顺序运行。例如，证明生成、数据发布和 L1 提交之间的具体依赖，取决于协议设计。

以 OP Stack 为例，派生节点需要从 L1 批次、deposit、L1 区块属性和既有 L2 状态，确定性地恢复 L2 区块。L2 并不是只要 Sequencer 输出一串交易，就可以任意定义执行上下文。[OP Stack Specification](https://specs.optimism.io/protocol/derivation.html)

因此：

> <b>L2 的性能优势之一，是可以让实时交互不必等待所有最终结算工作；但它没有消除数据发布、独立验证和恢复状态的成本。</b>

| 系统问题 | L1 的主要约束 | Mantle 类 L2 的主要约束 |
| --- | --- | --- |
| 谁确定交易顺序？ | 验证者共识和区块生产机制 | Sequencer 的实时排序，以及派生、结算规则 |
| 谁执行和验证？ | 自身验证节点执行或验证 | Sequencer、跟随节点、派生节点，以及证明或争议系统 |
| 数据传到哪里？ | 验证者和其他节点 | L2 节点、RPC、DA 服务和 L1 |
| 什么决定最终性？ | 自身共识协议 | L2 数据与 L1 的关系，以及结算机制 |
| 什么限制持续吞吐？ | 网络、验证、执行、状态等共同限制 | 上述限制，再加 DA 发布和证明/争议能力 |
| 优化能否只改客户端？ | 取决于是否改变协议语义 | 还需要检查派生、证明、L1 合约和桥 |

这里还要避免一种误解：\*\*增加完整复制执行的节点数量，不等于把这些节点的 CPU 简单相加来提高吞吐。\*\*如果每个节点都执行同一批交易，增加节点主要增加冗余和验证参与度；真正的横向扩容需要分工、分片或其他协议设计。

# 二、逐层理解瓶颈：问题究竟会出现在哪里？

这一部分暂时不讨论应该采用哪个项目的方案，而是先解释每一层为什么可能限制整条链。

## 2.1 账户、交易表达与准入层：系统可能还没开始执行，就已经拥堵

这一层把“用户想做什么”转换成“网络能够接受的操作”。

它包含账户授权、签名、nonce、费用支付、交易编码、RPC 接收、交易池管理，以及可能发生的模拟与预检查。

### 瓶颈一：一个业务动作被放大成多个协议动作

例如，一次资产购买可能需要准备 Gas、批准 Token、兑换支付资产，再执行购买。每一步都可能需要签名、网络请求和等待。

这里慢的不是 EVM，而是<b>业务流程存在过多串行交互</b>。即使执行器快十倍，多次人工确认和往返也不会同比缩短。

账户抽象之所以与性能有关，不只是它能减少签名次数，还因为它可以改变操作的表达方式、费用承担方式和授权粒度。ZKsync EraVM 的原生 AA，就是将可编程账户和 Paymaster 纳入交易处理体系的具体例子。[ZKsync Docs](https://docs.zksync.io/zksync-protocol/account-abstraction)

### 瓶颈二：准入消耗的资源，发生在收费之前

一个无效交易可能在被拒绝之前，已经触发解析、签名验证、状态读取，甚至复杂模拟。

如果准入层没有成本边界，攻击者或错误配置的机器人可以用大量不会上链的请求耗尽节点资源。此时链上 TPS 可能不高，但 RPC 和交易池已经不可用。

### 瓶颈三：账户规则制造队头阻塞

一个账户的多条业务操作，如果被同一串严格递增 nonce 绑定，前面一笔卡住，就可能阻塞后续无关操作。

但解除 nonce 阻塞，不代表解除状态冲突。两个策略仍然可能共享余额、限额、授权计数器或 Sponsor 预算。

- \*L1/L2 差异：\*\*L1 往往需要考虑多个节点的传播和交易池行为；单 Sequencer L2 可以集中管理准入，但也更容易形成入口热点和单点瓶颈。

这一层应该观察的不是只有 QPS，而是有效交易接收率、无效请求成本、队列年龄，以及每个成功业务动作需要多少次提交。

## 2.2 网络传播层：限制来自“传多少、传给谁、要传几轮”

网络层承担的不只是一种消息。交易、区块提案、投票、状态差分、witness、同步数据和 RPC 订阅，可能同时占用带宽和 CPU。

理解网络瓶颈，要区分<b>带宽</b>和<b>传播时延</b>。

带宽限制单位时间能传多少数据；传播时延限制一个消息最早何时到达对方。升级网卡能改善前者，却不能消除跨地域通信的物理延迟。

### 瓶颈一：生产者的扇出负担

如果一个生产者需要把同一个大区块完整发送给大量节点，它的出站带宽会随接收者数量增长。

将分发任务交给中继节点，可以减轻生产者压力，但又会增加跳数、丢包恢复和中继失效问题。Monad 的 RaptorCast 文档正是从这两种朴素方案的局限出发，设计编码与分层传播。[Monad Documentation](https://docs.monad.xyz/monad-arch/consensus/raptorcast)

### 瓶颈二：冗余消息和消息处理本身

网络不满，也可能因为每秒消息数量过多、签名验证过重、序列化成本过高或线程调度频繁而变慢。

因此，将区块切得更小会减少单条消息等待，却可能增加消息数量和固定处理开销。

### 瓶颈三：更高吞吐把下游节点拖入持续落后

生产者能执行，不代表验证者、RPC 和索引器能及时接收并处理。如果下游长期落后，系统可能出现“链还在出块，但应用一直看到旧状态”。

- \*L1/L2 差异：\*\*L1 更关注提案和投票能否在满足安全条件的节点集合中及时传播；L2 则尤其需要处理 Sequencer 向跟随节点和服务节点的分发压力。

不能把“最强节点的吞吐”当作网络的可持续吞吐，也不能简单地说网络速度由任意一个最慢节点决定。需要定义能够维持安全、验证和服务能力的节点性能边界。

## 2.3 排序、共识与区块构建层：等待与协调可能比计算更昂贵

这三个概念相关，但并不相同。

<b>排序</b>决定交易的先后；<b>区块构建</b>决定选哪些交易、如何满足容量与有效性约束；<b>共识</b>解决多个参与者如何接受同一条规范链或同一组有序输入。

### 瓶颈一：执行被压缩在有限的构建窗口里

假设一个区块周期中，节点要完成准备上下文、选择交易、执行、计算状态根和传播。即使区块周期很长，真正分给交易执行的窗口也可能很短。

如果这些阶段严格串行，执行器会在一些阶段等待，而不是持续工作。

这就是你们 RISE 研究中“连续区块流水线”所针对的问题。不过，旧文将 L1 输入获取与派生准备记作 C 阶段，不能把这个 C 与 L1 验证者的共识投票开销直接等同。[并行执行和并行 EVM 综述](https://app.notion.com/p/3d92f04c436c817b9735f84f2ff1390b?pvs=204)

### 瓶颈二：全局协调需要通信轮次

对于分布式共识，最终性通常依赖一定的通信和投票条件。节点计算变快，不会自动减少必要的网络往返。

改变协议可以缩短正常路径，但需要同时检查故障条件、超时、恶意节点比例和安全假设，而不是只比较正常网络下的延迟数字。

### 瓶颈三：构建器自身做了大量额外工作

交易模拟、bundle 组合、收益搜索、替换交易、处理失效报价，都可能消耗构建预算。业务越复杂，构建器越不像一个简单的 FIFO 队列。

### 瓶颈四：固定出块节奏产生等待

即使系统空闲，交易也可能需要等到下一个构建或发布时间点。

但直接缩短完整区块周期，会增加每秒区块头、状态承诺、持久化和传播的固定开销。因此，<b>低延迟与高吞吐并不天然同向</b>。

- \*L1/L2 差异：\*\*L1 需要在自身共识约束下设计构建和执行预算；L2 可以更早提供 Sequencer 承诺，但必须将其与最终性分开。OP Stack 的 unsafe、safe、finalized 也不是“接收、执行、证明完成”的同义词。[Optimism Documentation](https://docs.optimism.io/stack/transactions/transaction-finality)

## 2.4 执行层：瓶颈有三种，不能都叫“EVM 慢”

执行层读取已有状态，按照协议规则运行交易，并产生状态修改和回执。

其内部至少存在三类不同限制。

### 第一类：计算吞吐不足

解释器分发、算术、内存处理、调用帧、密码学计算等耗尽 CPU。这类问题适合考虑实现优化、批量计算或编译执行。

### 第二类：执行线程在等待数据

CPU 没有持续计算，而是在等状态读取、缓存填充或锁释放。增加执行线程可能有帮助，也可能把数据库压得更严重。

### 第三类：业务本身存在串行依赖

假设两笔交易连续修改同一个池子的储备。第二笔交易的正确结果，可能取决于第一笔交易后的价格。

这种依赖不是换语言、加线程就能消除的。并行执行只能发现和利用<b>实际存在的独立工作</b>，不能凭空创造独立性。

Block-STM 的核心约束正是：物理执行可以并发，但结果必须与预先确定的交易顺序一致。[arXiv](https://arxiv.org/abs/2203.06871)

- \*L1/L2 差异：\*\*两者都需要确定性执行；L2 还要考虑执行规则能否在派生和证明环境中一致实现。Sequencer 的原生执行更快，不意味着证明端的成本同比下降。

所以，执行层应该分别测计算时间、状态等待、冲突重试和最终提交，而不是只给出一个“执行耗时”。

## 2.5 状态与存储层：读到数据、修改数据、证明数据、保存数据，是四件事

这一层是最容易被“数据库”三个字掩盖的部分。

一笔交易修改余额时，系统可能需要：

```txt
取得账户和合约状态
        ↓
在执行期间维护可回滚的修改
        ↓
将修改合并为确定的新状态
        ↓
更新认证结构和状态根
        ↓
按持久化策略保存数据
```

这些操作并不意味着每执行一次 SSTORE 就立即进行一次物理磁盘写入。客户端通常会利用缓存、差分和批处理；物理落盘与协议层状态修改不能直接画等号。

### 瓶颈一：随机状态访问

当工作集无法有效命中内存时，交易会频繁读取磁盘。状态访问越分散，预读和缓存越难发挥作用。

### 瓶颈二：更新被多层结构放大

一个逻辑状态修改，可能引起认证树中多个节点更新；底层数据库又可能产生索引、日志和 compaction 工作。

这也是你们 QMDB 研究关注的主线：问题不只是“树很深”，而是认证结构与物理存储布局共同决定了实际 IO。[由 QMDB 引发的对于区块链状态管理方案综述](https://app.notion.com/p/3d92f04c436c8162aed7d87da1b7a1e9?pvs=204)

### 瓶颈三：长期增长改变了性能条件

当前状态、历史状态、历史区块和证明数据，是不同的数据集合。它们的增长速度、访问频率和保留要求不同。

一台机器在小状态、热缓存下很快，不代表它在长期运行后仍然很快。Geth 的归档文档也明确区分了历史状态与历史 trie 数据，并提供不同的保留配置。[geth.ethereum.org](https://geth.ethereum.org/docs/fundamentals/archive)

- \*L1/L2 差异：\*\*L1 需要考虑广泛节点的验证与存储门槛；L2 可以让生产者使用更强硬件，但仍需保证独立重放、witness 生成和恢复路径可行。

这一层的瓶颈，往往同时影响执行、状态根、证明和节点同步，而不是只影响一个数据库函数。

## 2.6 数据可用性层：状态根很小，不代表系统需要的数据也很小

一个状态根可以承诺大量数据，但不能代替这些数据本身。知道状态根，不代表能取得账户状态、重放交易或构建退出所需的证明。

数据可用性解决的是：\*\*系统参与者能否取得协议所需的数据，而不是只收到一个承诺。\*\*有效性证明与数据可用性也不是同一项保证。[ethereum.org](https://ethereum.org/en/developers/docs/data-availability/)

### 瓶颈一：每笔业务产生多少必须发布的数据

交易签名、calldata、批次元数据、状态差分等，都会影响 DA 消耗。不同架构发布的内容不同，不能只按交易数量比较。

### 瓶颈二：发布容量和价格

对于使用外部 DA 的 L2，本地执行能力再高，也不能无限期超过数据发布能力。否则未发布数据会持续积累。

### 瓶颈三：批处理成本与等待时间冲突

更大的批次可能提升压缩率、摊薄固定成本，却会增加等待时间和失败重试范围。

因此，DA 优化不仅是“选更便宜的 DA”，还涉及批次大小、发布频率、压缩、恢复和安全假设。

- \*L1/L2 差异：\*\*L1 自身需要保障其协议数据的可用性；L2 需要适配所选 DA 的规则和容量。使用 Ethereum blobs、外部 DA 或其他模式，带来的安全与恢复边界不同。

---

## 2.7 验证与结算层：实时执行的债务，最终必须有人偿还

这一层回答两个问题：系统为什么接受这次状态转换？用户什么时候可以依赖其不可逆性？

对 L1，验证和共识紧密相关；对 L2，则可能涉及独立派生、有效性证明或争议机制。

### ZK 路线的限制

证明系统不仅要完成数学证明，还需要取得输入、生成 witness、执行证明程序、生成分段证明、聚合并提交。

其中任何环节落后，都可能形成积压。OP Succinct 就明确区分 range proofs、聚合证明以及链上验证和状态根更新。[Succinct Labs](https://succinctlabs.github.io/op-succinct/architecture.html)

### Optimistic 路线的限制

没有持续生成每批有效性证明，不代表没有验证容量约束。挑战者需要能够独立重放，并在协议时间预算内完成必要的争议工作。

因此，这两类系统的容量模型不能完全相同：前者需要观察持续证明吞吐；后者还必须验证最坏情况下的挑战可完成性。

### 一个共同问题：不能靠无限积压展示高性能

如果执行端持续快于验证和结算路径，短时间内 TPS 很好看，但安全状态越来越落后，恢复成本也越来越高。

所以，链的可持续能力必须包含验证和结算路径，而不能只统计 Sequencer 已经执行的交易。

---

## 2.8 查询、索引与恢复层：系统不仅要写得快，还要读得到、追得上

应用并不直接观察执行器内部的内存。用户余额、成交回执、行情和历史记录，通常通过 RPC、订阅和索引服务取得。

### 瓶颈一：读请求被放大

一笔交易可能引起钱包、浏览器、Router、做市商和监控系统的多次查询。业务吞吐增长一倍，读取压力未必只增长一倍。

### 瓶颈二：共享资源相互干扰

历史查询、大范围日志扫描和交易模拟，可能与最新状态服务争用 CPU、缓存和磁盘。

### 瓶颈三：数据虽然响应很快，但已经过时

一个 RPC 在几毫秒内返回旧状态，不能被视为低延迟交易服务。对交易系统而言，<b>响应时间和状态新鲜度必须分别测量</b>。

### 瓶颈四：新节点或故障节点无法追赶

如果节点重放速度只等于链持续产生工作的速度，那么一旦掉队，就没有余量追上。

因此，高性能建设必须包含同步、快照验证、历史保留和故障恢复。MegaETH 的节点分工设计，把直接应用状态更新的 replica 与独立重执行的 full node 区分开，说明“快速提供读取”和“独立验证”可以是不同职责，但信任边界必须明确。[Megaeth Docs](https://docs.megaeth.com/architecture?utm_source=chatgpt.com)

---

## 2.9 横切约束：费用与容量管理决定谁承受拥堵

费用不是独立于性能的经济装饰，而是有限资源的准入和分配机制。

如果收费不能约束最昂贵的资源，攻击者或套利流量就可能以低成本消耗大量 CPU、状态 IO、DA 或证明工作。

EIP-1559 根据区块 Gas 使用与目标调整 base fee，但 Gas 仍是协议定义的计量，而不是现实硬件消耗的直接读数。[Ethereum Improvement Proposals](https://eips.ethereum.org/EIPS/eip-1559)

这意味着一条链必须同时回答：

> <b>系统最多承受多少工作？拥堵时接受哪些工作？不同工作如何付费？</b>

这三个问题对应容量、排序/准入和定价，不能混成同一个“提高 Gas limit”。

# 三、把各层连起来：为什么单点优化经常无法改善整条链？

## 3.1 吞吐受资源预算限制，延迟受关键路径限制

假设业务类型 \\(k\\) 每秒到达 \\(\\lambda\_k\\) 次，每次在资源 \\(r\\) 上消耗 \\(c\_\{k,r\}\\)，该资源每秒可提供预算 \\(B\_r\\)。

可持续运行至少需要满足：

\\\[<br />\\sum\_k \\lambda\_k c\_\{k,r\}\\le B\_r<br />\\\]

这里的资源可以是 CPU、状态读取 IO、写入带宽、网络带宽、DA 或证明算力。

这个模型比“整条链的 TPS 等于最慢组件 TPS”更准确，因为多个组件可能争用同一块 CPU 或磁盘。把它们拆成多个服务，并不会创造额外资源。

单笔延迟则不同。它由关键路径上的计算、等待、排队和通信组成。即使总资源足够，只要必须等待某个时间窗口或前置结果，交易仍然会慢。

因此：

<b>吞吐优化关注单位时间完成多少工作；延迟优化关注一项工作的必要等待能否减少。</b>

## 3.2 流水线、并行和更早反馈，是三种不同优化

考虑一个纯示意系统，每批处理相同数量的交易：

| 阶段 | 耗时 |
| --- | --- |
| 输入准备 | 40 ms |
| 执行 | 80 ms |
| 状态承诺 | 120 ms |
| 发布 | 60 ms |

如果严格串行，每批需要 300 ms。

如果不同批次能够在不同阶段重叠，且资源和状态依赖允许，那么稳定状态下可能每 120 ms 完成一批。但第一批的端到端时间仍可能是 300 ms。

这就是<b>流水线提高吞吐，并不自动缩短单批延迟</b>。

如果把执行从 80 ms 优化到 40 ms，稳定吞吐仍可能受 120 ms 的状态承诺限制。

如果在执行后先发布临时回执，用户更早看到结果，但完整状态承诺和最终结算仍然要完成。

这就是为什么不能把并行 EVM、Flashblocks 和延迟 Merkleization，都统称为“让执行更快”。

## 3.3 缩短区块时间，会降低等待，也会增加固定开销

在交易均匀到达、没有排队的简化假设下，固定发布间隔为 \\(\\Delta\\) 时，平均等待约为 \\(\\Delta/2\\)。

但如果每次发布有固定成本 \\(f\\)，每秒固定开销会随 \\(f/\\Delta\\) 增长。

因此，直接将完整区块切得更小，可能一边降低等待，一边消耗更多资源。小区块或增量预确认的价值，正是在一定条件下将<b>反馈频率</b>与<b>完整区块承诺频率</b>分开。

## 3.4 热点状态决定并行上限

对于一批交易，设总计算工作量为 \\(W\\)，执行线程数为 \\(p\\)，依赖图上最长串行路径耗时为 \\(L\\)。理想执行时间至少受到：

\\\[<br />T\\ge \\max(W/p,L)<br />\\\]

的约束。

增加线程只能改善第一项，不能直接缩短第二项。

因此，做并行执行决策时，不能只问“多少交易冲突”，而应问：

<b>最昂贵的依赖链有多长？哪些依赖是业务必需的，哪些是共享计数器或实现设计人为造成的？</b>

## 3.5 瓶颈会迁移，而且迁移本身就是优化成功后的正常现象

改善执行后，状态根可能成为瓶颈；改善数据库后，网络可能成为瓶颈；扩大本地吞吐后，DA 和证明可能成为瓶颈。

所以工程目标不是“消灭所有瓶颈”，而是：

> <b>在目标工作负载和安全约束下，让各环节拥有足够余量，并避免某个下游长期积压。</b>

# 四、从瓶颈到方案：现实项目究竟优化了什么？

## 4.1 账户与准入：减少操作链路，同时限制进入系统的成本

这一层的优化可以分成两类。

第一类是改善业务表达：批量调用、代付、session key、有效期、不同用途的 nonce 空间，让一个业务动作不必拆成多次低效交互。

第二类是控制验证成本：低成本检查前置、去重、有界队列、模拟预算、过期淘汰，以及把昂贵查询与交易入口隔离。

ZKsync EraVM 的原生 AA 提供可编程账户和 Paymaster，是第一类方案的参考；Solana 的交易结构则展示了另一种设计：交易显式携带账户与权限信息，网络据此组织验证和执行。两者改变的接口不同，不能简单认为都属于“钱包体验优化”。[ZKsync Docs](https://docs.zksync.io/zksync-protocol/account-abstraction)

- \*代价在于：更灵活的账户验证可能更昂贵。\*\*Session key、Sponsor 或复杂权限策略也可能引入新的共享状态热点。

对 Mantle，native AA 设计应该同时包含交易池、验证预算、撤权和费用失败语义，而不是只设计账户合约接口。

---

## 4.2 网络：通过分发拓扑、编码和节点分工降低传播成本

网络优化主要有三条路线。

- \*改变谁发送数据。\*\*将生产者直连所有消费者，改为分层分发或专用扇出服务。
- \*改变如何发送数据。\*\*使用分块、编码、去重和更合适的传输协议，在丢包和带宽之间取得平衡。
- \*改变谁需要处理全部内容。\*\*让部分节点提供读取，部分节点独立执行，部分节点生成证明。

Monad RaptorCast 使用纠删编码和两层广播结构，分担 leader 的分发工作。编码并不是把必须传输的信息“消失掉”，而是在增加一定冗余的同时改善恢复与传播。[Monad Documentation](https://docs.monad.xyz/monad-arch/consensus/raptorcast)

Base Flashblocks 架构中的 websocket-proxy 则解决了一个更直接的 L2 问题：让大量消费者读取增量流，而不直接压垮 builder。[Base documentation](https://docs.base.org/base-chain/flashblocks)

对 Mantle，通常应先评估 builder、节点同步和对外行情分发之间是否耦合过深，再决定是否需要更复杂的专用网络。

---

## 4.3 共识与构建：减少关键路径工作，而不是删除验证义务

### L1 路线一：优化共识通信

Alpenglow 的设计将投票与数据分发分别优化，研究如何减少正常路径的投票轮次和传播跳数。这类收益来自协议协调方式，而不是 EVM 执行速度。

需要注意，原始介绍中的低延迟数字来自仿真，且明确没有计入计算开销，不能拿来直接与生产链端到端延迟比较。[anza.xyz](https://www.anza.xyz/blog/alpenglow-a-new-consensus-for-solana)

### L1 路线二：让排序与执行重叠

Monad 将执行从排序共识的关键路径中分离，并用延迟状态根等机制处理后续一致性检查。这样扩大了执行可以使用的时间预算，但也引入了状态滞后下的准入和余额管理问题。[Monad Documentation](https://docs.monad.xyz/monad-arch/consensus/asynchronous-execution)

### L2 路线：连续构建与增量发布

你们的 RISE 研究，可以抽象成两项独立工作：

<b>连续构建</b>减少阶段之间的空闲；<b>增量发布</b>让用户不必等待完整区块结束才得到反馈。

RISE 的 Preconfirmation Shreds 设计将 Merkleization 移出增量预确认的关键路径，同时保留完整 L2 区块，并在后续批量处理状态承诺。[并行执行和并行 EVM 综述](https://app.notion.com/p/3d92f04c436c817b9735f84f2ff1390b?pvs=204) [RISE Labs](https://blog.risechain.com/incremental-block-construction/)

Base Flashblocks 则提供了增量构建的实际架构参考。重要的不只是更短的发布周期，还包括：一旦前缀已经构建并广播，后来的高优先费交易不能插入已经锁定的前缀。[Base documentation](https://docs.base.org/base-chain/network-information/transaction-ordering)

- \*对 Mantle 的含义：\*\*优先改善现有构建、状态提交和下一块启动之间的等待，而不是照搬某个 L1 共识算法。并且，所有提前执行都必须绑定正确的区块与 L1 上下文；上下文变化时，相关结果必须失效或重新验证。

---

## 4.4 并行执行：静态声明、乐观执行与辅助验证

### 静态声明：先知道可能访问什么

Solana 的交易账户和权限信息，使运行时能够在执行前识别账户级别的冲突。优势是依赖较早可见；限制是账户粒度和声明接口会影响可并行程度。[Solana](https://solana.com/docs/core/transactions/transaction-pipeline)

### 乐观执行：先运行，再验证读取是否成立

Aptos 的 Block-STM 和 Monad 的乐观并行执行，允许交易在前序交易完成之前启动，通过记录依赖、验证读取和必要时重执行，保持既定逻辑顺序。[arXiv](https://arxiv.org/abs/2203.06871)

例如：

```txt
初始 x = 10

既定顺序：
T1：x = x + 5
T2：z = 2 × x
```

T2 若提前读到 10，得到 20，只能作为临时结果。最终必须让它观察到 T1 后的值，得到 30。

### 辅助验证：生产者提供已经发现的访问信息

EIP-7928 的 block-level access list 记录实际访问和交易后的状态变化，可辅助并行读取、验证和状态根计算。本次读取的规范状态为 Review。它不等于“生产者在执行前天然知道所有依赖”，也不能把未经验证的列表当作事实。[Ethereum Improvement Proposals](https://eips.ethereum.org/EIPS/eip-7928)

### 对已有 Mantle 依赖研究的更新

你们 2025 年的分析得到 49.10% 的依赖比例，但使用了同发送方、同目标合约、同函数选择器等启发式条件。这个结果适合发现交易集中度，不能直接当作 storage-slot 级冲突率。[流式出块技术方案设计 - geth](https://app.notion.com/p/3d92f04c436c813bb8f7d98ed9572d11?pvs=204)

新的实验应记录账户字段与 storage slot 的真实读写集合，再计算带执行成本的依赖图。

尤其要区分：同一 Token 合约中的独立账户转账，可能在业务状态上独立；同一热池中不同函数，却可能共享关键状态。费用账户等公共写入还需要单独处理。

<b>工程上，先做预读和并行准备工作，再引入完整的乐观执行器，通常比直接重写整个执行调度风险更低。</b>

---

## 4.5 虚拟机：减少每笔交易的计算成本

虚拟机优化包括解释器热路径、内存分配、调用帧、密码学库，以及 JIT/AOT。

Monad 当前文档描述了混合路径：普通调用使用优化解释器，热点合约异步编译为原生代码并缓存；编译尚未完成时仍可走解释器。其目标是保持相同的 EVM Gas 和错误语义，而不是通过改变语义获得速度。[Monad Documentation](https://docs.monad.xyz/monad-arch/execution/native-compilation)

这里的工程重点有两个。

第一，<b>收益取决于计算占比</b>。如果大部分时间花在状态读取或 root 计算，替换解释器的整链收益有限。

第二，<b>编译执行增加了新的风险面</b>：冷编译、缓存淘汰、缓存键与协议版本、不同 CPU、内存占用，以及 out-of-gas 和回滚行为。

对 Mantle，不应把“换客户端”“换 VM 库”和“引入 JIT”当成同一个项目。完整客户端还包含数据库、同步、RPC、交易池和构建逻辑；不同改动覆盖的瓶颈并不相同。

---

## 4.6 状态系统：先优化数据路径，再决定是否更换承诺结构

你们 QMDB 研究可以进一步拆成三种工程路线。

### 路线 A：保持协议语义与状态根，优化物理实现

包括缓存、预读、批量访问、异步 IO、版本化状态、写入布局和历史数据分层。

MonadDb 就属于重要参考：它原生组织 MPT 数据，支持异步 IO 和版本化读写，而不是通过取消 MPT 来取得全部收益。[Monad Documentation](https://docs.monad.xyz/monad-arch/execution/monaddb)

Geth 的 path-based archive 也说明，存储结构和历史状态组织会持续演进。因此，去年的 Geth/Reth 归档体积对比，不能直接当作今天的迁移收益。[geth.ethereum.org](https://geth.ethereum.org/docs/fundamentals/archive)

### 路线 B：优化状态承诺的计算方式

多个修改共享上层路径时，可以合并重复工作，进行独立子树并行、脏节点去重和批量更新。

这里改善的是“如何计算同一个正确结果”，未必需要改变状态根格式。

### 路线 C：更换认证数据结构

NOMT 和 QMDB 提供了更深层的设计参考。QMDB 的追加写、Twig 和 ActiveBits，将可变状态管理与认证结构结合起来；NOMT 则围绕高性能认证存储设计。[GitHub](https://github.com/thrumdev/nomt)

但新的认证结构不是一个普通数据库替换。它可能影响状态证明、同步、桥、witness 和证明程序。

- \*对 Mantle，我建议 A 与 B 优先，C 独立立项。\*\*这不是保守地拒绝新结构，而是先取得低协议风险收益，再证明大迁移的必要性。

另外，历史数据治理与活跃状态治理必须分开。EIP-4444 讨论的是历史区块头、区块体和回执保留，不是清理当前活跃状态。[Ethereum Improvement Proposals](https://eips.ethereum.org/EIPS/eip-4444)

---

## 4.7 资源计量与区块空间：把“分配容量”与“决定顺序”分开

可以把交易资源消耗写成一个分析向量：

```txt
[CPU、状态读取、状态写入、网络数据、DA、证明工作、长期状态增长]
```

这不意味着 Mantle 必须立刻推出七种费用。第一步是测量各维度，识别单一 Gas 计量与真实资源之间的偏差。

ZKsync OS 的 Double Resource Accounting，是区分执行环境计量与底层原生资源计量的现实参考。[ZKsync Docs](https://docs.zksync.io/zksync-protocol/zksyncos/double-accounting)

你们 A2S 研究中“不同业务需要不同排序服务”的方向值得保留，但需要修正两个推论。

- \*服务隔离不等于状态隔离。\*\*两个服务可能共同访问同一个池子、Sponsor 或资金账户，仍然发生冲突。
- \*Tips 上下限不等于独立费用市场。\*\*它可以改变优先级，却不自动隔离共享 base fee、CPU、IO 和 DA。[Rise Chain 中对区块构建的设计](https://app.notion.com/p/3d92f04c436c813ba306cdfd44fe9a4f?pvs=204)

因此，应分别设计：

| 设计问题 | 对应机制 |
| --- | --- |
| 哪类业务可以获得多少容量？ | 准入、配额、预留容量、可借用余量 |
| 进入容量范围的交易如何排序？ | FCFS、拍卖、批量规则、有限优先级 |
| 谁为哪些资源付费？ | 计量、费用和拥堵定价 |
| 谁能验证规则被遵守？ | 协议检查、合约约束、证明或可审计承诺 |

对 Mantle，应用特定排序不应从“引入外部 builder 拍卖市场”开始，而应从<b>明确一类业务需要什么保证，以及保证如何被检查</b>开始。

---

## 4.8 DA 与证明：压缩、批量和并行，都要计算端到端成本

DA 优化主要减少必须发布的字节，或改善发布与恢复流程；证明优化主要减少或并行化验证状态转换的工作。

PeerDAS 的方向，是让节点通过下载部分数据进行可用性检查，从而扩展 DA，而不是加速 EVM。它说明“减少每个节点必须承担的工作”也是扩容方式。[Ethereum Improvement Proposals](https://eips.ethereum.org/EIPS/eip-7594)

OP Succinct 的 range 与 aggregation 分工，则展示了证明流水线的组织方式。但分段证明不意味着 witness、数据获取和状态边界完全没有依赖。[Succinct Labs](https://succinctlabs.github.io/op-succinct/architecture.html)

对 Mantle，native AA、新预编译或新状态规则必须检查执行与证明是否一致。原生执行中的优化，只要不改变语义，可以不要求证明程序采用相同实现；但改变状态转换的功能，必须进入统一验证范围。

你们 Arsia 清算压测已经要求观察预确认、op-batcher 和 ZK 证明，这是应该继承的完整测试边界。[MegaEth 高性能技术解析](https://app.notion.com/p/3d92f04c436c8106a243f8df68df4667?pvs=204)

---

## 4.9 查询与节点分工：将“高性能生产”和“低成本读取”解耦

实时状态、历史查询、交易模拟和独立验证，不一定要由同一组节点承担。

MegaETH 的架构研究把 Sequencer、Replica、Full Node 和 Prover 分开，目的是对不同职责采用不同资源配置。这里可借鉴的是职责分离，而不是直接复制其硬件数字或将所有角色视作相同信任级别。[MegaETH](https://www.megaeth.com/research?utm_source=chatgpt.com)

Mantle 可以逐步建立带版本的实时状态流，配合快照、游标、缺口补齐和重组撤销；让 Router 和做市商基于同一状态上下文工作。

此外，高可用需要明确持久化和复制边界。备用节点的存在，并不能自动保证已经发出的预确认在切换后仍可延续。

---

## 4.10 横向扩展与专用执行：最后才决定是否拆开统一执行域

当前面的优化仍不足时，才需要进一步讨论状态分片、专用执行模块或独立应用链。

它们可能提高总容量，但也会改变跨域操作的成本。

| 方向 | 可能收益 | 新增代价 |
| --- | --- | --- |
| 单一执行域内并行 | 保留较直接的原子可组合性 | 仍受共享热点限制 |
| 统一验证边界内的专用模块 | 对特定业务减少通用运行时成本 | 新接口、状态语义、证明与升级工作 |
| 独立应用执行域/L3 | 更独立的容量、规则和发布节奏 | 跨域通信、流动性、原子性和安全边界 |

不能把“拆成多个域后总 TPS 提高”与“同一个热门市场的单笔交易更快”混为一谈。后者仍可能受到共享订单簿、库存或清算状态的限制。

# 五、将通用模型应用到 Mantle：mStocks 对每一层提出什么要求？

前面的分析没有以 Mantle 的产品先入为主。现在可以反过来：将具体产品放入系统模型，判断哪些瓶颈更值得优先解决。

## 5.1 不同用户需要的是不同的性能属性

| 场景 | 主要状态与交互特征 | 更可能限制体验的组件 |
| --- | --- | --- |
| 资产发行、销毁和申赎 | 权限、供应量、资产注册、批量操作、对账 | 账户授权、幂等流程、共享写状态、事件与结算 |
| 普通用户买入 mStocks | 报价、授权、换币、购买、Gas 支付 | 多次交互、报价陈旧、排序等待、失败重试 |
| 做市商报价与库存调整 | 高频状态更新、撤改、外部参考价格 | 入口、状态流、排序规则、尾延迟、热点状态 |
| Agent 执行策略 | 持续请求、多策略并发、权限与预算 | nonce 阻塞、验证成本、Sponsor 热点、准入控制 |
| 波动或清算高峰 | 多参与者争抢相同状态 | 冲突、失败交易、容量竞争、DA/证明积压 |

由此可以得到一个不同于“先上并行 EVM”的优先顺序。

<b>发行体验</b>首先需要可靠授权、幂等和状态可追踪；<b>普通交易体验</b>首先需要减少操作与过期报价；<b>做市体验</b>首先需要新鲜数据、可预测排序和低尾延迟。

这些目标会用到执行性能，但不都由执行性能决定。

你们最新产品笔记已经将 mStocks、native AA、交易排序、JIT Router 和 Prop AMM 放在同一条产品驱动的基础设施路线中。这里需要保留的是这种关联，而不是把某一项单独包装成整条链的性能方案。[Monad 高性能设计解析](https://app.notion.com/p/3d92f04c436c816daa42eb3d6fa02260?pvs=204)

## 5.2 用一次 mStocks 买入贯穿全系统

假设 Alice 使用稳定币购买 mStock-X。

Router 首先基于明确的状态版本获取报价。账户层表达最大支出、目标资产、有效期和费用承担者，将不必要的多次操作合并。

准入层验证授权与费用预算，避免代付变成无限模拟和垃圾请求的入口。

Builder 确定交易顺序。执行层读取相应状态并完成购买；如果已有预确认锁定顺序，后来的报价更新或高 tips 交易不能任意插入前面。

执行结果进入带版本的数据流，使 Alice、Router 和做市商看到一致的余额与库存变化。

随后，DA、证明和结算路径继续推进。界面区分“执行成功”与“满足最终结算条件”，不把它们统一为一个模糊的确认状态。

这个流程中的任意一段落后，都可能让其他优化失去价值：账户操作再少，报价过期仍会失败；执行再快，RPC 旧状态仍会误导下一次交易；预确认再早，DA 长期积压也不可持续。

## 5.3 成交质量必须成为独立目标

更高吞吐并不自动带来更好成交。

例如，撤单优先可以降低做市商风险，但如果允许做市商在观察到用户接受后无限撤回报价，就可能形成对用户不利的 last look。

因此，建议为 mStocks 明确报价生效、用户接受、顺序锁定和撤单失效的边界。评估排序改动时，同时观察 maker 的风险与 taker 的成交率、成本和等待时间。

同样，预留容量可以提高纳入确定性，却不能在未修改费用机制时保证其他业务永远不会推高其费用。

# 六、工程规划：按收益、依赖和复杂度安排，而不是按技术热度安排

## 6.1 先确定当前基线，避免把已完成工作重新列为目标

本次核查的 Mantle v1.6.3 Elysium 发布记录，已经包含 eager next-block construction；Arsia 相关发布记录也包含 span batch、Brotli 和 DA 费用相关改动。因此，这些不能直接写成“从零引入”的新项目。

同时，公开发布记录仍以 op-geth 为上游基础。此前 Reth 研究、候选实现或局部组件使用情况，不能自动等同于生产 Sequencer 已迁移。以下规划以实际角色、版本和配置清单为启动条件，不将发布记录视作生产部署审计。[GitHub](https://github.com/mantle-xyz/mantle-v2/releases?utm_source=chatgpt.com)

## 6.2 优先级总表

下面的优先级是基于 mStocks 目标与改动风险的初始判断，不是 Mantle 已测得的瓶颈排名。

| 工作包 | 预期收益类型 | 复杂度 | 优先级与理由 |
| --- | --- | --- | --- |
| 端到端 trace、真实依赖图、重放基线 | 确定瓶颈，验证所有后续改动 | 中 | P0，所有项目共同依赖 |
| 现有构建、预确认和读取链路 | 减少固定等待与状态陈旧 | 中 | P0，直接影响交易体验 |
| mStocks 账户与业务操作闭环 | 减少签名、授权和失败恢复成本 | 中 | P0，直接对应产品需求 |
| Native AA 协议设计与原型 | 确定权限、支付和并发接口 | 高 | P0 启动，不等待底层优化结束 |
| Cache、预读、root、witness 数据路径 | 改善执行与提交共同瓶颈 | 中至高 | P0/P1，依据 profile 选择 |
| 受控容量与排序服务 | 改善拥堵下的纳入和成交质量 | 高 | P1，需要业务规则和可验证边界 |
| 确定性并行执行 | 提高独立和多市场负载容量 | 高 | 条件式 P1，必须有依赖图依据 |
| JIT 和更深的执行优化 | 降低计算密集负载成本 | 高 | 条件式 P1/P2，取决于计算占比 |
| 新认证结构、专用执行域 | 提高架构上限或提供新能力 | 很高 | 长期独立立项 |

这里“依据测量”不是推迟决策，而是明确哪些项目值得立即投入、哪些项目需要进入下一阶段的证据。

---

## 6.3 短期：T0 至约三个月

<b>目标：形成可解释的性能基线，交付实际交易路径改善，并启动 native AA 的跨层设计。</b>

### 第一条工作线：继承已有测试，升级其分析能力

以 Arsia 清算压测为基础，保留多机器人竞争、热点池和普通用户背景负载，同时加入 mStocks 发行、普通买入、报价更新和 AA Sponsor 场景。旧压测已经覆盖入口、预确认、batcher 和证明，应该继续沿用这一系统边界。[MegaEth 高性能技术解析](https://app.notion.com/p/3d92f04c436c8106a243f8df68df4667?pvs=204)

新增的关键能力，是把提交、准入、排队、执行、root、可读、DA 和证明的时间关联到同一交易或批次，并生成真实状态依赖图。

测试不能只按 Gas 匹配。相同 Gas 的交易，可能具有不同的 CPU、冷读取、新增状态、依赖和证明成本。Mock 适合压力扫描，真实协议回放适合验证负载真实性，两者应互补。

### 第二条工作线：优化当前快路径

排查现有构建与提交之间的空窗，隔离昂贵查询与交易入口，改善状态流和 RPC 新鲜度，并实施已经能够确认收益的缓存、预读和批量访问优化。

短期不应同时重写数据库、调度器和状态承诺。

### 第三条工作线：账户与产品闭环

产品侧完成一次确认购买、受限代付、限权 Agent、幂等重试和明确的交易状态。

协议侧形成 native AA 原型，覆盖交易池、验证预算、nonce 域、撤权、费用失败，以及派生和证明端影响。产品能力可以先行，但不能因此将合约级方案宣称为 native AA 已完成。

- \*短期验收：\*\*不仅有一个更高的数字，而且能够解释收益来自哪一层、是否传递到用户路径、是否把积压推给下游。

---

## 6.4 中期：约三至六个月

<b>目标：建立原生账户与交易服务能力，提高真实混合负载下的持续容量。</b>

Native AA 进入客户端、钱包、RPC、派生和证明的集成验证。主网激活依赖正确性和安全门槛，而不是到了月份就自动发布。

性能主线根据短期结果选择：如果 IO 与 root 占主导，继续优化状态系统；如果依赖图显示足够并行度，推进确定性并行；如果计算占主导，则提前引入热点编译执行。

交易服务主线开展有限范围的容量保障、报价更新和撤改规则试点。外部构建服务需要截止时间、失败回退和可审计规则，不应通过人为拖慢默认入口来强迫流量迁移。

同时扩充 DA、证明与恢复余量，避免本地容量扩大后形成新的长期债务。

- \*中期验收：\*\*业务高峰下有效完成率和尾延迟改善；热点负载不失控；DA 和证明积压在约定范围内回落；maker 与 taker 的交易质量没有单边退化。

---

## 6.5 长期：约六至十二个月及以后

<b>目标：只对已经证实的剩余限制进行架构级改造。</b>

候选项目包括深度数据库重构、选择性原生执行、专用资产或交易模块，以及更强的排序可验证性。

更换状态承诺或引入专用执行域之前，需要单独回答统一账本、跨模块原子性、witness、证明、DA、桥和退出机制的问题。

L3 不应成为 mStocks 产品闭环的前置条件。它是否值得采用，取决于是否真的需要独立的执行规则、容量和迭代边界，以及跨域代价是否可接受。

如果现有统一执行环境已经满足需求，继续投入交易质量、流动性和发行流程，可能比再次更换底层架构更有价值。

## 6.6 工作量与依赖关系

以下是规划用的数量级估算，不是对现有代码完成度的审计，也不是上线承诺。实际投入可能因证明适配、历史兼容和审计返工显著变化。

| 工作包 | 粗略工程投入 |
| --- | --- |
| 端到端观测、重放和依赖分析 | 6–10 人周 |
| 构建、状态流和读取路径优化 | 8–14 人周 |
| mStocks 账户与操作闭环 | 8–14 人周 |
| Native AA 原型与跨层设计 | 6–12 人周 |
| Native AA 完整协议集成 | 20–40+ 人周 |
| 增量状态访问与 root 优化 | 10–20 人周 |
| 确定性并行执行 | 20–36+ 人周 |
| 受控 QoS 与排序服务 | 10–18 人周 |

这些工作不能机械相加，也不能假设都能无限并行。主要依赖关系是：

```txt
重放与分层测量
    ├── 构建 / 状态流优化 ── 业务排序与容量服务
    ├── 状态数据路径优化 ── 确定性并行执行
    └── 计算 profile ───── 选择性 JIT

账户与资产接口
    └── Native AA 原型 ─── 客户端、钱包、派生和证明集成

所有容量提升
    └── DA、验证、同步和故障恢复共同验收
```

每次上线应尽量保持改动边界可解释。新 AA 语义、新数据库、新调度器和新排序政策同时切换，会显著扩大验证组合与故障定位成本。

# 七、如何把这篇文章用于开发者 onboarding？

新同事的学习目标，不应是记住项目用了哪些技术名词，而是能够从现象反推瓶颈。

建议将 onboarding 组织为四个实验。

- \*第一个实验：跟踪一笔交易。\*\*从签名到可读结果，再到数据发布和结算，画出实际时间线，说明每一阶段可以依赖什么保证。
- \*第二个实验：构造不同资源负载。\*\*分别运行计算密集、状态读取密集、新状态写入、多独立账户和单热点池场景，解释为什么相同 TPS 或 Gas 可能对应不同压力。
- \*第三个实验：分别开启不同优化。\*\*对比流水线、预读、并行执行和增量发布，观察它们改变的是吞吐、等待、尾延迟还是状态新鲜度。
- \*第四个实验：让下游失败。\*\*中断 batcher、证明服务、RPC 或 leader，检查系统是否背压、预确认是否按定义恢复、跟随节点是否能追赶。

最终，新同事应当能够回答：

> 为什么这条链慢？慢在资源、依赖、通信、时间窗口，还是长期状态增长？拟议改动消除了什么成本，又把什么成本转移到了哪里？

# 结论

从通用系统看，高性能链建设不是一组互不相关的技术升级，而是对以下关系的重新设计：

<b>谁处理请求，谁决定顺序，谁执行，谁保存状态，谁验证，以及谁在什么时刻能够依赖结果。</b>

不同优化解决的问题并不相同：

- 连续构建减少阶段等待。
- 并行执行利用独立工作。
- JIT 降低计算成本。
- 数据库与认证结构优化降低状态处理成本。
- 增量预确认提前反馈，但不自动加快最终结算。
- DA、证明和恢复能力决定扩容能否持续。
- 容量和排序规则决定性能收益由哪些业务获得。

对 Mantle，合理路线不是先追求一个通用 TPS 数字，再为它寻找用途，而是先根据 mStocks 的发行、普通交易、做市和 Agent 场景定义服务要求，再沿着这些业务经过的系统路径逐层消除瓶颈。

- \*短期优先减少操作与等待，中期建立原生账户、交易服务和持续执行能力，长期再判断是否需要改变认证结构或执行域。\*\*这既承接了你们此前关于 RISE、并行 EVM、QMDB、Base 扩展、A2S 和 Arsia 压测的研究，也把这些研究放回了同一个可解释、可验证的系统模型中。
