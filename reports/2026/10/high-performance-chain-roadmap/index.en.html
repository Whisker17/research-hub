High-Performance Chain Design: Components, Bottlenecks, and Mantle's Engineering Roadmap

Chain performance comes from 8 layers of work, not from the executor alone. Mantle mainnet now uses about 0.17% of its gas limit, so fix latency, ingress, and accounts first, then scale execution and state when measurements call for it.

Key point first: chain performance is not one number. Different components limit throughput, latency, tail latency, state freshness, and sustained capacity (F1). Two things limit an L1: whether the slowest acceptable validator can replay blocks in time, and voting rounds. An L2 can make its real-time path fast, but its sustained capacity is the minimum of execution, DA, and proving (F2).

The industry moved faster in 2026 than our 2025 internal research. In reth, the state-root work left at block end is now 1–2 ms. Cold reads are the main remaining cost (F9, F11). OP Stack chains moved preconfirmations away from rollup-boost / op-rbuilder, into short native blocks or in-house systems (F8). Ethereum blob capacity, shared by all L2s, is only about 152 KB/s (F14).

For Mantle: mainnet uses about 0.17% of its gas limit on average, and all latency growth in the load test came from queueing (F19). So the short term is measurement, an mStocks peak plan, sub-second preconfirmations, and the account layer. Parallel execution, JIT, and a new state structure start only when measurements justify them (roadmap).

Conclusion

Fix latency, ingress, and accounts first; scale after you measure

Background

Running example: Alice buys one mStock with USDC from an AMM pool on Mantle. Each component section uses this order to show where it can get stuck.

B-1

Five performance metrics

~3min
What it is

Throughput is work done per unit of time. Latency is the time from submission until you can rely on a transaction. Tail latency looks at p99. State freshness is how far the state you read lags behind. Sustained capacity is the long-run limit with no backlog.

Why it matters here

Each component limits a different metric. Parallel execution raises throughput, preconfirmations cut latency, and DA and proving set sustained capacity.

Minimal example

Mantle load test: saturated throughput 29.5M gas/s, chain-inherent latency 2 s, end-to-end 18.2 s.

Common misconception

Myth: high TPS means a good experience. Fact: in Mantle's load test, all added latency came from queueing, not from the chain.

[24] Mantle internal load-test report §3

B-2

The two L2 paths and three heads

~4min
What it is

Real-time path: the sequencer orders and executes, producing unsafe blocks. Safety path: the batcher posts data to L1, nodes derive safe blocks from L1, and blocks become finalized once L1 finalizes.

Why it matters here

An L2 lets the real-time path run ahead of the safety path. If the safety path falls behind for long, the backlog keeps growing.

Minimal example

OP Mainnet: unsafe about 2 s, safe in minutes, finalized in about 15–30 minutes.

Common misconception

Myth: 7 days is finality. Fact: 7 days is the standard bridge withdrawal delay, and a challenge does not reorg the L2 chain.

Go deeper

[3] OP Docs, Transaction finality

Needs: B-1

B-3

Critical path and pipelining

~3min
What it is

The critical path is the chain of steps that must finish in order. Pipelining overlaps different stages of different blocks.

Why it matters here

Pipelining raises steady-state throughput but does not shorten one block's end-to-end time. This is the difference between "faster" and "more".

Minimal example

Parallel execution time T ≥ max(W/p, L): W is total work, p is threads, L is the longest dependency chain.

Common misconception

Myth: more threads give unlimited speedup. Fact: the dependency chain L does not shrink with more threads.

Go deeper

[5] Blumofe & Leiserson 1999

Needs: B-1

B-4

State root and merkleization

~3min
What it is

The state root is one hash that commits to all state. Each block writes its changes into the Merkle Patricia Trie (MPT) and rehashes up to the root. This step is merkleization.

Why it matters here

Both block building and validation wait for the root. In 2024 the root took more than 75% of reth's block-sealing time. By 2026 reth runs it in a pipeline.

Common misconception

Myth: the root is always the bottleneck. Fact: Reth 2.0 cut the root work at block end to 1–2 ms.

Go deeper

[10] Paradigm, "Releasing Reth 2.0"

Needs: B-3

B-5

Preconfirmation

~3min
What it is

The sequencer streams the order or results of some transactions before it seals the full block.

Why it matters here

It sets how fast users see results. Mantle has no sub-second preconfirmations today, so its floor is the 2 s block interval.

Common misconception

Myth: a preconfirmation is finality. Fact: it carries the sequencer's trust assumption and can be withdrawn.

Go deeper

[13] OP Docs, Subblocks

Needs: B-2

B-6

DA and blobs

~3min
What it is

Data availability (DA) means others can get the data they need to rebuild or verify the chain. An L2 compresses its transaction batches and posts them in Ethereum blobs.

Why it matters here

However fast execution is, data that the batcher cannot post piles up. All L2s share blob capacity.

Minimal example

One blob holds 130,044 bytes; the current target is 14 blobs per block.

Common misconception

Myth: the state root is small, so the data to publish is small. Fact: a root cannot replace the data itself.

Go deeper

[15] OP Spec, Ecotone blob encoding

Needs: B-2

Fig 2 puts Alice's order on the two L2 paths. The top row sets how fast Alice sees her fill. The bottom row sets how fast the fill becomes irreversible, and whether the system can keep running like this.

F1

Performance is not one number: five metrics, each limited by different components

confidence: high
Claim

Pipelining raises steady-state throughput but does not shorten one block's latency. A preconfirmation gives feedback earlier but does not speed up finality. Parallel execution can only use independent work that already exists. A fast read response does not mean fresh state.

Evidence

inferred From the work/span bound, the semantics of RISE shreds and OP Subblocks, and Block-STM's ordering-equivalence rule (ledger S8, B7, B17, E11, R14). inferred The read-path trade-off (B65).

Implication

Before you judge any optimization, write down which metric and which layer it changes.

F2

L1 and L2 limits come from different places

confidence: high
Claim

Every L1 validator replays every block, so the slowest acceptable validator's replay and catch-up speed limits capacity. Normal-path voting rounds have a theoretical lower bound. An L2's real-time path can be fast, but sustained capacity is the minimum of execution, DA posting, and proving.

Evidence

observed Solana required more than 70% of stake to run XDP before 100M CU blocks. It also noted that large blocks slow replay (S16, S59). Two-step Byzantine consensus needs n ≥ 5f−1 (S21). observed In the OP Stack, nodes drop data that the batcher did not post within the 12-hour sequencing window (S5). inferred S60.

Implication

Judge any L2 "high performance" claim together with its DA and proving headroom, not only by how many transactions the sequencer executed.

Self-check for new engineers: after reading the page, you should be able to answer these 4 questions.

  1. An RPC replies fast, but the router's quotes keep failing. Which layer could be stuck?
  2. If the block interval drops from 2 s to 200 ms, which fixed costs now happen 10 times per second?
  3. At the same 1,000 TPS, why do transfers and liquidations put different loads on the chain?
  4. An optimization raises sequencer throughput. Which two downstream paths must you check?
K

Component ①: accounts, transaction expression, and admission

What goes wrong (Alice's order):

  • One business action becomes several protocol actions: get gas, approve, swap, buy. Each step needs a signature and a wait.
  • Admission costs come before fees: an invalid transaction uses parsing, signature checks, and simulation before the node rejects it.
  • Nonce head-of-line blocking: if one transaction from an account is stuck, unrelated later actions also wait.

F3

At peak load, ingress breaks first, not execution

confidence: high
Claim

At saturation in Mantle's load test, end-to-end latency rose from 3.4 s to 18.2 s. All of the increase came from self-queueing and mempool backlog. The HTTP 429 rate on writes was 7.9% (67% before tuning). Many bots racing for the same borrower caused 27–49% guard reverts.

Evidence

observed Internal load-test report, 2026-06-24 (ledger K8, K9). inferred R7.

Implication

Before mStocks launches, add ingress rate limits, sender-side backpressure, and hot-spot partitioning. The native AA design must also cover txpool validation budgets, revocation, and sponsorship failure semantics.

L

Component ②: propagation

What goes wrong:

  • Leader upload fan-out: sending one block to N nodes needs bandwidth that grows with N.
  • Hop count: each hop costs at least one one-way network delay. Anza holds that network latency, not transfer or compute time, mostly sets propagation delay.
  • On an L2, the matching problem is not network-wide voting. It is distribution from the sequencer to follower nodes, RPCs, and apps.

Optimization paths and examples:

Erasure coding + multi-level tree Solana Turbine ✓mainnet
Erasure coding + two-level tree; upload independent of node count Monad RaptorCast: worst case 1 RTT ✓mainnet
Single relay layer, fewer hops Alpenglow Rotor ✗not scheduled
Dedicated low-latency network DoubleZero: about 58% of Solana stake connected (project dashboard) !ingress filtering not live
L2 streaming distribution OP Stack p2p for unsafe blocks; preconfirmation streams ✓
F4

Before raising block capacity, prove the network can deliver in time

confidence: medium
Claim

Under 20% packet loss and 33% malicious nodes, RaptorCast sends about 87% extra chunks so that it never retransmits. Before raising blocks to 100M CU, Solana required more than 70% of stake to run XDP kernel-bypass networking.

Evidence

observed Monad Docs, RaptorCast (S12, S13); Solana 100M CU page (S16). observed Rotor is not scheduled (S14).

Implication

For a single-sequencer L2, the main network work is read-path distribution and preconfirmation streams, not consensus propagation.

M

Component ③: ordering, consensus, block building, and preconfirmation

This layer does three jobs. Ordering decides the sequence. Block building decides which transactions go in and when to seal. Consensus makes many parties accept the same chain. An L1 does all three; a single-sequencer L2 mainly does the first two.

F5

Consensus rounds have a lower bound; "faster" is paid for with assumptions

confidence: high
Claim

Partially synchronous Byzantine consensus can decide in 2 message delays only if n ≥ 5f−1; PBFT-style protocols need 3. Alpenglow's roughly 150 ms is a simulated median without compute cost, with "20% malicious + 20% offline" fault tolerance. MonadBFT runs 300 ms blocks with 600 ms finality.

Evidence

observed PODC'21 paper (S21); solana.com Alpenglow page and Anza blog (S22–S25); Monad Docs (S29–S31). inferred No public mainnet measurement yet (S26).

Implication

Before you compare finality numbers, check whether each one comes from a simulation, a self-test, or mainnet.

F6

Decoupling execution from consensus buys execution time at the cost of user-visible semantics

confidence: medium
Claim

Monad's consensus agrees only on order, and proposals carry the state root from D=3 blocks earlier. Consensus sees only old state, so Monad adds a 10 MON reserve balance. Ethereum Glamsterdam adopts ePBS (EIP-7732); delayed execution (EIP-7886) is Stagnant.

Evidence

observed Monad Docs (S41–S43); EIP-7732 / 7886 / 7773 (S45–S47). inferred Costs include a lagging root, changed admission rules, and later detection of divergence (S58).

Implication

An L2 sequencer does not vote anyway. For Mantle, the useful lesson here is to move merkleization off the critical path. See O.

F7

L2 tail latency comes from the state root and storage IO

confidence: high
Claim

OP Stack block building is a serial loop: prepare attributes → execute → getPayload seals (computes the root) → gossip. On Base mainnet, one root per Flashblock took about 130 ms. After Base moved the root to the final block only, build P50 fell from 150 ms to 10 ms. In Base's own test, Geth build p99 was 2,319 ms and Reth 698 ms.

Evidence

observed OP Spec exec-engine (B1); Base blog (B2–B4); before NVMe, OP Mainnet blocks degraded to 2.5–3 s (B5). inferred B8.

Implication

Mantle's eager next-block construction shortens the gap between blocks. The next gain is in the root and IO, not in the interpreter.

In 2026, preconfirmations moved into the protocol or in-house stacks; the trust assumption did not change

confidence: high

N

Component ④: execution (scheduling and VM)

The execution layer has three kinds of bottleneck, each with a different fix:

  • Compute: interpreter dispatch, precompiles, keccak. Interpreter work or JIT can shrink it.
  • Waiting for state: cold SSD reads and trie read amplification. Prefetching, caching, and better storage can shrink it.
  • Business-level serial dependencies: many transactions change the same pool. Only a change in the application or the state layout helps.
F9

In 2026 reth-class clients, the remaining bottleneck is cold reads, not the interpreter

confidence: high
Claim

Base measured that blocks with heavy storage access take about 30× longer to execute than blocks without it. evm2's interpreter work is only 4.8–6.2% faster on mainnet replay. revmc JIT is 1.85–19× faster on synthetic loads but only 1–10% faster on L1 historical sync.

Evidence

observed Base blog (E3, E4); revm-vs-evm2 ledger H37 (E8); Paradigm revmc blog (E32). inferred E9, E38.

Implication

JIT matters only for compute-heavy contracts. Mantle should first measure the compute share with a profile, then decide (R12).

F10

Real workloads have little parallelism; parallel designs come in three kinds

confidence: high
Claim

Declared (Solana account locks, Sui object ownership), optimistic (Block-STM, Monad, Sei Giga Ares), and validation-assisted (EIP-7928 BAL). Recent Ethereum blocks have a median parallelism below 2. RISE pevm averages about 2.02× on in-memory mainnet replay. reth and geth both implement the BAL path, but Glamsterdam is not on mainnet, so it is not active there.

Evidence

observed Block-STM paper and chain docs (E11–E15); MegaETH research page and pevm benches (E18, E19); EIP-7928, reth v2.8.0, geth v1.17.9 (E20, E22, E28, E29). inferred E31.

Implication

Mantle's 2025 "49.1% dependency rate" used heuristics (same sender, same contract and selector). It is not an upper bound on parallel gains. Measure slot-level read/write sets first (M43, M45).

O

Component ⑤: state access, commitment, and persistence

One write goes through four steps. Read the old value, keep a revertible change, update the trie and root, then persist in batches. Each step has its own bottleneck.

F11

The state root is no longer reth's critical-path bottleneck; moving it off the path is now common

confidence: high
Claim

Reth 2.0 keeps a sparse trie cache across blocks, which cuts the root work at mainnet block end to 1–2 ms. Paradigm restarted revmc because of this and plans full parallel execution on BAL. Monad delays the root by D=3 blocks; RISE shreds skip it on the preconfirmation path. Sei Giga uses an LtHash digest of the write log. The EF Hegotá tier list defers EIP-7862 (delayed state root).

Evidence

observed Paradigm blog and reth v2.0.0 release (E5, E7, E51); Monad Docs (E49); RISE blog (B7); Sei Docs (E55); EF Hegotá post (E54). inferred E56.

Implication

The 2025 conclusion "execution takes only 1/6–1/10 of merkleization time" no longer holds (E70).

F12

Storage: a trie on top of a KV store amplifies reads; new structures mostly cite their authors' own benchmarks

confidence: medium
Claim

base/triedb estimates that an MPT inside a generic KV store needs about 50 disk operations per value. Page-based layout cuts this to about 4–8. MonadDb implements the Patricia trie natively with io_uring; MIP-8 changes the storage commitment to 4 KiB pages. Reth Storage v2 cut persistence for gigagas-scale blocks from 8.4 s to 0.4 s. QMDB claims 6× over RocksDB, and NOMT has shipped 1.0.x.

Evidence

observed base/triedb README (E39); Monad Docs and MIP-8 (E40, E41); Paradigm (E6, E46); QMDB paper and Commonware (E42, E43); NOMT (E44). inferred E48.

Implication

Storage work that keeps the MPT root unchanged is class A. Changing the commitment structure is class D (see S).

F13

State growth means "put it all in RAM" is not free

confidence: medium
Claim

In 2026-01 the geth state database was about 390 GiB. After the gas limit went from 30M to 60M, state grows about 116 GiB per year. Since 2025-07, all execution clients can drop pre-merge history (saving 300–500 GB). Full rolling history expiry and state expiry are still research. MegaETH's 2024 "all state fits in RAM" assumed about 100 GB.

Evidence

observed EIP-8037 (E61); EF blog (E57–E59); MegaETH research page (E64, E67). inferred E69.

Implication

Keeping state in memory only fixes read latency. It does not remove the cost of the root, persistence, DA, or proving.

P

Components ⑥⑦: data availability, proving, and settlement

These two layers set sustained capacity. However fast the sequencer runs, the backlog grows if the batcher cannot post data or proofs fall behind.

F14

Shared blob capacity is about 152 KB/s, and small transactions hit DA limits first

confidence: high
Claim

One OP Stack blob holds 130,044 bytes. After BPO2, the blob target / max per block is 14 / 21, or about 152 / 228 KB/s, shared by all L2s. At 100 bytes per transaction, that supports about 1,500 / 2,300 TPS. If Mantle filled its 60M gas / 2 s blocks with 21k-gas transfers, it would need about 143 KB/s. EigenDA V2 claims 100 MB/s, but its security rests on a restaking quorum.

Evidence

observed OP Spec (B30); EF Fusaka announcement (B31); EigenDA blog (B37). inferred B33, B34, R8; B39.

Implication

Raising the gas limit alone does not add capacity for small Mantle transactions. Capacity plans must include compression ratios and blob prices.

F15

Proving capacity is a sustained limit; the common pattern is TEE / optimistic plus ZK on demand

confidence: medium
Claim

Base wrote that an optimistic system "cannot produce more data than the proof system can prove". Base Azul uses TEE + ZK multi-proofs: when both agree, settlement takes 1 day. BOB's Kailua is optimistic by default and proves only 6 blocks in a dispute. Axiom's own test proves L1 blocks on 4 RTX 5090s with p99 of 9.7 s.

Evidence

observed Base blog and Docs (B42, B43); BOB Docs (B47); Axiom (B48); Ethproofs (B49). speculative A linear extrapolation by gas rate suggests real-time proving of a 200 Mgas/s L2 needs about 40× the GPUs (B50).

Implication

Mantle publishes no proof latency. Every capacity change must include "proof lag" as an acceptance metric (R9).

Q

Component ⑧ and cross-cutting: read path and fee metering

F16

A fast response is not fresh state

confidence: medium
Claim

MegaETH replica nodes apply the sequencer's execution results without re-executing; full nodes re-execute on their own. On Base's Flashblocks-aware RPC, the block context of eth_call pending can lag by about 5 blocks. The returned state still includes every Flashblock received. OP Subblocks require RPC nodes to execute transactions themselves to get state.

Evidence

observed MegaETH Docs (B62); Base Docs (B64); OP Docs (B15). inferred B65.

Implication

Routers and market makers need fresh state with a version number. Measure RPC response time and state freshness separately.

F17

Fees allocate capacity: Jovian already puts DA into the base fee

confidence: medium
Claim

OP Stack Jovian adds a minimum base fee and a DA footprint. It estimates each transaction's DA bytes with FastLZ and adds them to blobGasUsed. The base fee then updates with max(gasUsed, blobGasUsed). Before this, chains could only throttle the batcher, which pushed the base fee down and caused priority-fee auctions. Arbitrum shipped multi-dimensional pricing in ArbOS 61 but says not to enable it; EIP-7999 is still a Draft.

Evidence

observed OP Spec Jovian (B52, B53); Arbitrum notice (B57); EIP-7999 (B60); ZKsync OS double accounting (B58); MegaETH dual gas (B59).

Implication

Mantle already aligned with Jovian in Arsia (M9, M10). Before the mStocks peak, rehearse SystemConfig parameters before you consider new fee dimensions.

F21

The change class sets the complexity: class C changes Go, Rust, and the proof program together

confidence: high
Claim

Mantle builds its SP1 proof program from kona, and the program redoes derivation and execution inside the zkVM. So any change to derivation or the state transition must change op-node, op-geth, reth / op-revm, and kona, and rotate the vkey. A change to sequencer scheduling that keeps canonical results does not touch proofs. A new state commitment also affects withdrawal proofs on L1.

Evidence

observed OP Succinct does not change op-geth / op-batcher / op-node (M55); Mantle SP1 Workflow (M56); output root construction (M60). inferred M57, M59, R5.

Implication

Swapping the EL is class A but carries class C verification work. In 2026-01, Mantle already had one incident where revm and geth disagreed and the prover could not produce a ZKP (M58, R4).

Limits and open questions

  • Public data cannot confirm the mainnet sequencer's real setup: the op-node version (is eager build on?), the execution client, and whether the preconfirmation lane is active (K5, M15). We guess the sequencer still runs mainly on op-geth ([speculative] M24).
  • Mantle publishes no proof latency (M26). The "proving headroom" threshold in the roadmap needs operations data.
  • No Mantle-specific execution profile exists. The E findings come from Ethereum and Base data; Mantle's more concentrated load may differ.
  • The load test used synthetic load: mock contracts on the Sepolia QA chain, not a fork of mainnet state (K7).
  • mStocks terms have only secondary sources: the claim that Halo Prime Limited is the issuer has no primary text ([speculative] M36). The launch target is 2026-11 (M34).
  • Many external numbers are self-reported or simulated: Alpenglow 150 ms, QMDB 6×, RISE 5 Ggas/s, Sei 5 Ggas/s.

Glossary

sequencer
The L2 node that receives, orders, and executes transactions and produces blocks.not a validator set
derivation
Rebuilding L2 blocks deterministically from L1 data only.not syncing from the sequencer
unsafe blockunsafe head
A block the sequencer produced that cannot yet be derived from L1 data.not an invalid block
preconfirmationpreconf
The sequencer publishes the order or results of some transactions before the full block is sealed.not finality
state root
One hash that commits to all state, recomputed every block.not the block hash
merkleization
Writing state changes into the trie and rehashing up to the root.not persistence
critical path
The chain of steps a piece of work must finish in order.not the most expensive step
pipelining
Overlapping different stages of different blocks to raise steady-state throughput.does not cut one block's latency
sustained capacity
The long-run limit with no backlog, set by the smallest of execution, DA, and proving.not peak TPS
state freshnessfreshness
How far the state you read lags behind the latest execution result.not RPC response time
DAdata availability
The guarantee that participants can get the data needed to verify or rebuild the chain.not propagation
blobEIP-4844 blob
A large data object attached to an Ethereum block; L2s post batches in it.not calldata
BPOblob-parameter-only fork
A small fork that changes only the blob target / max.
eager next-block construction
Start building the next block right after sealing the previous one, to shorten the gap.not a preconfirmation
BALblock-level access list, EIP-7928
The block lists the state each transaction read and wrote, so validators can work in parallel.not a scheduler
Block-STMoptimistic parallel execution
Run in parallel first, then validate read sets in the preset order and re-execute on conflict.result equals serial order
reserve balance
Monad's rule that lets consensus include transactions safely while it sees only old state.
ePBSEIP-7732
Proposer-builder separation that moves payload validation off the consensus critical path.not delayed execution
JITjust-in-time compilation
Compile hot contract bytecode to machine code at run time.does not change gas semantics
cold read
A read of state that is not cached in memory and must hit the SSD.
sparse trie
Loads only the changed trie paths, used to compute the root in the background.
SystemConfigL1 config contract
An L1 contract whose parameters reach L2 through derivation, such as gas target and min base fee.changing it needs no hard fork
DA footprintJovian DA metering
Adds estimated DA bytes to a block's blobGasUsed, which feeds the base-fee update.not the L1 data fee
konaRust OP Stack implementation
Mantle's SP1 proof program is compiled from it and redoes derivation and execution in the zkVM.
vkeyverification key
The key an L1 contract uses to verify SP1 proofs; it rotates whenever the proof program changes.
2D noncetwo-dimensional nonce
One account has several independent nonce sequences, which avoids head-of-line blocking.does not remove state conflicts
native AAnative account abstraction
Protocol-level support for smart accounts, sponsorship, and session keys.not ERC-4337
replica node
A read node that applies the sequencer's results without re-executing.not a full node
