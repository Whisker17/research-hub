Background

Running example: mainnet block 102640855 holds an ERC-4337 handleOps transaction. It used 120,982 gas, and its DA footprint is 151,600 (K41). The sections below use it to show where each stage can limit a transaction.

B-1

Commitment levels: six different kinds of "fast"

~3min
What it is

A transaction gets six results in order: submission accepted, preconfirmed, readable over RPC after sealing, published to DA, proven, settled. Each level is a different strength of promise.

Why it matters here

E1–E8 in the draft measure the first three levels. Capacity depends on the last three. One set of numbers cannot stand in for the other.

Minimal example

Illustration: a transaction becomes readable over RPC about one block interval (2 s) after sealing. Proofs arrive per range: the latest submission came about 40 minutes after its range's last block and 100 minutes after its first (D42).

Common misconception

Myth: a fast receipt means the transaction is safe. Fact: the receipt is the sequencer's promise. E4 tests whether the sequencer keeps it.

[9] OP Spec; GPT review §1.1 (lead only)

B-2

Queues and backlog

~3min
What it is

The backlog of each stage changes as dQ/dt = λ − μ. λ is the arrival rate and μ is the service rate. When λ stays above μ, the backlog keeps growing.

Why it matters here

If a downstream stage (DA, proving) cannot keep up, a faster sequencer only grows the backlog. After a burst, draining takes about Q / (μ − λ_normal).

Minimal example

At default concurrency the prover runs one range (1,800 blocks) at a time. If one range takes more than about 3,600 s, ranges pile up (D72).

Common misconception

Myth: if the backlog clears after the load stops, the system recovers. Fact: production traffic does not stop, so draining is slower.

Go deeper

GPT review §1.2, E8 (lead only); ledger D70

Needs: B-1

B-3

Preconfirmation

~4min
What it is

The sequencer executes a transaction and returns a receipt before it seals the block. Mantle has two implementations: the op-geth one (in the mainnet client; we could not confirm it is on) and the reth one (enabled on Sepolia and the standby node).

Why it matters here

It sets how fast users see results. It also sets what the sequencer has promised them.

Minimal example

reth defaults: 1 s timeout, 2M gas per transaction, 6M gas budget per block, normal transactions released every 200 ms (P4–P8).

Common misconception

Myth: --preconf.all is the on switch. Fact: the switch is --preconf.enable; --preconf.all is an eligibility rule (P1, P2).

Go deeper

[1] mantle reth preconf crate; [2] op-geth preconf package

Needs: B-1

B-4

Sealing and persistence

~3min
What it is

Sealing a block computes its state root. Persistence writes sealed blocks to the on-disk database. reth persists on its own thread, in parallel with executing the next block.

Why it matters here

Slow sealing delays block publication. If persistence falls 16 blocks behind, reth stops serving engine requests (X84).

Minimal example

Mantle production reth persists every block, and MDBX runs in Durable mode (K5, K6).

Common misconception

Myth: Reth 2.0 cut the root to 1–2 ms, so the root no longer limits sealing. Fact: that is the engine validation path. Mantle's builders do not use it (X42).

Go deeper

[4] reth v2.2.0 engine tree; [12] Paradigm, Reth 2.0

Needs: B-2

B-5

How many samples tail latency needs

~3min
What it is

p99 is the 99th percentile. To estimate it, the sample must hold enough of the slowest 1%.

Why it matters here

The draft's E8 runs about 40 full blocks. In 40 samples, the expected count above the true p99 is only 0.4 (K35).

Minimal example

30 minutes of 2 s blocks gives 900 blocks. The true p99 then lies between the 16th and 4th largest sample with about 96% probability (K36).

Common misconception

Myth: many transactions make a block-level p99 reliable. Fact: for block-level metrics, the sample size is the block count, not the transaction count.

Needs: B-2

B-6

DA footprint

~3min
What it is

The OP Jovian rules estimate each transaction's compressed size and multiply it by a scalar (400 on Mantle). The result is the DA footprint. The block's total footprint may not exceed the gas limit.

Why it matters here

The base fee follows max(gasUsed, footprint) (D20). Small transactions can hit the footprint limit first.

Minimal example

The running example used 120,982 gas but has a footprint of 151,600, so the fee follows the footprint (K41, K42).

Common misconception

Myth: if the footprint hits the limit first, L1 blob bandwidth is short. Fact: Mantle's blobs are only about 5% full (D13, D27).

F2

The mainnet sequencer is still op-geth; the draft's reth path is the target architecture

confidence: high
Claim

The deployment profile confirmed on 2026-10-27 shows op-geth v1.6.3 producing mainnet blocks. Mainnet reth is a standby sequencer that follows it. reth produces blocks only on Sepolia. So the draft's "passive mainnet measurement" and its "QA-chain experiments" measure two different implementations.

Evidence

observed Deployment profile config/repos.json@6be759c (K1–K4). observed The public RPC reports Geth/v1.17.3 (K17). inferred K9, K10. observed The GPT review does not separate the two implementations (G3).

Implication

E0 first records each environment's sequencer client and preconf mode. Group every result by client. Do not compare across groups.

F3

A reth preconf commitment can be lost on power loss or failover

confidence: high
Claim

After reth gets the execution receipt from the builder, it tries to append the commitment to its journal, then returns the receipt to the client. The write flushes but does not fsync. A failed write only logs a warning, and the client still gets the receipt. The journal stores the transaction and a predicted block number, not the execution context, and the code has no failover handoff. The op-geth version in the mainnet client is weaker: commitments live only in memory, and receipts come from a shadow environment. We could not confirm that mainnet enables it.

Evidence

observed journal.rs:234–235, rpc.rs:245–253, the JournalEntry fields (P22–P25). observed op-conductor only replicates sealed blocks (P41, P42). observed op-geth's FIFO is memory-only and its receipts come from a shadow environment (P82, P84); no record shows whether mainnet enables it (K12). inferred P34, P43, P88. speculative If the team adds conductor failover after the switch, some receipts may go unhonored (P44).

Implication

E4 is a launch gate: run a fault matrix on both paths. Before you promise "always lands on chain", design a durable or replicated write, and refuse the receipt when the write fails.

F4

With --preconf.all and the default budget, reth admits about 6M gas of new user transactions per block

confidence: high
Claim

The reth pool listener pushes every eligible transaction into the preconf queue, and the normal packing path skips them. With preconf enabled, --preconf.all and the default budget, every transaction takes the preconf path. The pool rejects a transaction above 2M gas at entry and evicts new transactions beyond the 6M per-block budget; replayed earlier commitments bypass the budget. The draft's E3 "normal transaction" control group does not exist. In execution gas, E7 cannot reach the 15M target either.

Evidence

observed preconf_pool_listener.rs, payload_builder.rs:747, validator.rs, dispatch.rs:268 (P14–P18). observed Defaults at config.rs:36, 43 (P7, P8); Replay entries bypass the budget gate (P13). inferred P19–P21. inferred GPT found the control-group problem but not the capacity cap (G2).

Implication

Before reth takes over as sequencer, reset the eligibility rule and budget (R4). Run E3 only in allowlist mode.

F5

Eager build is deployed; its gain is capped near 50 ms per block

confidence: medium
Claim

--sequencer.eager-build is on by default and shipped with v1.6.3. It only moves the start of the next build to the moment the previous block becomes canonical. Seal timing does not change. op-node seals 50 ms before the payload time, so eager build removes at most about 50 ms of idle window.

Evidence

observed op-node/flags/flags.go:275–278, sequencer.go:25, 476 (P45–P47). observed v1.6.3 in the deployment profile (K1). inferred P48, P49.

Implication

In E2, bucket the gain by where in the slot a transaction arrives. Overall p99 will likely show no difference.

F6

As a sequencer, reth still computes the state root synchronously at the end of the block

confidence: high
Claim

Mantle has two reth builders, with and without preconf. Both drop the execution cache and sparse trie that the engine offers. Both call finish(…, None) when they seal. Reth 2.0's "1–2 ms root" applies only to the engine validation path. Upgrading dependencies alone does not change this.

Evidence

observed payload_builder.rs:888–892, 1185–1187; op-reth builder.rs:230, 473–474 (X35–X39). observed The v2.2.0 share flags are off by default (X79, X80). observed Paradigm's 1–2 ms is the root time left at the end of a block (X26). inferred X42–X44, X81. speculative Under full blocks, the synchronous root may become the sealing bottleneck (X75).

Implication

Add E9 to time the sealing root before the reth switch. If the root dominates seal time, fixing the builder may gain more than evm2.

F7

Production reth persists every block, so time it separately

confidence: medium
Claim

Every production reth node sets persistence-threshold=0, so each new block triggers persistence, and MDBX runs in Durable mode. Persistence runs on its own thread, in parallel with the next block. The engine stalls only when the gap reaches 16 blocks. Persistence writes may contend with execution's cold reads on the same disk. Nobody has measured whether this happens or how much it costs.

Evidence

observed Deployment profile (K5, K6). observed reth v2.2.0 config.rs:7, 10 and persistence.rs, tree/mod.rs (K14, X82–X84). inferred K15, X85. speculative Disk contention slows execution (X86). observed The 2026-10-27 check found 3 settings beyond the developers' first answer (K8).

Implication

In E6–E8, read commit_duration and the backpressure metrics before you decide to change disks. E0 must read config from the nodes, not from memory.

F8

At default concurrency, the prover must finish one range in about 1 hour, or the backlog grows without bound

confidence: high
Claim

Mantle runs OP Succinct in validity mode and submits to mainnet every 1,800 blocks (about 1 hour). The proposer's concurrency limit defaults to 1 and counts witness generation, execution and proving together. If production keeps the default, one range must finish in less than about 3,600 s under sustained load. Internal QA docs also list a one-range gateway and a 1,800 s witness timeout. Nobody has verified the production values.

Evidence

observed The last three validity-mode L1 submissions are 1,800 blocks apart (D39, D41), and the code sets the proposer's default concurrency (D71). observed The QA prover-network README: range size, concurrency, timeouts; it says deployment config decides the real values (K19–K23, K43); inferred D70, D72. speculative The draft says the bottleneck is ZK proving; no public result shows it (U4, D51).

Implication

Add E10. First read production's concurrency and timeout values. Then use the three stage durations in the database plus L2OO submission times to test "the bottleneck is proving" directly. Move this item from mid–long term to short term.

confidence: medium
Claim

In network mode, the proposer database stores 0 for cycles and prover gas, and the self-hosted cluster leaves those fields empty. The guest marks only two spans, derivation and execution; MPT and state-root work fall under execution. keccak already uses the SP1 precompile.

Evidence

Implication

F10

Hitting the DA footprint limit first does not mean L1 bandwidth is short

confidence: medium
Claim

Mantle's scalar is 400, so every transaction's footprint is at least 40,000, more than the 21,000 gas of a plain transfer. At the 15M target, a block can count only 37,500 estimated bytes. Real blobs are only about 5% full. So a footprint that hits the limit first shows a metering constraint, not a blob-bandwidth limit.

Evidence

observed Scalar 0x190 and receipts (D23, D24, K41). observed A blob carrying 6,836 bytes (D13). observed Jovian rules (D19, D20). inferred D25–D27. inferred The draft's 152 / 228 KB/s arithmetic is right (D9). observed But "100 bytes per transaction" is the fee-estimate floor, not a measured mean (D11).

Implication

Add E11: compare footprint with the batcher's real compressed bytes first. In E7, count load as max(gas, footprint).

F11

The draft's E8 fee-parameter direction is backwards

confidence: medium
Claim

The base-fee change scales with 1/denominator, so a faster reaction needs a lower denominator. A lower elasticity lowers the largest per-block rise. Neither drains a backlog faster. With current parameters, 40 full blocks raise the base fee about 10.3×. It then takes about 3.8 minutes to fall back to the floor.

Evidence

observed EIP-1559 formula (D30). observed Mainnet D=50, E=4 (K16). inferred D31–D35, K37, K38. inferred GPT's correction holds (G6).

Implication

In E8, record price recovery and queue draining separately. Use fee parameters only as a helper.

F12

40 full blocks cannot estimate p99, and most draft thresholds have no source

confidence: medium

In 40 samples, the expected count above the true p99 is only 0.4. The 200 ms seal threshold has no basis either: op-node leaves only 50 ms for sealing.

F13

confidence: medium
Claim

Reth v2.9.0 (10-29) switched to evm2 and reports execution about 10% faster. Mantle is on v2.2.0, and the latest OP upstream op-reth v2.8.0 is still on revm. If Mantle moves now, it must port at least 7 custom pieces itself, including the proving path.

F14

Short blocks are a protocol change, not a parameter

confidence: medium

op-node schedules in whole seconds. op-geth preconf hard-codes 2 s. At constant gas per second, 200 ms blocks give reth a 0.6M budget. That is below the 2M per-tx cap, so the current validation rejects the config. Base's Denim also changes timestamps and RPC semantics. Base plans its mainnet launch for November.

Limits and open questions

Limits

  • This page ran no experiment on the QA chain. Every "observation → action" is a reading rule, not a measured Mantle result.
  • The deployment profile comes from the author's config record (confirmed 2026-10-27) and covers only reth nodes. The op-geth sequencer's preconf settings are unknown (K12).
  • Prover-network soak results are not in the repository, so there is no data on range proving time (K40). The last three submissions are only 3 samples (D42).
  • Some reth source findings were read at symbol level, not traced line by line. "kill -9 recovers, power loss does not" is an inference (see the uncertainty notes in the P notes).
  • Speculative claims: P44, P79, P80, X33, X45, X75, X86, D16, D51, D68, U3, U4. The page marks each as speculative where it appears.

  1. Does the mainnet op-geth sequencer run preconf? What commitment level do users get?

Glossary

sequencer—
The L2 node that orders transactions and produces blocks.not the batcher
ELexecution client
The client that executes transactions and keeps state; Mantle has op-geth and reth.not op-node
preconfirmationpreconf
An execution receipt the sequencer returns before it seals the block.not finality
journalcommitment log
The local file where reth preconf writes commitments it has returned.not the txpool journal
fsyncsync_all
Forces file contents to disk so they survive power loss.flush only empties user-space buffers
eager build—
Starts building the next block as soon as the previous one is canonical.does not change seal time
sparse trie—
Part of the trie that reth keeps in memory across blocks to compute the root in parallel.not the full state
persistence—
Writing sealed blocks to the on-disk database.not sealing
backpressure—
When persistence falls 16 blocks behind, reth pauses engine requests.not RPC rate limiting
rangeproof range
The run of consecutive blocks the proposer proves at once; 1,800 on Mantle.not a batch
DA footprintDA metering
Estimated compressed bytes times a scalar; it limits a block together with gas.not real blob bytes
Storage v2—
reth's tiered storage format; v1 support ends 2027-01.not an MDBX version
critical path—
The longest chain of dependent steps; it caps parallel speedup.not the conflict rate
